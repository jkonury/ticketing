# herdr 오케스트레이션 워크플로

메인 세션이 **오케스트레이터**가 되어 구현자(impl)와 리뷰어(review) 에이전트에게 작업을 맡기고, 완료되면 검토·재검증·커밋까지 이어가는 방식이다. herdr 명령 자체는 [herdr.md](herdr.md)를 따르고, 이 문서는 그 위의 절차와 역할만 다룬다. Claude Code와 Codex 어느 쪽이 메인이어도 같다.

이 문서는 프로젝트에 묶이지 않는다. 아래 값은 대상 저장소의 프로젝트 지침(`AGENTS.md`·`CLAUDE.md`와 그 지침이 가리키는 문서)에서 찾는다. 지침에 없으면 사용자에게 묻는다.

- task 단위(모듈 경계), 커밋 규칙, 빌드·테스트 동시 실행 제약
- 변경 유형별 최종 검증 명령, 리뷰 기준 문서와 불변 조건
- 지시서 작성 원칙(서브에이전트 위임 지침이 있으면 그 문서)

`$SKILL_DIR`는 이 스킬의 디렉터리(`SKILL.md`가 있는 곳)다. 스크립트는 저장소 루트에서 `$SKILL_DIR/scripts/<이름>.sh`로 실행한다. 실행 상태는 `build/orchestration/`(`HERDR_STATE_DIR`로 변경)에 남는다.

**사용자가 위임·오케스트레이션을 명시적으로 지시했을 때만 쓴다.** 지시가 없으면 이 워크플로를 시작하거나 에이전트 pane을 만들지 않고, 메인이 직접 작업한다. 한 번 지시받았다고 이후 작업에 자동으로 확장하지 않는다.

## 1. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| main | 로드맵 확인, task 분해, 지시서 작성, 위임, diff 검토, AC 재검증, task별 커밋, 로드맵 체크, 사용자 보고 | 구현을 직접 하지 않는다 |
| impl | 지시서대로 구현하고 AC를 실행해 보고서를 쓴다 | 커밋, 로드맵 체크, 지시서 밖 수정 |
| review | 읽기 전용으로 diff와 인접 코드를 리뷰하고 결과 파일을 쓴다 | 코드 수정, 커밋, 빌드·테스트 실행(impl 작업 중) |

### 에이전트 종류

- **impl과 review는 항상 서로 다른 종류**다. 다른 모델이 교차 검토하게 하려는 것이다. 다만 종류가 다르다고 리뷰가 독립적이거나 정확하다는 보장은 없다. 품질은 리뷰 범위, 완료 판정, 검증 증거, 수정 반복 규칙이 좌우한다.
- impl의 기본 종류는 **메인 세션과 같은 종류**이고, review는 claude↔codex 중 반대쪽이다.

| 메인 | impl | review |
|---|---|---|
| claude | claude | codex |
| codex | codex | claude |

종류는 `--impl-kind`·`--review-kind`로 바꿀 수 있으나 같은 값은 거부된다. 메인 종류를 감지하지 못하면 `--impl-kind`가 필요하다.

서브 세션의 모델과 추론 강도 기본값은 다음과 같다(`lib.sh`의 `agent_args`).

| 종류 | 모델 | 추론 강도 |
|---|---|---|
| claude | `sonnet` | `--effort medium` |
| codex | `gpt-6.2-sol` | `model_reasoning_effort=medium` |

- 모델은 `herdr-up.sh --impl-model M`·`--review-model M`으로 지정한다. 모델만 바꾸고 추론 강도 등 나머지 기본 인자는 유지한다. 지정값은 `panes.json`에 기록되어 task별 새 세션 재시작에도 적용된다. 이미 살아 있는 에이전트를 재사용할 때는 다음 재시작부터 적용되며, 다시 지정하지 않으면 이전 기록을 유지한다. 인자 전체를 바꾸려면 `--impl-args`·`--review-args`를 쓴다(재시작 후에는 적용되지 않는다).
- 설계 판단이 많은 task(모듈 경계 재구성, 메시징·멱등성, 동시성)만 `herdr-delegate.sh --effort high`로 올린다. 프로젝트의 서브에이전트 위임 지침에 모델·추론 강도 기준이 있으면 그 기준을 따른다.
- 추론 강도는 task 첫 위임에서 세션을 다시 시작할 때 적용된다(4절). 같은 task의 수정·재리뷰는 그 세션을 이어 쓴다.

## 2. 실행 범위

기본값은 **`single-task`·`auto-commit`**이다. 이 워크플로로 구현하라는 지시는 task별 로컬 커밋 요청으로 본다. 커밋은 **main 세션만** 하고, impl·review는 커밋하지 않는다. 푸시는 하지 않는다.

| 사용자 지시 | 허용 동작 |
|---|---|
| "이 작업을 리뷰해 줘" | 리뷰만 |
| "이 작업을 herdr로 구현해 줘" | 구현·리뷰·재검증과 그 task의 커밋 |
| "이 작업을 herdr로 구현하되 커밋하지 마" | 구현·리뷰·재검증까지(`no-commit`) |
| "로드맵의 X 항목을 끝까지 진행해 줘" | 해당 범위 안의 연속 task 실행과 task별 커밋 |

- 시작할 때 main이 해석한 범위(단일/다중, 커밋 제외 task)를 사용자에게 한 줄로 알린다.
- `multi-task`는 지시에 범위가 명시된 경우만 켠다. 그 범위를 넘는 task는 시작하지 않는다.
- `no-commit` task가 있으면 그 task의 구현·리뷰·최종 검증까지 마치고 멈춘다. 다음 task의 Git 가드(4절)가 직전 task의 커밋을 요구하기 때문이다.
- 프로젝트 지침이 "커밋은 사용자가 요청할 때만"이라면, 이 워크플로가 추가하는 예외는 이 절의 위임 지시뿐이며, 프로젝트 지침의 다른 예외는 그대로 따른다.

### 공용 실행 프롬프트

Claude Code 또는 Codex 메인에 아래 입력을 채워 전달한다.

```text
delegate 스킬의 워크플로에 따라 아래 범위를 herdr로 위임해 완료해 줘.

- 리뷰 파일 경로: <저장소 기준 경로>
- 작업 항목과 실행 순서: <task별 항목을 순서대로, 각 task의 완료 기준 포함>
- 설계 합의가 필요한 항목: <항목과 합의 필요 사항 또는 없음>
- 커밋 제외 task: <task 목록 또는 없음>
- 추론 강도 high task: <task 목록 또는 없음>

설계 합의가 필요한 항목은 합의한 뒤 시작해. 구현자와 리뷰어는 서로 다른 종류로 실행해.
각 task의 리뷰와 최종 검증을 마치고, 커밋 제외가 아닌 task는 로컬 커밋 후 다음 작업으로 넘어가.
검사 결과와 해당 로그 경로를 남기고, 리뷰 차단이나 필수 검사·커밋 훅 실패는 해당 task에서 해결해.
```

예: 리뷰 결과 `#1~#7`을 처리할 때, 독립 항목은 순서대로 각각 검증·커밋하고, 설계 합의가 필요한 항목들은 합의한 뒤 하나의 task로 묶어 진행한다.

## 3. 준비

```bash
test "${HERDR_ENV:-}" = 1                  # herdr 밖이면 중단하고 사용자에게 알린다
git status --porcelain=v1 -uall            # 비어 있어야 자동 진행한다 (아래)
$SKILL_DIR/scripts/herdr-up.sh          # 현재 탭 오른쪽에 impl, 그 아래에 review pane 생성 (멱등)
herdr agent list                           # impl·review가 idle인지 확인
```

- 현재 탭·현재 디렉터리의 형제 pane만 만든다. workspace·tab·worktree는 만들지 않는다.
- 이미 살아 있는 `impl`·`review`가 있으면 재사용한다. 종류가 규칙과 어긋나면 오류로 멈추며 임의로 닫지 않는다.
- 만든 pane은 `build/orchestration/panes.json`에 기록되고 `herdr-down.sh`는 그 pane만 닫는다.
- 가드를 쓰는 실행은 깨끗한 작업 트리에서 시작한다. `build/`처럼 Git에서 제외한 생성물은 상태 검사에 포함되지 않는다. 사용자가 기존 변경을 둔 채 독립 위임을 진행하라고 하면 위치 인자 호출을 사용하고, 시작 변경 목록을 기록해 해당 경로를 위임 범위에서 제외한다.
- 실행마다 `build/orchestration/<run-id>`를 만들고 그 바로 아래에 task 디렉터리를 둔다. 한 실행은 한 메인이 순차로 진행한다. 모든 구현·리뷰·수정 위임에 같은 실행 디렉터리의 `--task`를 사용한다.
- `herdr-context.sh self`로 main의 사용률이 읽히는지 확인한다. Codex에서 `HERDR_PANE_ID`가 비어 있으면 4절의 pane ID 지정 예시로 조회한다. 그래도 `unknown`이면 4절 압축 절차를 task마다 수행한다.
- 프로젝트 지침이 가리키는 리뷰 기준 문서가 있고 읽히는지 확인한다. 없으면 5절 리뷰 기준만 쓴다.

| 스크립트 | 용도 |
|---|---|
| `herdr-up.sh [--impl-kind K] [--review-kind K] [--impl-model M] [--review-model M] [--impl-name N] [--review-name N] [--impl-args "…"] [--review-args "…"]` | pane 생성과 에이전트 시작. args를 생략하면 1절 기본값 |
| `herdr-delegate.sh [--task <task-dir>] [--effort medium\|high] [--ignore-limit] <agent> <brief.md> [<report.md>]` | 경로를 담은 짧은 프롬프트 전송. `--task`는 실행의 Git 상태를 확인하고, task에서 처음 위임받는 에이전트를 새 세션으로 다시 시작한다. 위치 인자만 주면 독립 위임으로 동작하고 재시작하지 않는다. main이나 대상의 5시간 한도가 기준 이상이면 보내지 않고 종료 코드 7로 끝난다 |
| `herdr-wait.sh <agent> [--timeout ms]` | 실행 종료 대기 (백그라운드 실행) |
| `herdr-context.sh <agent\|pane\|self> [--max pct]` | 상태줄에서 컨텍스트 사용률 읽기. 읽지 못하면 종료 코드 5, `--max` 이상이면 6 |
| `herdr-limit.sh [--max pct] [<agent\|pane\|self>...]` | 상태줄에서 5시간 사용 한도 읽기(기본 `self impl review`, 기준 85%). 모두 읽지 못하면 5, 하나라도 기준 이상이면 6 |
| `herdr-relay.sh --resume <progress.md> [--mode compact\|clear] [--max pct] [--log file]` | main 자가 압축. 백그라운드로 실행하고 턴을 끝내면 idle 후 `/compact`와 재개 프롬프트를 보낸다 |
| `herdr-down.sh` | 내가 만든 pane 정리 |

## 4. task 루프

### task 분해

- 서브 세션 하나가 압축 없이 끝낼 수 있는 크기로 나눈다. 프로젝트의 서브에이전트 위임 지침에 task 분할 기준이 있으면 따른다.
- task 하나는 가능한 한 **모듈 하나**만 수정한다. 모듈 단위는 프로젝트 지침이 정한다. 계약 변경처럼 여러 모듈을 함께 바꿔야 빌드가 성립하는 경우만 예외로 하고, 지시서의 변경 허용 범위에 이유를 적는다.
- 각 task는 그 자체로 빌드·테스트가 통과하는 커밋 하나가 되어야 한다. 앞 task가 끝난 과도기 상태도 이 조건을 지킨다.

### 실행 순서

1. 다음 task를 정하고(로드맵 항목이면 다음 미완료 항목) 지시서를 쓴다(5절). `task_dir=build/orchestration/<run-id>/<task-id>`로 두고, 그 안의 `base.txt`에 기준 `HEAD`, 시작 시 `git status --porcelain=v1 -uall` 출력, 허용 경로 목록을 기록한다.
2. main의 컨텍스트 사용률을 확인하고 아래 「컨텍스트와 토큰」 절차를 적용한 뒤 `$SKILL_DIR/scripts/herdr-delegate.sh --task "$task_dir" impl "$task_dir/brief.md"`로 구현을 맡긴다. 어려운 task(설계 판단·동시성·데이터 이전)만 `--effort high`를 붙이고, 복사·배선·문서처럼 기계적인 task는 기본 `medium`으로 둔다. 위임이 종료 코드 7로 끝나면 「5시간 한도」 절차로 중단한다. task의 첫 위임이면 impl이 새 세션으로 다시 시작된다.
3. `herdr-wait.sh impl`을 메인 클라이언트의 백그라운드 명령으로 실행하고, 결과가 도착하면 이어간다. 완료 판정은 6절을 따른다. 구현이 끝나면 `herdr-context.sh impl`로 컨텍스트를 점검한다(4절 「컨텍스트와 토큰」).
4. 변경 범위가 지시서 안인지 확인한다. `git diff`는 신규 파일과 staged 변경을 놓치므로 다음을 함께 본다. 범위 밖이면 impl에 되돌리도록 지시한다.
   ```bash
   git status --porcelain=v1 -uall
   git diff HEAD --stat
   git ls-files --others --exclude-standard
   ```
5. 리뷰 지시서를 쓰고 `$SKILL_DIR/scripts/herdr-delegate.sh --task "$task_dir" review "$task_dir/review-brief.md"`로 맡긴다. `herdr-wait.sh review`를 백그라운드로 실행하고, 리뷰가 끝나면 컨텍스트를 점검한다.
6. `review.md`는 통째로 읽지 않는다. 마지막 줄(`차단 있음|차단 없음`)을 먼저 확인하고, 차단이 있으면 5절 형식에 따라 `sed -n '/## 차단 사항/,/## 비차단/p'`로 차단 절만 보며, 수정 지시서에 필요한 항목만 해당 절을 더 읽는다. 차단 항목이 있으면 수정 지시서(`fix-N/brief.md`)를 만들어 2번으로 돌아간다. `--task`에는 계속 원래 `task_dir`를 전달한다. 수정이 끝나면 컨텍스트를 점검하고 다시 리뷰한다.
   - **초기 구현 1회 + 후속 수정 최대 2회**다. 후속 수정에는 리뷰 차단 사항과 main 재검증 실패가 모두 포함된다.
   - 2회를 넘으면 자동으로 더 시도하지 않고 남은 문제를 사용자에게 보고한다.
7. 리뷰 차단이 해소되면 main이 검증할 변경을 확정한다. 완료 기준을 충족한 로드맵 항목은 해당 체크박스를 갱신하고 그 변경도 검토한다. 커밋 제외 task가 아니면 리뷰를 마친 경로만 명시해 스테이징한다. `git diff --cached`로 기준 `HEAD` 대비 변경이 리뷰에서 확인한 내용과 일치하는지 확인하고 `git write-tree`로 인덱스 트리 ID를 기록한다. `git diff --quiet --ignore-submodules=none`이 통과하고 `git ls-files --others --exclude-standard` 출력이 비어 있어야 검증을 시작한다.
8. main은 리뷰된 변경에서 7절의 최종 AC를 순차 실행한다. impl의 관련 회귀 검사 결과는 보고서에서 확인한다. Docker 미기동·포트 충돌·Testcontainers 실패 같은 환경 문제는 수정 횟수에 세지 않는다. 검사가 끝날 때마다 결과와 로그를 보관한다(7절). 최종 AC의 성공·실패가 결정되면 커밋이나 수정 위임 전에 main의 컨텍스트를 점검한다. 필수 검사 실패나 리뷰 차단이 남아 있는 동안에는 해당 task에 머문다.
9. 최종 AC 통과 후 커밋 제외 task가 아니면 `HEAD`가 시작값인지, `git write-tree` 값이 검증 전과 같은지, unstaged·untracked 변경이 없는지 다시 확인한다. 내용이 바뀌면 영향을 받는 리뷰와 검증을 다시 진행한다. 커밋 훅이 통과한 뒤 커밋의 트리(`git rev-parse 'HEAD^{tree}'`)가 검증한 트리와 같은지, 작업 트리가 깨끗한지 확인한다. 훅이 실패하거나 검증과 커밋 내용이 다르면 해당 task에서 멈춘다. 커밋 메시지는 프로젝트 지침의 커밋 메시지 형식을 따르고 scope는 그 task의 모듈이다. 커밋 제외 task는 검증 결과와 미커밋 상태를 보고한다.
10. task를 마무리하면 사용자의 최신 지시에서 마지막으로 허용한 task를 확인한다. 마지막 task이거나 커밋 제외 task이면 결과를 보고하고 종료한다. 허용된 다음 task가 있으면 단계의 완료 기준, main의 컨텍스트 사용률, `herdr-limit.sh`의 5시간 한도를 확인한 뒤 1번으로 돌아간다. 릴레이로 재개한 뒤에도 커밋마다 같은 점검을 이어 간다.

### 위임 전 Git 검사

`--task`는 `task_dir`의 부모에 있는 `active-task.json`에 현재 task 경로, 시작 `HEAD`, 이 task에서 새 세션으로 시작한 에이전트 목록(`agents`)을 기록한다. 첫 task는 staged·unstaged·untracked 변경이 모두 없을 때 시작한다. 같은 task의 구현·리뷰·수정은 작업 트리에 변경이 있어도 `HEAD`가 시작값과 같으면 허용한다. 다음 task는 현재 `HEAD`의 유일한 부모가 직전 task의 시작 `HEAD`이고 작업 트리가 깨끗할 때 허용한다. 차단되면 해당 사유를 출력하고 보고서를 지우거나 프롬프트를 보내기 전에 종료한다.

### task별 새 세션

impl·review는 **task마다 새 세션**으로 시작한다. 이전 task의 탐색·실패 로그가 다음 task의 문맥으로 쌓이지 않게 하려는 것이다.

- `herdr-delegate.sh --task`가 task에서 처음 위임받는 에이전트를 같은 pane에서 `/exit`로 끝내고 1절 기본 인자(와 `--effort`)로 다시 시작한다. 같은 task의 수정·재리뷰는 기존 세션을 이어 쓴다.
- `herdr-up.sh --impl-args`·`--review-args`로 준 인자는 재시작 후에는 적용되지 않는다. 재시작은 항상 1절 기본 인자를 쓴다.
- 재시작한 에이전트가 시작 중 `blocked`(폴더 신뢰, 업데이트 안내 등)이면 위임은 프롬프트를 보내지 않고 실패한다. 화면을 확인하고 8절처럼 처리한 뒤 같은 명령을 다시 실행한다. `agents`에 기록되기 전이므로 다시 실행해도 재시작을 한 번 더 시도한다.
- main 세션은 이 규칙의 대상이 아니다. 아래 컨텍스트 규칙을 따른다.

### 컨텍스트와 토큰

Claude Code·Codex 모두 모델이 `/context`·`/status`를 직접 실행하거나 그 결과를 읽을 수 없다. 대신 herdr가 pane의 상태줄을 읽을 수 있으므로 **main도 자기 pane을 포함해 `herdr-context.sh`로 사용률을 확인**한다.

```bash
$SKILL_DIR/scripts/herdr-context.sh self --max 25      # main. 25% 이상이면 종료 코드 6
$SKILL_DIR/scripts/herdr-context.sh impl               # 서브 세션
```

`self`는 `HERDR_PANE_ID`를 사용한다. Codex의 명령 실행 환경에 이 변수가 없으면 `herdr agent list`에서 현재 main Codex의 `pane_id`를 확인한 뒤 명령에 직접 전달한다. 여러 후보가 있으면 작업 디렉터리와 상태를 확인한다. 이 환경에서 `herdr pane current --current`는 다른 pane을 반환할 수 있다.

```bash
herdr agent list
# w7:p1은 예시다. 확인한 main Codex의 pane_id로 바꾼다.
HERDR_PANE_ID=w7:p1 $SKILL_DIR/scripts/herdr-context.sh self --max 25
```

- 릴레이도 `HERDR_PANE_ID`를 사용한다. 변수가 비어 있으면 릴레이 실행 명령 앞에도 확인한 ID를 같은 방식으로 전달한다.
- 종료 코드 5(`unknown`)는 상태줄에서 사용률을 읽지 못했다는 뜻이다. impl·review(자기 pane이 아닌 대상)는 상태줄에 없으면 idle인 pane에 Claude는 `/context`, Codex는 `/status`를 입력해 출력에서 읽는다(대화에 출력이 남는다). main 자신은 턴 중에 입력할 수 없어 이 fallback이 없고, 릴레이가 idle을 확인한 뒤에만 같은 방식으로 `before`·`after-*` 사용률을 기록한다. 그래도 읽지 못하면 성공으로 보지 않고, 아래 압축 절차를 task마다 수행한다.
- main은 구현 위임 직전, 최종 재검증 직후, 다음 task를 준비하기 전에 확인한다. 구현·리뷰·수정이 끝날 때는 해당 서브 세션도 확인한다.
- 20%부터 해당 task의 `progress.md`에 현재 task와 마지막으로 허용된 task, 결정, 검증 결과와 로그 경로, 커밋 여부(완료 시 해시), 다음 행동을 기록하거나 갱신한다.
- 서브 세션은 task마다 새 세션이므로 별도 조치가 없다. task 도중 25% 이상이면 수정 위임 전에 해당 에이전트를 새 세션으로 시작한다(`herdr-delegate.sh --task`가 task 첫 위임에서만 재시작하므로, 필요하면 `restart_agent`를 사용한다).

#### main 자가 압축(릴레이)

main은 여러 task를 한 턴에서 이어 가므로 턴 종료 후 자동 압축이 걸리지 않아 컨텍스트가 누적된다. 또 main은 자기 턴 안에서 `/compact`·`/clear`를 실행할 수 없다. 그래서 **턴을 일부러 끝내고 외부 프로세스가 idle이 된 main pane에 명령을 넣는다.**

1. 25% 이상이거나 `unknown`이면, 진행 중인 명령이 끝나고 task가 마무리된 시점(커밋 직후 또는 다음 task 시작 전)에 `progress.md`를 갱신한다. 같은 task에 남은 작업이 있으면 그 작업을 위임하기 전에 한다.
2. `herdr-relay.sh --resume "$task_dir/progress.md" --log build/orchestration/<run-id>/context.log`를 **백그라운드로 실행**하고 즉시 턴을 끝낸다. 추가 작업이나 긴 설명을 덧붙이지 않는다.
3. 스크립트가 main이 idle이 되면 `/compact`를 보내고, 압축 후에도 25% 이상이면 `/clear`를 보낸 뒤, `progress.md`를 읽고 이어 가라는 프롬프트를 보낸다. main이 `blocked`이면 보내지 않고 종료한다.
4. 재개한 main은 `progress.md`의 다음 행동부터 진행한다. 릴레이가 실행되는 동안 사용자가 main 입력창에 입력하면 간섭할 수 있으므로 보고 문구에 알린다.

- 사용률 기록은 릴레이의 `context.log`(단계별 사용률)에 남는다. 클라이언트가 상태줄에 입력·출력 토큰을 표시하면 함께 기록한다.
- 클라이언트의 자동 압축 설정은 바꾸지 않는다. 자동 압축은 안전망일 뿐 위 점검을 대신하지 않는다.

#### main의 읽기 범위

main 컨텍스트는 task를 거치며 누적되므로 탐색은 impl에 맡긴다.

- 지침·계획 문서는 처음 한 번 필요한 절만 `rg -n`과 `sed -n`으로 읽는다. 같은 문서를 task마다 다시 읽지 않는다.
- 지시서를 쓰려고 코드를 직접 읽지 않는다. `rg -l`·`wc -l` 수준으로 위치만 확인하고, 지시서에는 목표·변경 허용 범위·AC와 "확인할 경로"를 적는다. 사용처 조사, diff 검토는 impl·review의 일이다.
- 보고서·리뷰는 마지막 줄과 판단에 필요한 절만 읽고, 이미 읽은 파일은 바뀌지 않았으면 다시 읽지 않는다.

### 5시간 한도

Claude·Codex 모두 5시간 사용 한도가 있고, 중간에 한도에 걸리면 task가 반쯤 끝난 채 멈춘다. 그래서 **85%에서 새 위임을 멈추고 인계한다.** 기준은 `HERDR_LIMIT_MAX`로 바꿀 수 있다.

```bash
$SKILL_DIR/scripts/herdr-limit.sh                 # self impl review. 85% 이상이면 종료 코드 6
```

- `herdr-delegate.sh`가 위임 직전에 main(self)과 대상의 한도를 확인하고, 기준 이상이면 보내지 않고 종료 코드 7로 끝난다. 사용자가 계속하라고 지시한 경우에만 `--ignore-limit`을 쓴다.
- main은 커밋 직후와 다음 task 시작 전에도 `herdr-limit.sh`를 실행한다.
- 종료 코드 6·7이면 새 위임을 하지 않는다. 진행 중인 impl·review는 끝날 때까지 기다리고(중간에 끊으면 결과를 잃는다) 결과를 `progress.md`의 다음 행동에 반영한다. 그런 다음 handoff 스킬 절차로 `.handoff/`에 인계 문서를 쓰고, 한도와 재개 방법을 보고한 뒤 턴을 끝낸다. 릴레이는 실행하지 않는다.
- 상태줄에서 읽지 못한 대상은 `unknown`으로 출력한다. Claude는 재시작 뒤 첫 응답 전까지 한도가 표시되지 않으며, 같은 계정의 Claude pane끼리 한도를 공유하므로 다른 Claude pane 값으로 판단한다. 모두 `unknown`(종료 코드 5)이면 task마다 다시 확인하고 보고에 적는다.

## 5. 지시서 템플릿

경로는 `<task-dir>/brief.md`다. 본문은 파일에 두고 위임 메시지에는 지시서 경로를 전달한다. 지시서에 `herdr-delegate.sh`가 지울 보고서 경로를 적는다. 기본값은 지시서와 같은 디렉터리의 `report.md`이며, 에이전트 이름이 `review`이면 `review.md`다. 다른 경로를 쓰면 호출의 보고서 인자에도 같은 경로를 준다. 결과 채팅은 판정과 로그 경로만 전달한다. 프로젝트에 서브에이전트 위임 지침이 있으면 지시서 작성 원칙은 그 문서를 따른다.

```markdown
# <task-id> <제목>

## 목표
## 기준 커밋
- `<시작 HEAD>`
## 추론 강도
- `medium` 또는 `high`(위임 시 `--effort`와 같게)
## 읽을 문서
- `<프로젝트 지침 문서> § <관련 절>`, `<설계 문서> § <관련 절>`
## 변경 허용 범위
- 모듈 하나와 그 안의 파일(여러 모듈이면 이유)
## 금지
- 커밋 금지, 범위 밖 수정 금지, `@Suppress`·baseline·테스트 삭제/비활성화 금지
## AC
- 관련 회귀 검사의 명령과 기대 결과 (저장소 테스트 규칙에 맞춰 실행)
## 보고
- 보고 파일은 `<task-dir>/report.md`다.
- 형식: 첫 줄 `# <task-id> 보고`, 마지막 줄 `결과: 완료` 또는 `결과: 실패`
- 포함: 변경 요약, 실행한 검사와 결과(실패는 그대로), 미해결 사항
```

### 리뷰 지시서

목표, 기준 커밋, 대상 diff 범위(기준 커밋 대비 변경과 신규 파일), 프로젝트 리뷰 기준 문서의 관련 절, 확인할 검증 명령과 아래 출력 형식(그대로)을 적고 읽기 전용으로 지시한다. 호출자와의 계약, 이벤트 소비자, 기존 테스트와의 충돌을 확인할 때 인접 코드와 ADR을 참고한다. 결과는 `review.md`다.

리뷰 기준:

1. 지시서의 목표와 AC를 만족하는가
2. 변경 범위를 벗어나지 않았는가
3. 설계·ADR·모듈 경계를 지키는가
4. 동시성·트랜잭션·재시도·실패 흐름이 안전한가
5. 테스트가 실제 위험을 검증하는가

특히 프로젝트 지침이 정한 불변 조건(설계 규칙, 데이터 무결성 제약, 멱등성 등)을 확인하게 한다.

출력 형식:

```markdown
# Review

## 판정
## 차단 사항
### R-001 [P0] 제목
- 파일 / 발생 조건 / 근거 / 실제 영향 / 수정 방향 / 관련 AC
## 비차단 사항
- …
(마지막 줄) 차단 있음 | 차단 없음
```

- 이 형식은 위임 리뷰 결과 파일의 기계 판독 계약이다. 프로젝트 리뷰 지침의 결과 형식보다 우선하므로 리뷰 지시서에 반드시 적는다.
- 판정 기준과 심각도 정의는 프로젝트 리뷰 지침을 따른다. 프로젝트 지침의 차단 등급은 `차단 사항`에, 그 밖의 등급(주의·제안 등)은 `비차단 사항`에 적는다.

- P0: 정합성·보안·데이터 손실 위험. P1: AC 위반이나 중대한 기능 결함. P2: 개선 제안(차단 아님).
- **차단 결론에는 구체적인 발생 조건과 코드 근거가 필수**다. 추측이나 취향만으로 수정 루프를 돌리지 않는다.

## 6. 대기와 완료 판정

완료는 두 단계로 판정한다. 에이전트가 idle이 됐다고 지시받은 작업이 정상 완료된 것은 아니다(테스트 실패 후 보고서 없이 멈췄을 수 있다).

| 단계 | 확인할 증거 |
|---|---|
| 실행 종료 | 상태 변화 이후 `idle`·`done` (`herdr-wait.sh` 종료 코드 0) |
| 작업 완료 | 이번 위임의 보고 파일이 존재하고(delegate가 이전 파일을 지우므로 존재하면 이번 실행 것), 첫 줄의 task-id가 맞고, 마지막 줄 결과가 있고, main이 실제 diff를 확인 |

보고서가 없거나 형식이 틀리면 성공으로 보지 않고 `herdr agent read`로 상태를 확인한 뒤 판단한다. 보고서는 참고 증거일 뿐이고 테스트 통과는 main이 직접 검증한다.

| 상태 | 의미 |
|---|---|
| `idle`·`done` | 입력 가능. 단 위 조건을 만족해야 완료로 본다 |
| `working` | 작업 중 |
| `blocked` | 승인·질문 UI 대기 |
| `unknown` | 완료의 증거가 아니다 |

`herdr-wait.sh`는 다음을 지킨다.

- `--until`을 주지 않아 idle·done·blocked를 모두 매칭한다. `--until idle`만 쓰면 `done`을 놓쳐 영원히 기다린다.
- 위임 직후에는 아직 idle일 수 있으므로, `herdr-delegate.sh`가 남긴 기준 `state_change_seq` 이후에 상태가 바뀐 뒤의 idle·done만 완료로 본다.
- idle이어도 화면에 `shell still running`·`monitors still running`이 보이면(작업자가 장시간 작업을 백그라운드 셸로 돌리는 중) 끝난 것이 아니므로 다시 기다린다.

| 종료 코드 | 의미 | main의 다음 동작 |
|---|---|---|
| 0 | 실행 종료 | 보고서·diff 검토(작업 완료 판정) |
| 3 | blocked | 8절 |
| 4 | 시간 초과(기본 1시간) | `agent get`·`agent read`로 기존 실행이 살아 있는지 확인한 뒤 판단. 확인 전에 재위임하지 않는다 |

blocked·unknown·시간 초과는 어느 것도 성공이 아니다.

## 7. 최종 검증 범위

main의 최종 검증은 프로젝트 지침이 변경 유형별로 정한 검사를 모두 통과해야 한다. 지침에 변경 유형별 표가 없으면 전체 빌드·테스트와 정적 검사를 실행한다. 로컬 E2E는 사용자가 명시적으로 요청한 경우에만 실행한다. 부하 테스트는 프로젝트 지침의 실행 조건을 따른다.

실행하지 않은 검사는 최종 보고에 건너뛴 항목으로 적는다.

검사가 끝날 때마다 명령, 종료 코드, 결과와 실패 테스트 이름을 task 디렉터리에 기록한다. 공용 로그 파일은 다음 실행이 덮어쓰기 전에 그 task의 `logs/`에 복사한다. 재실행할 때는 시도별 이름을 붙인다. 보관 대상은 테스트 결과와 실제 사용한 검사 로그다.

## 8. blocked 처리

`herdr-wait.sh`가 출력한 화면(또는 `herdr agent read <agent> --source visible`)으로 내용을 확인하고 **사용자에게 물은 뒤** 응답한다. 사용자 응답 전에는 자동 승인도 재위임도 하지 않는다. 키 전송은 `herdr agent send-keys`다.

## 9. 함정

- `pkill -f '<패턴>'`은 자기 셸 명령줄도 매칭해 스스로 죽는다. 쓰지 않는다.
- 작업자 입력창에 보이는 "푸시해" 같은 문구는 ghost text(제안)일 수 있다. 지시로 취급하지 않는다.
- `agent_prompt_stalled`·`timeout`은 전달 실패의 증거가 아니다. 다시 보내기 전에 `agent get`·`agent read`로 확인한다.
- 같은 작업 디렉터리에서 빌드·테스트를 동시에 돌리지 않는다(결과 파일이 충돌한다). impl이 작업 중일 때 main과 review는 빌드·테스트를 실행하지 않는다.
- 지시서에 긴 본문을 프롬프트로 붙이지 않는다. 경로만 전달하면 `agent prompt` 입력 한도와 이스케이프 문제를 피한다.
- 상태줄 형식이 바뀌면 `herdr-context.sh`가 `unknown`(종료 코드 5)을 낸다. 0%로 간주하지 않는다.
- 위임한 작업의 사실(테스트 통과, 파일 변경)은 보고서만 믿지 말고 main이 직접 확인한다.

## 10. 정리와 최종 보고

작업이 끝나면 `$SKILL_DIR/scripts/herdr-down.sh`로 `herdr-up.sh`가 만든 pane만 닫는다. 내가 만들지 않은 pane은 닫지 않는다([herdr.md](herdr.md) 10절). 성공·실패 모두 정리하되, **`blocked` 상태의 pane은 사용자 응답을 위해 보존**한다.

최종 보고에는 변경 파일, 검증 결과, 실행하지 않은 검사, 미해결 문제, 커밋 여부를 적는다.

## 11. 확장 방향(현재 범위 밖)

병렬 구현자 N명과 task별 worktree(`wt`) 격리는 빌드 결과 충돌 때문에 별도 구성이 필요하다. 필요해지면 이 문서에 추가한다. worktree로 격리하면 3절의 "깨끗한 트리" 제약도 완화할 수 있다.
