# 검증 스킬 만들기

진지한 프로젝트에는 실제 앱을 구동해 동작을 증명하는 스크립트화된 방법이 필요하다. 앱을 띄우고, 기능을 사용자처럼 실행하고, 증거를 남기는 것이다. 이 스킬은 그 방법을 이 저장소에 맞춘 프로젝트 전용 스킬(`.agents/skills/verify-<앱>/`)로 생성한다. 생성물은 사람이 아니라 **앱을 처음 보는 다음 에이전트**가 작업 도중에 읽는다. 그 독자를 기준으로 쓴다.

출처: [cursor/plugins의 pstack `create-verification-skill`](https://github.com/cursor/plugins/tree/main/pstack/skills/create-verification-skill)(commit `b7b93c3`)을 이 저장소에 맞게 고쳤다. 이 스킬 디렉터리를 `SKILL_DIR`이라 부른다.

## 1. 사용자가 아니라 저장소에 묻는다

관찰할 수 없는 것만 사용자에게 묻고, 나머지는 코드와 문서로 답한다.

- **표면**: 사용자가 실제로 만지는 것은 무엇인가. 웹 UI, CLI, API, 라이브러리 가운데 주된 것을 고르고 나머지는 적어 둔다. 이 저장소는 web 화면(BFF 포함), Gateway(18000)를 거치는 API, SSE 대기열이 있다.
- **실행**: 로컬에서 어떻게 시작하는가. 저장소의 문서화된 명령을 우선한다([AGENTS.md 5절](../../../AGENTS.md#5-명령)의 `docker compose`, `scripts/dev/run.sh`, `./gradlew :<모듈>:bootRun`, `cd web && pnpm dev`, `scripts/dev/seed-demo.sh`). 포트, 환경 변수, 시드 데이터, 인증을 적는다.
- **구동**: 에이전트가 프로그램으로 조작할 방법은 무엇인가. **기존 하네스를 먼저 쓴다.** 예: `web`의 Playwright E2E와 캡처, `scripts/e2e/run.sh`(전체 스택 E2E), `curl`로 부를 수 있는 Gateway 엔드포인트. 그다음에야 일반 방식(웹은 브라우저, CLI는 PTY, 서비스는 HTTP)을 고른다.
- **관찰**: 어떤 증거를 남길 수 있는가. 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태.
- **격리**: 인스턴스 둘이 나란히 돌 수 있는가(포트, 데이터 디렉터리). 안 되면 생성물에 그렇게 적는다. 공유 인스턴스를 같이 구동해 사용자의 세션을 망가뜨리는 것보다 거부하는 편이 낫다. 같은 작업 디렉터리에서 Gradle 실행을 동시에 돌리지 않는다는 [AGENTS.md 6절](../../../AGENTS.md#6-테스트와-검사)의 제약도 여기에 속한다.

체크아웃이 그대로는 빌드·시작되지 않으면, 생성 전에 먼저 고치거나(또는 정확히 보고) 한다. 깨진 기반 위에서 쓴 스킬은 틀린 절차를 가르친다. 시작을 막는 무관한 누락 자산(앱이 서비스하지 않는 정적 디렉터리, 샘플 설정)은 생성물이 만들어도 된다. 단 검증용 임시 설치물임을 표시하고 정리 단계에서 지운다.

## 2. 스킬 생성

`.agents/skills/verify-<앱>/SKILL.md`를 쓴다. YAML frontmatter(`name: verify-<앱>`과 앱·표면·언제 쓰는지를 담은 `description`)가 없으면 스킬이 등록되지 않는다. 아래 절을 두고, 각 절은 인터뷰에서 실제로 찾은 내용으로 채운다. 빈 자리표시자를 남기지 않는다.

- **Launch**: 검증용으로 앱을 시작하는 정확한 명령과 준비 완료 판정 방법(로그 한 줄, 프롬프트). 빈 데이터 디렉터리에서 마이그레이션과 시드까지 거쳐 사용 가능한 상태에 도달해야 한다. 준비 완료는 프로세스가 응답한다는 뜻이 아니라 사용 가능하다는 뜻이다. DB 헬스체크는 초기화 스크립트가 도는 중에도 통과할 수 있다. 종료 절차를 포함한다. 짧게 사는 CLI는 유지할 서버가 없으므로, 빌드(또는 의존성 설치)를 한 번 하고 구동마다 격리된 세션을 시작한다.
- **Doctor**: "이 인스턴스를 구동할 가치가 있는가"에 답하는 읽기 전용 점검 하나. 프로세스가 떠 있는가, 올바른 버전·빌드인가, 포트를 우리가 쥐고 있는가, 인증이 유효한가. 뭔가 이상하면 에이전트가 가장 먼저 실행한다.
- **Drive**: 예시가 아니라 이 저장소의 실제 선택자·명령으로 쓴 하네스 절차. 좌표나 탭 순서보다 안정적인 핸들(ARIA 레이블, data 속성, 프롬프트 문구, 라우트 경로)을 쓴다.
- **Evidence**: 증명에 무엇을 남기고 어디에 두는가. 증명 기준을 적는다.
  - 내부 setter나 테스트 전용 엔드포인트가 아니라 **실제 사용자 경로**를 실행한다.
  - 마지막 화면만이 아니라 동작과 그 결과 상태를 함께 남긴다.
  - 눈에 보이는 결과와 함께 부수 효과(저장된 파일, 삽입된 행, 발행된 메시지)를 확인한다.
  - mock은 운영 경계가 이미 외부 시스템을 격리하는 곳(이 저장소에서는 `fake-pg`)에만 쓴다.
  - 안전한 경로가 dry-run이나 테스트 모드라면, 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰(파일, 네트워크, git ref)로 확인한다.
  - 증거 경로는 git 제외 위치(`build/` 아래 등)로 정한다. 증거를 커밋하지 않는다.
- **Cleanup**: 이번 실행이 만든 인스턴스를 내리는 방법. 프로세스 이름으로 죽이지 않고 **자기가 시작한 것만** 죽인다. 정리는 인스턴스와 임시 상태를 지우되 증거는 지우지 않는다. 증거는 스킬이 이름 붙인 위치에 남는다.
- **Helpers**: 스킬이 싣는 스크립트는 실행 가능하고 호출 방법이 스킬 본문에 있다. 독자가 역공학해야 하는 도우미는 도우미가 아니다.

## 3. 기능 지도(feature map) 심기

`.agents/skills/verify-<앱>/features/README.md`와, 식별할 수 있는 사용자 기능마다 파일 하나를 만든다(라우트, 명령, 메뉴, 문서에서 상위 3~5개로 시작). 형식은 [references/feature-map-example/](references/feature-map-example/)를 따른다. 각 파일은 사용자 관점에서 기능이 무엇이고, 어떻게 도달하고, 하네스로 어떻게 구동하고, 어떤 관찰 가능한 최종 상태가 동작을 증명하는지에 답한다. H2 네 개는 `Sub-features`, `How to get to it (user POV)`, `Driving it with <하네스>`, `Gotchas`다.

시드 데이터에 어떤 여정의 전제가 없으면 그 여정은 실패로 보고하고, 이유를 해당 기능의 `Gotchas`에 적는다. 통과시키려고 여정을 약하게 만들지 않는다. 지도는 이 저장소가 관리하는 검증의 원천이다. 편한 진입점 하나만 구동한 증명은 지도에 다른 진입점이 있으면 불완전하다.

## 4. 넘기기 전에 생성물을 증명한다

생성한 스킬의 지시를 처음부터 끝까지 한 번 실행한다. 시작, doctor, 지도의 기능 **하나** 구동(하나면 충분하다. 나머지는 이후 실행이 다룬다), 증거 수집, 정리 순이다. 정리 뒤에 증거가 이름 붙인 위치에 남아 있는지 확인한다. 증거를 지워 버리는 정리는 이 단계 실패다. 실패한 부분을 고치고, 실패한 시도 뒤에도 생성된 정리를 실행해 깨진 시도가 프로세스와 포트를 남기지 않게 한다. **한 번도 실행하지 않은 생성물은 초안이지 결과물이 아니다.**

실제 대상 대신 대역(예: 원격 스택 대신 로컬 스택)에서 증명했다면, 대역이 한 설정 중 실제 대상에서는 일어나지 않는 단계를 모두 적는다. 그 단계들은 실제 대상에서 실행하기 전까지 미검증이다.

생성 후 `./scripts/agent/skills/check-skills.sh`를 실행한다.

## 5. 후속

기능 지도는 앱이 바뀌면 낡는다. 정기적으로 지도와 검증 스킬을 앱과 대조해 고치는 절차는 이 스킬에 포함하지 않았다. 필요하면 원본의 [`maintain-verification-skill`](https://github.com/cursor/plugins/tree/main/pstack/skills/maintain-verification-skill)을 참고해 별도 항목으로 정한다.
