`HEAD`와 사용자가 준 기준점 사이의 diff를 두 축으로 리뷰한다.

- **Standards**: 저장소에 문서화된 규칙을 지켰는가
- **Spec**: 원래 요청한 계획·명세를 빠짐없이, 요청한 만큼만 구현했는가

한 축이 다른 축을 가리지 않도록 결과를 합치거나 순위를 매기지 않는다. 규칙은 지키지만 엉뚱한 것을 만들 수도, 명세대로지만 규칙을 어길 수도 있다.

출처: [mattpocock/skills `code-review`](https://github.com/mattpocock/skills/tree/main/skills/engineering/code-review) (commit `6f7f783`)를 이 저장소에 맞게 고쳤다.

## 순서

### 1. 기준점 고정

사용자가 말한 값이 기준점이다(커밋 SHA, 브랜치, 태그, `main`, `HEAD~5` 등). 없으면 묻는다.

- `git rev-parse`로 기준점과 HEAD를 각각 전체 커밋 SHA로 고정하고 `git diff --stat <기준SHA>...<검토SHA>`가 비어 있지 않은지 확인한다. 잘못된 ref나 빈 diff는 여기서 멈춘다.
- diff 범위는 `<기준SHA>...<검토SHA>`(three-dot, merge-base와 비교)로 고정하고 커밋 목록은 `git log <기준SHA>..<검토SHA> --oneline`으로 적어 둔다.
- 커밋되지 않은 변경이 있으면 사용자에게 포함 여부를 묻는다.

### 2. Spec 출처 찾기

다음 순서로 찾는다.

1. 사용자가 인자로 준 경로
2. 커밋 메시지·브랜치 이름이 가리키는 문서: `docs/workflow/plans/`의 계획, `docs/roadmap.md`·`docs/workflow/roadmap.md`·`docs/ui/roadmap.md`의 항목과 완료 기준, `docs/adr/`의 관련 ADR
3. 찾지 못하면 사용자에게 명세 위치를 묻는다. 없다고 하면 Spec 축은 건너뛰고 최종 보고에 "명세 없음"이라고 적는다.

### 3. Standards 출처 찾기

변경 경로에 해당하는 규칙을 모두 모은다.

- 공통: [AGENTS.md](../../../AGENTS.md)의 4절 설계 규칙과 7절 공통 규칙
- 백엔드 변경: [backend-review.md](../../../docs/rules/backend-review.md)(심각도·확인 순서)와 그 안에서 가리키는 작성·테스트 지침
- `web` 변경: [frontend-review.md](../../../docs/rules/frontend-review.md)와 [frontend.md](../../../docs/rules/frontend.md)
- 구조·결정의 근거: `docs/architecture.md`, 관련 ADR

위 문서가 다루지 않는 부분에만 [코드 스멜 기준선](references/smell-baseline.md)을 보조로 적용한다. 문서화된 규칙이 항상 이긴다. 스멜은 확정 위반이 아니라 판단 사항("Feature Envy 가능성")으로만 보고하고, 린터·detekt·ktlint가 이미 잡는 것은 건너뛴다.

### 4. 두 축 실행: 다른 모델에 맡긴다

서브에이전트를 쓰지 않는다. 구현한 모델이 자기 변경을 보면 같은 맹점을 공유하므로, **지금 실행 중인 도구와 다른 모델의 CLI**를 호출해 리뷰시킨다.

| 지금 실행 중인 도구 | 리뷰어 |
| --- | --- |
| Claude Code | `codex` |
| Codex | `claude` |

1. 두 축의 프롬프트를 각각 파일로 쓴다. `mktemp -d`로 만든 저장소 밖 임시 디렉터리에 `standards.md`, `spec.md`를 둔다. 리뷰어는 이 대화를 보지 못하므로 아래 입력을 프롬프트에 모두 넣는다. 비밀 값(`.env` 등)은 넣지 않는다.
2. 저장소 루트에서 축마다 한 번씩 호출한다. 두 호출은 서로 독립이므로 동시에 실행해도 된다.

   ```bash
   SKILL_DIR/scripts/run-reviewer.sh <codex|claude> <프롬프트 파일> <결과 파일> <기준SHA...검토SHA>
   ```

   - 리뷰어는 읽기 전용이다. Codex는 `read-only` 샌드박스에서 Git으로 diff를 읽는다. Claude는 스크립트가 고정 범위에서 만든 diff 파일과 저장소 문맥을 읽기·검색 도구로 확인한다. 호출 방식을 바꾸려면 스크립트를 고친다.
   - 호출이 실패하면(CLI 없음, 인증 만료, 시간 초과) 결과 파일의 `.log`를 확인해 사용자에게 알리고 멈춘다. 같은 모델로 대신 리뷰하는 것은 독립성이 사라지므로 사용자가 동의할 때만 한다. 이때 보고에 "교차 모델이 아님"이라고 적는다.
   - 호출은 축당 1회다. 재호출은 사용자가 승인한 경우에만 한다.
3. 두 축을 합치거나 서로의 결과를 한 프롬프트에 넣지 않는다. 한 축의 결론이 다른 축을 물들이지 않게 한다.

**Standards 입력**: 고정 diff 범위와 커밋 목록, 3단계에서 모은 규칙 파일 경로, 스멜 기준선 본문(`references/smell-baseline.md`).
지시: "위반을 파일·행 단위로 보고한다. (a) 문서화된 규칙 위반은 규칙 문서와 절을 인용하고 `backend-review.md`·`frontend-review.md`의 심각도(차단·주의·제안)를 따른다. (b) 기준선 스멜은 이름과 해당 코드를 적고 판단 사항으로 표시한다. 이번 변경이 건드리지 않은 기존 코드는 지적하지 않는다. 취향 차이는 차단·주의로 올리지 않는다. 400단어 이내."

**Spec 입력**: 고정 diff 범위와 커밋 목록, 명세 경로(또는 본문).
지시: "(a) 명세가 요구했는데 빠졌거나 일부만 구현된 것, (b) 요청하지 않은 동작(범위 확장), (c) 구현된 것처럼 보이지만 틀려 보이는 것을 보고한다. 각 항목에 해당 명세 줄을 인용한다. 400단어 이내."

명세가 없으면 Spec 축은 건너뛴다.

### 5. 취합

두 보고를 `## Standards`, `## Spec` 제목 아래에 원문 그대로 또는 가볍게 다듬어 나란히 싣는다. 합치거나 재정렬하지 않는다.

- 리뷰어 보고의 지적 가운데 판단의 근거가 되는 것(차단·주의)은 해당 파일의 `파일:행`을 직접 열어 사실인지 확인하고, 확인하지 못한 것은 "미확인"으로 표시한다. 리뷰어도 틀릴 수 있다.
- 어느 모델이 리뷰했는지(`codex` 또는 `claude`)를 보고 맨 위에 적는다.
- 끝에 한 줄로 축별 지적 수와 **각 축 안에서** 가장 심각한 문제를 적는다. 축을 가로지르는 1순위를 고르지 않는다.

## 규칙

- 읽기 전용이다. 이 스킬은 코드를 고치지 않는다. 수정은 사용자가 요청하면 별도로 한다.
- 다른 모델 CLI 호출은 저장소 내용을 그 모델 제공사로 보낸다. 사용자가 이 스킬을 호출한 것을 그 범위의 동의로 보되, 범위 밖 파일(저장소 밖 경로, 비밀 값)은 프롬프트에 넣지 않는다.
- 지적에는 `파일:행`과 구체적인 실패 시나리오를 붙인다.
- 테스트·검사 결과를 근거로 삼는다면 [AGENTS.md 6절](../../../AGENTS.md#6-테스트와-검사)의 스크립트로 실행하고, 실패는 실패한 그대로 보고한다. 실행하지 않았으면 그렇게 적는다.
- 라이브러리 버전과 API 관련 지적은 기억이 아니라 공식 문서나 설치된 버전의 문서를 근거로 한다.
