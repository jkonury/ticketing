# 도메인 모델링

설계하는 동안 프로젝트의 도메인 모델을 능동적으로 다듬는다. 용어에 이의를 제기하고, 경계 사례 시나리오를 만들고, 용어와 결정이 굳어지는 순간 바로 문서에 적는 일이다. 용어사전을 어휘 확인용으로 읽기만 하는 것은 이 규율이 아니다. 모델을 바꿀 때 쓴다.

## 파일 구조

- 용어: [docs/glossary.md](../../../../docs/glossary.md) 하나다. 이 저장소는 모듈이 여러 개지만 용어사전을 모듈별로 나누지 않는다. 새 파일(`GLOSSARY.md`, `GLOSSARY-MAP.md`)을 만들지 않는다.
- 결정: [docs/adr/](../../../../docs/adr/README.md)다.
- 필요가 없으면 파일을 건드리지 않는다. 쓸 내용이 생겼을 때만 고친다.

## 세션 중에 하는 일

### 용어사전과 대조해 이의를 제기한다

사용자가 `docs/glossary.md`의 용어와 충돌하는 말을 쓰면 바로 지적한다. 예: "용어사전은 '선점'을 X로 정의하는데 지금은 Y를 말씀하시는 것 같습니다. 어느 쪽인가요?"

### 모호한 말을 정확히 만든다

모호하거나 여러 뜻으로 쓰이는 말이 나오면 정확한 표준 용어를 제안한다. 예: "'결제'가 결제 요청(`PaymentRequested`)인지 결제 승인인지 정해야 합니다."

### 구체적인 시나리오로 시험한다

도메인 관계를 논의할 때는 경계 사례를 건드리는 구체적 시나리오를 만들어 개념 사이의 경계를 정확히 말하게 만든다. 예: "같은 좌석을 두 사용자가 동시에 확정하면 어느 쪽이 실패합니까?"

### 코드와 대조한다

사용자가 동작 방식을 말하면 코드가 그와 일치하는지 확인한다. 모순이 있으면 알린다. 예: "코드는 예매 전체를 취소하는데 부분 취소가 가능하다고 하셨습니다. 어느 쪽이 맞습니까?"

### 용어사전을 바로 갱신한다

용어가 확정되면 그 자리에서 `docs/glossary.md`를 고친다. 모아 두지 않는다.

- 기존 표의 구조와 [표기 원칙](../../../../docs/glossary.md#1-표기-원칙)을 따른다. 새 항목은 어울리는 절의 표에 한 행으로 넣는다.
- 구현 세부사항을 넣지 않는다. 명세, 메모장, 구현 결정의 보관소가 아니다. 용어사전은 용어사전일 뿐이다.
- 프로젝트 고유의 개념만 넣는다. 타임아웃, 오류 타입, 유틸리티 패턴 같은 일반 프로그래밍 개념은 많이 쓰더라도 넣지 않는다.
- 같은 개념에 말이 여럿이면 가장 좋은 하나를 고르고 나머지는 쓰지 않을 말로 적는다.
- 아직 정하지 않은 클래스·테이블·이벤트 이름을 표준 식별자로 만들지 않는다.

### ADR은 아껴서 제안한다

다음 세 가지가 모두 참일 때만 ADR을 제안한다.

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 의미 있다.
2. **맥락 없이는 놀랍다**: 나중에 읽는 사람이 "왜 이렇게 했지?" 하고 궁금해한다.
3. **실제 트레이드오프의 결과다**: 진짜 대안이 있었고 구체적인 이유로 하나를 골랐다.

하나라도 빠지면 쓰지 않는다. 쓰기로 했으면 [ADR 템플릿](../../../../docs/templates/adr.md)의 작성 원칙을 따른다.

- 번호는 `docs/adr/`의 최대 번호 + 1이고, 작성 후 `docs/adr/README.md` 목록에 한 줄을 더한다.
- 상태는 사용자와 합의했을 때만 `합의`이고 그 전에는 `제안`이다.
- 포트·모듈·이벤트·배포 방식이 바뀌면 `docs/architecture.md`를 같은 변경에서 고친다.
- 검토한 대안과 채택하지 않은 이유를 남긴다. 규칙 7개와 겹치는 결정이면 [AGENTS.md 4절](../../../../AGENTS.md#4-반드시-지킬-설계-규칙)을 가리키기만 한다.

ADR로 남길 만한 것: 아키텍처의 모양, 컨텍스트 사이의 연동 방식, 갈아타기 어려운 기술 선택, 경계와 범위 결정(하지 않기로 한 것 포함), 뻔한 길에서 의도적으로 벗어난 것, 코드에서 보이지 않는 제약, 이유가 자명하지 않은 대안 기각.
