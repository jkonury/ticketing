# 코드베이스 설계 어휘

**깊은 모듈**을 설계한다. 작은 인터페이스 뒤에 많은 동작이 있고, 깨끗한 seam에 놓이며, 그 인터페이스로 테스트할 수 있는 모듈이다. 코드를 설계하거나 재구성할 때 이 어휘와 원칙을 쓴다. 목표는 호출자에게 레버리지, 유지보수하는 사람에게 locality, 모두에게 테스트 용이성이다.

이 저장소의 모듈 구조와 계층(`domain`, `application`, `adapter`) 규칙은 [core 작성 지침](../../../../docs/rules/backend-core.md)과 [docs/architecture.md](../../../../docs/architecture.md)가 정한다. 이 문서는 그 위에서 설계 판단을 말할 때 쓰는 공용 어휘다.

## 용어

"컴포넌트", "서비스", "API", "경계"로 바꿔 쓰지 않고 아래 용어를 정확히 쓴다. 용어의 일관성이 요점이다.

- **모듈(module)**: 인터페이스와 구현을 가진 모든 것. 규모와 무관하다(함수, 클래스, 패키지, 계층을 가로지르는 슬라이스). 피할 말: 단위, 컴포넌트, 서비스.
- **인터페이스(interface)**: 호출자가 모듈을 올바르게 쓰려고 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변식, 순서 제약, 오류 방식, 필요한 설정, 성능 특성을 포함한다. 피할 말: API, 시그니처(타입 수준의 표면만 가리켜 너무 좁다).
- **구현(implementation)**: 모듈 안, 코드 본체. **어댑터**와 구분한다. 작은 어댑터에 큰 구현이 있을 수 있고(Postgres 저장소), 큰 어댑터에 작은 구현이 있을 수 있다(인메모리 fake). seam이 주제일 때는 "어댑터", 그 외에는 "구현"이라 한다.
- **깊이(depth)**: 인터페이스에서의 레버리지. 호출자(또는 테스트)가 배워야 하는 인터페이스 한 단위당 실행할 수 있는 동작의 양. 작은 인터페이스 뒤에 많은 동작이 있으면 **깊고**, 인터페이스가 구현만큼 복잡하면 **얕다**.
- **seam**(Michael Feathers): 그 자리를 고치지 않고도 동작을 바꿀 수 있는 지점. 모듈의 인터페이스가 놓이는 *위치*다. seam을 어디에 두는가는 그 뒤에 무엇을 두는가와 별개의 설계 결정이다. 피할 말: 경계(DDD의 bounded context와 겹친다).
- **어댑터(adapter)**: seam에서 인터페이스를 만족시키는 구체적인 것. 내용물이 아니라 *역할*(어떤 자리를 채우는가)을 말한다.
- **레버리지(leverage)**: 깊이가 호출자에게 주는 것. 배운 인터페이스 단위당 더 많은 능력. 구현 하나가 N개 호출처와 M개 테스트에서 값을 한다.
- **locality**: 깊이가 유지보수하는 사람에게 주는 것. 변경, 버그, 지식, 검증이 호출자에 흩어지지 않고 한곳에 모인다. 한 번 고치면 모든 곳이 고쳐진다.

## 깊은 모듈과 얕은 모듈

**깊은 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│    작은 인터페이스    │  ← 메서드 적음, 단순한 파라미터
├─────────────────────┤
│                     │
│      깊은 구현       │  ← 복잡한 로직이 숨겨짐
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 얇은 구현(피한다):

```
┌─────────────────────────────────┐
│          큰 인터페이스           │  ← 메서드 많음, 복잡한 파라미터
├─────────────────────────────────┤
│  얇은 구현                       │  ← 그냥 넘겨 주기만 함
└─────────────────────────────────┘
```

인터페이스를 설계할 때 묻는다.

- 메서드 수를 줄일 수 있는가?
- 파라미터를 단순하게 할 수 있는가?
- 더 많은 복잡도를 안으로 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성이다.** 깊은 모듈도 내부는 작고 mock·교체할 수 있는 부품들로 이루어질 수 있다. 그것들이 인터페이스의 일부가 아닐 뿐이다. 모듈은 인터페이스에 놓인 **외부 seam**과 구현 안에 숨은(자기 테스트가 쓰는) **내부 seam**을 모두 가질 수 있다.
- **삭제 테스트.** 모듈을 지운다고 상상한다. 복잡도가 사라지면 그것은 단순 통과 모듈이었다. 복잡도가 N개 호출자에 다시 나타나면 제 몫을 하던 모듈이다.
- **인터페이스가 곧 테스트 표면이다.** 호출자와 테스트는 같은 seam을 건넌다. 인터페이스 *너머*를 테스트하고 싶다면 모듈의 모양이 잘못된 것이다.
- **어댑터가 하나면 가상의 seam, 둘이면 진짜 seam이다.** 실제로 달라지는 것이 없다면 seam을 만들지 않는다.

## 테스트하기 좋게 설계하기

1. **의존성을 만들지 말고 받는다.** 생성자 주입으로 외부 의존성을 넘긴다.
2. **부수 효과를 일으키지 말고 결과를 반환한다.** 도메인 메서드는 결과(값, 상태 전이)를 돌려주고 호출자가 효과를 적용하게 한다.
3. **표면적을 작게.** 메서드가 적을수록 테스트가 적게 필요하다. 파라미터가 적을수록 준비가 단순하다.

## 관계

- **모듈**은 정확히 하나의 **인터페이스**를 가진다(호출자와 테스트에 내미는 표면).
- **깊이**는 **모듈**의 속성이고 **인터페이스**를 기준으로 잰다.
- **seam**은 **모듈**의 **인터페이스**가 놓이는 곳이다.
- **어댑터**는 **seam**에 놓여 **인터페이스**를 만족시킨다.
- **깊이**는 호출자에게 **레버리지**를, 유지보수하는 사람에게 **locality**를 낳는다.

## 깊게 만들기: 의존성 분류

얕은 모듈 묶음을 깊게 만들 때는 의존성을 분류한다. 분류가 깊어진 모듈을 seam 너머로 테스트하는 방법을 정한다.

1. **프로세스 내부**: 순수 계산, 메모리 상태, I/O 없음. 항상 깊게 만들 수 있다. 모듈을 합치고 새 인터페이스로 바로 테스트한다. 어댑터는 필요 없다.
2. **로컬 대체 가능**: 로컬 테스트 대역이 있는 의존성(Testcontainers의 PostgreSQL·Redis). 대역이 있으면 깊게 만들 수 있다. 테스트 스위트 안에서 대역을 띄워 테스트한다. seam은 내부이므로 모듈의 외부 인터페이스에 포트를 두지 않는다.
3. **원격이지만 우리 소유**(포트와 어댑터): 네트워크 너머 우리 서비스(`payment`, `realtime` 등). seam에 **포트**(인터페이스)를 정의한다. 깊은 모듈이 로직을 소유하고 전송은 **어댑터**로 주입한다. 테스트는 인메모리 어댑터, 운영은 HTTP·Kafka 어댑터를 쓴다.
4. **진짜 외부**: 통제하지 못하는 제3자 서비스(PG 등). 깊어진 모듈이 외부 의존성을 주입받는 포트로 받고, 테스트는 mock 어댑터(이 저장소에서는 `fake-pg`나 가짜 구현)를 준다.

seam 규율:

- 어댑터가 둘(보통 운영 + 테스트)로 정당화되지 않으면 포트를 만들지 않는다. 어댑터가 하나뿐인 seam은 우회로일 뿐이다.
- 내부 seam은 테스트가 쓴다는 이유로 인터페이스에 노출하지 않는다.

테스트 전략은 **쌓지 말고 교체한다**:

- 깊어진 모듈의 인터페이스에 테스트가 생기면, 얕은 모듈에 있던 예전 단위 테스트는 낭비이므로 지운다.
- 새 테스트는 깊어진 모듈의 인터페이스에 쓴다. 인터페이스가 테스트 표면이다.
- 테스트는 내부 상태가 아니라 인터페이스로 관찰되는 결과를 단언한다.
- 내부 리팩터링에 살아남아야 한다. 구현이 바뀔 때 테스트를 고쳐야 한다면 인터페이스 너머를 테스트하고 있는 것이다.

> 병렬 서브에이전트로 인터페이스를 여러 가지로 설계해 비교하는 "Design It Twice" 절차는 가져오지 않았다. 필요하면 [원본](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/DESIGN-IT-TWICE.md)을 참고한다.
