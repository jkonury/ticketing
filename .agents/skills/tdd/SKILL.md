TDD는 red → green 루프다. 이 스킬은 그 루프가 남길 가치가 있는 테스트를 만들도록 하는 기준이다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴, 루프 규칙을 다룬다. 모든 절을 사이클마다, 루프 전과 도중에 확인한다.

출처: [mattpocock/skills](https://github.com/mattpocock/skills)의 `tdd`, `codebase-design`(commit `6f7f783`)을 이 저장소에 맞게 고쳤다. 이 스킬 디렉터리를 `SKILL_DIR`이라 부른다.

## 시작 전에

1. 변경 경로에 해당하는 규칙을 읽는다. 백엔드는 [백엔드 테스트 지침](../../../docs/rules/backend-testing.md)과 해당 모듈 지침, web은 [프론트엔드 지침](../../../docs/rules/frontend.md)의 테스트 절이다. 테스트 이름·단언·픽스처·Testcontainers 같은 **작성 규범은 그 문서가 정한다.** 이 스킬은 규범을 다시 쓰지 않는다.
2. 코드를 탐색할 때 [docs/glossary.md](../../../docs/glossary.md)를 읽어 테스트 이름과 인터페이스 어휘를 도메인 용어에 맞춘다. 건드리는 영역의 ADR을 존중한다.

## 좋은 테스트란

테스트는 구현 세부가 아니라 **공개 인터페이스를 통한 동작**을 검증한다. 코드가 완전히 바뀌어도 테스트는 바뀌지 않아야 한다. 좋은 테스트는 명세처럼 읽힌다. "만료된 예매는 확정할 수 없다"는 어떤 능력이 있는지 정확히 알려 주고, 내부 구조에 관심이 없으니 리팩터링에도 살아남는다.

예시는 [tests.md](references/tests.md), mock 기준은 [mocking.md](references/mocking.md)를 본다.

## seam: 테스트를 두는 곳

**seam**은 테스트하는 공개 경계다. 안으로 들어가지 않고 동작을 관찰할 수 있는 인터페이스다. 테스트는 seam에 두고 내부에 두지 않는다.

**미리 합의한 seam에서만 테스트한다.** 테스트를 쓰기 전에 테스트 대상 seam을 적고 사용자에게 확인받는다. 확인하지 않은 seam에는 테스트를 쓰지 않는다. 모든 것을 테스트할 수는 없으므로, seam을 먼저 합의해야 테스트 노력이 모든 경계 사례가 아니라 핵심 경로와 복잡한 로직에 쓰인다.

"공개 인터페이스가 무엇이고 어떤 seam을 테스트할까요?"라고 묻는다. 제안한 seam마다 무엇을 잡고 무엇을 놓치는지 한 줄을 붙인다. 위임 실행(지시서를 받은 서브에이전트)이라면 seam이 지시서에 이미 합의되어 있어야 하고, 없으면 임의로 정하지 않고 보고한다.

인터페이스의 모양 자체가 문제일 때(모듈이 얼마나 깊은지, seam이 어디여야 하는지, 인터페이스가 무엇을 드러내야 하는지)는 [codebase-design.md](references/codebase-design.md)의 어휘를 참고한다. 참고서이고 따로 진행하는 세션이 아니다.

이 저장소의 seam 후보와 우선순위는 설계 규칙에서 나온다. 예: `(회차, 좌석)` 유니크 제약이 최종 방어선인 확정 경쟁, Redis Lua 원자성, 이벤트·웹훅 멱등성, 도메인의 상태 전이 허용·금지 경로. 어느 것이 테스트 대상인지 정하는 근거는 [AGENTS.md 4절](../../../AGENTS.md#4-반드시-지킬-설계-규칙)이다.

## 안티패턴

- **구현 결합**: 내부 협력자를 mock하거나, private 메서드를 테스트하거나, 우회 경로로 검증한다(인터페이스 대신 DB를 직접 조회). 리팩터링했는데 동작은 같아도 테스트가 깨지면 이 신호다.
- **동어반복**: 단언이 코드가 계산하는 방식 그대로 기대값을 다시 계산한다(`assertThat(add(a, b)).isEqualTo(a + b)`). 구성상 통과하므로 코드와 절대 어긋나지 않는다. 기대값은 독립된 진실의 출처(검증된 리터럴, 손으로 푼 예, 명세)에서 와야 한다.
- **수평 슬라이싱**: 테스트를 전부 먼저 쓰고 구현을 나중에 쓴다. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증한다. 실제 동작이 아니라 구조의 _모양_을 테스트하고, 실제 변경에 둔감해지며, 구현을 이해하기 전에 테스트 구조에 얽매인다. 대신 **수직 슬라이스**로 진행한다. 테스트 하나 → 구현 하나 → 반복이며, 각 테스트는 직전 사이클이 가르쳐 준 것에 반응하는 **예광탄**이다.

## 루프 규칙

- **green 전에 red.** 실패하는 테스트를 먼저 쓰고, 통과시킬 만큼만 코드를 쓴다. 미래의 테스트를 예상하거나 추측성 기능을 추가하지 않는다. 쓴 테스트가 **올바른 이유로** 실패하는지 확인한다.
- **한 번에 한 슬라이스.** 사이클마다 seam 하나, 테스트 하나, 최소 구현 하나.
- **리팩터링은 루프에 넣지 않는다.** 리뷰 단계 몫이다([review-diff](../review-diff/SKILL.md)). red → green 구현 사이클 안에서 하지 않는다.

## 실행

- 슬라이스의 red·green 확인은 해당 테스트만 `./scripts/agent/test/run-tests.sh --tests "패턴"`으로 실행한다.
- 작업을 마치기 전에는 필터 없이 `run-tests.sh`와 `./scripts/agent/test/verify-changed.sh`를 실행한다([AGENTS.md 6절](../../../AGENTS.md#6-테스트와-검사)). 이 검사 결과가 끝났다는 근거다.
- 실패는 실패한 그대로 보고한다. 통과시키려고 테스트를 지우거나 `@Disabled` 처리하지 않는다.
