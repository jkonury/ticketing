# 실행 계획

[`/plan-next`](../../../.agents/skills/plan-next/SKILL.md)가 쓰고 [`/implement`](../../../.agents/skills/implement/SKILL.md)가 실행하는 계획 문서를 둔다. [템플릿](template.md)을 복사해 `YYYY-MM-DD-<slug>.md`로 저장한다. 마일스톤 설계 계획은 [docs/plans/](../../plans/)에 둔다.

## 계획과 승인

- `status`는 `draft` → `approved` → `done` 순서로 바뀐다. 사용자가 해당 계획을 승인하면 `approved_at`에 시간대를 포함한 승인 시각을 적는다. 최종 검사와 리뷰를 마친 뒤 `done`으로 바꾼다. [ADR 0048 결정 7](../../adr/0048-ai-dev-workflow-pipeline.md#결정)
- task 하나는 독립적으로 시연하거나 검증할 수 있는 변경으로 묶는다. 동작은 공개 경계를 가로지르는 작은 단위로 구현하고, 준비 리팩터링은 필요할 때 별도 선행 task로 둔다. 폭이 넓은 기계적 변경은 도입 → 호출처 이전 → 기존 형태 제거로 나누고 제거는 모든 이전이 끝난 뒤에 한다.
- task마다 변경 범위, `Blocked by`, 실행 가능한 AC, 테스트할 공개 경계·모듈과 선례를 적는다. AC는 저장소 루트에서 실행할 명령으로 적고 필요한 준비와 기대 결과를 함께 기록한다. 테스트 경계는 계획 승인에 포함한다.

## 실행과 재개

- 시작 전 승인된 계획이 HEAD에 있고 작업 트리는 깨끗해야 한다. 계획에 포함된 task 커밋은 계획 승인으로 권한을 얻는다. 승인본과 완료 상태를 담는 별도 계획 커밋은 사용자에게 커밋 요청이 있어야 한다. [저장소 작업 지침](../../../AGENTS.md#7-공통-규칙)
- 먼저 끝난 task는 HEAD의 계획 체크박스로 확인한다. 중단된 동일 task를 재개할 때만 그 task와 계획 체크박스의 미커밋 변경을 이어 간다. 활성 상태의 계획이나 변경의 소유자가 다르면 사용자와 확인한다.
- Stop 훅과 CLI 검증은 같은 검사 시간과 차단 횟수를 공유한다. CLI의 검증 성공을 확인한 뒤 해당 task와 계획 체크박스만 커밋한다. 차단 상한을 넘긴 task의 수정·재검증 방식은 사용자와 정한다.
- 최종 검사에서는 처음 시작한 SHA부터 HEAD까지의 변경을 기준으로 변경 범위 검사와 계획에 명시한 추가 검사를 실행한다. E2E는 해당하는 경우 이 단계에서 실행한다. 최종 `review-diff`의 범위는 그 SHA와 HEAD 사이이며 명세는 승인된 계획이다.
