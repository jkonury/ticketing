## Important

### 1. `X-Forwarded-For` 위조로 비회원 rate limit 우회

- 위치: `ratelimit/RateLimitFilter.kt:50` (`trustedProxies` 기본값 1, 37줄)
- 원인: `XForwardedRemoteAddressResolver.maxTrustedIndex(1)`은 `X-Forwarded-For`의 마지막 값을 키로 쓴다. 그런데 Gateway 18000은 브라우저가 SSE로 직접 붙는 포트이고, 앞단에 신뢰할 프록시가 없다.
- 시나리오: 공격자가 `GET /api/v1/performances`나 로그인 요청마다 `X-Forwarded-For: <난수 IP>`를 붙여 Gateway에 직접 보낸다. 그러면 키가 매번 `ip:<난수>`로 바뀌어 초당 20, 버스트 40 한도가 적용되지 않는다. 테스트(`GatewayIntegrationTestSupport.kt:39`, `RateLimitTests.kt:80`)도 바로 이 방식으로 IP 키를 바꾼다.
- 수정안: 앞단 프록시가 없는 배포에서는 원격 주소만 신뢰한다. 프록시가 있으면 그 프록시가 XFF를 덮어쓰게 한다. 2번과 함께 설계해야 한다.

### 2. BFF 경유 비회원 트래픽이 버킷 하나를 같이 씀

- 위치: `ratelimit/RateLimitFilter.kt:55` (`RateLimitKeyResolver.resolve`)
- 원인: BFF(`web/src/server/api/gateway-client.ts`)가 `X-Forwarded-For`를 보내지 않는다. 그래서 리졸버가 원격 주소인 BFF IP로 대체하고, 모든 비회원 요청이 `ip:<BFF IP>`로 묶인다.
- 시나리오: 비로그인 사용자 수백 명이 동시에 공연 목록을 보거나 로그인한다. BFF가 Gateway를 초당 20회 넘게 호출하는 순간부터 모든 사용자가 429 `RATE_LIMITED`를 받는다.
- 수정안: BFF가 브라우저 IP를 `X-Forwarded-For`로 넘기고, Gateway는 BFF를 신뢰할 홉으로 설정한다. 이때 1번과 충돌하지 않도록 정해야 한다. 브라우저가 직접 붙는 경로에서는 헤더를 믿지 않고, BFF 경로에서만 헤더를 믿는다.

### 3. 검증 필터가 rate limit보다 먼저 실행됨

- 조치 완료: 예매 생성은 `requireBookingMember → rateLimitFilter → admissionTokenFilter` 순서로 바꿨다. SSE는 `SseTicketFilter`가 티켓 조회(삭제 안 함) → 회원 키로 한도 → `GETDEL` 소비 순서로 `RateLimitFilter`를 감싼다. 429이면 티켓이 남는다.

- 위치: `route/GatewayRoutes.kt:62` (`realtime-streams`), `:66` (`core-bookings-create`)
- 원인: `filters.filter(GatewayFilter)`는 모든 필터에 order 0을 주므로 등록 순서대로 실행된다. 지금은 `sseTicketFilter`, `admissionTokenFilter`가 `rateLimitFilter`보다 앞에 등록되어 있다.
- 시나리오:
  - 같은 회원이 SSE 버스트 10을 넘겨 연결하면 `getAndDelete`로 티켓이 삭제된 뒤 429가 난다. 클라이언트가 같은 티켓으로 재시도하면 401 `SSE_TICKET_INVALID`를 받는다.
  - 공격자가 무작위 `X-Admission-Token`으로 `POST /api/v1/bookings`를 대량으로 보내면 요청마다 Redis HGETALL이 실행된다. 이 요청은 403으로 끝나 rate limit 단계까지 가지 않는다.
- 수정안: 각 라우트에서 `rateLimitFilter`를 검증 필터보다 앞에 둔다. 회원 키가 필요한 라우트에서는 회원 키가 확정된 직후(`requireBookingMember` 다음)에 둔다.

## 기존 문제

### 4. Redis 장애 시 기본 500 응답

- 위치: `admission/AdmissionTokenFilter.kt:36`, `SseTicketFilter.kt:21`
- 원인: `redis.opsForHash().entries(...)`와 `getAndDelete`에서 난 오류를 처리하지 않고 그대로 흘려보낸다.
- 시나리오: Redis가 재시작되는 동안 `POST /api/v1/bookings`가 SCG 기본 오류 형태(`timestamp`, `path`, `status`, `error`)로 응답한다. 응답에 `code`가 없어 BFF와 클라이언트가 `code`로 분기할 수 없다. 이는 [API 규약](../architecture/api-conventions.md)의 "Gateway와 realtime도 같은 모양(status, detail, code)으로 응답한다"와 어긋난다.
- 수정안: `onErrorResume`으로 503 problem 응답을 쓰거나, 전역 `ErrorWebExceptionHandler`를 둔다.

## Nit

### 5. 예열 자격이 예열 종료 후에도 유효

- 위치: `warmup/GatewayWarmupRunner.kt:145`
- 원인: `finally`는 Redis 입장 키만 지우고 `StartupWarmupGatewayCredential`은 비우지 않는다.
- 영향: 예열이 일찍 끝나 readiness 이후에도 최대 3분 동안 `X-Startup-Warmup-Key`가 일치하는 요청은 `STARTUP_WARMUP`으로 표시된다. 이 요청은 rate limit을 건너뛰고(`RateLimitFilter.kt:86`), core에도 예열 요청으로 전달된다.
- 수정안: `finally`에서 자격을 폐기한다(예: `credential.revoke()`).

### 6. 규약 표에 없는 오류 코드

- 위치: `admission/AdmissionTokenFilter.kt:80`
- 내용: 본문 검증 실패에 `INVALID_REQUEST_BODY`를 쓴다. 그런데 [API 규약](../architecture/api-conventions.md)은 검증 오류를 `INVALID_REQUEST`로 정하고, 새 코드를 추가하면 오류 코드 표를 갱신하라고 한다.
- 수정안: `INVALID_REQUEST`를 쓰거나, 오류 코드 표에 이 코드를 추가한다.

### 7. SSE 라우트의 `proxy` 단계 타이머

- 위치: `ratelimit/RateLimitFilter.kt:106`
- 원인: SSE 스트림에서는 `chain.filter`가 연결이 닫힐 때 완료된다. 그래서 `ticketing.gateway.stage{stage=proxy}`에 연결 수명 전체가 기록된다.
- 영향: route 태그 없이 `proxy` p99를 보면 수 분으로 표시되어, 병목 단계를 가르는 지표로 쓸 수 없다.
- 수정안: `realtime-streams`에서는 `proxy` 단계를 기록하지 않거나, 응답 커밋 시점(`beforeCommit`)까지만 잰다.

## 결과에서 뺀 항목

경로 변형으로 라우팅을 우회하는 경우(끝에 `/` 붙이기, `//`, `/./`, `;`)도 검토했다. 이런 요청은 core의 Spring Security(StrictHttpFirewall)가 거부하거나 매핑이 없어 404가 나므로 문제로 보지 않았다.
