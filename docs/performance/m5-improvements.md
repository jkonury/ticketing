# M5-2 개선 및 측정 인계

실행 순서와 결과 확인 방법은 [로컬 부하 테스트 실행 절차](loadtest-runbook.md)를 따른다.

## Step 1: 측정 공백 보완 (검증 미완료)

### 구현 및 지표 해석

- `queue.registration`은 대기열 신규 등록, 기존 대기자 재등록, 이미 입장한 회원의 재등록을 구분한다. `queue.departure`는 실제 대기열 제거 건수로 명시 이탈, 생존 신호 없음, 유예 초과를 구분한다. 입장 Lua는 실제 검사 건수와 제거 건수, 조회 키 생성 건수를 반환한다. `queue.admission`은 조회 키 생성과 Gateway 검증 키 준비 성공·실패를 구분한다. 입장 배치·스케줄러 시작 간격·생존 신호 갱신은 타이머로 기록한다.
- 모든 태그는 제한된 결과와 사유만 사용한다. 인스턴스별 카운터를 합산해야 하며 Redis 스크립트는 한 번의 실제 변경만 반환한다. 프로세스 중단이나 Redis 응답 유실 시 변경은 발생했어도 카운터가 빠질 수 있으므로 이 지표는 정합성 원장이 아니다. Gateway 키 기록이 중간 실패하면 생성된 조회 키 수와 준비된 키 수가 다를 수 있다.
- Gateway `spring.cloud.gateway.requests` 경로별 히스토그램과 Reactor Netty 연결 풀의 active·idle·pending 및 획득 대기를 수집한다. 경로 태그에 사용자 URL을 추가하지 않는다. 코어 `hikaricp.connections.acquire` 버킷과 기존 평균·최대·pending·timeout을 보존한다. 5초 게이지는 순간 급증을 놓칠 수 있으므로 타이머와 JFR을 함께 해석한다.
- k6는 등록·티켓 발급·예매·결제·상세의 전체 실행 Trend와 등록·입장·정시 준비·지각 준비·예매 시도·예매 생성·결제 요청·확정 흐름을 기록한다. 각 Trend는 모든 시도의 HTTP duration이며 SSE 유지 시간이 아니다. `resources.csv`는 1초 간격이다. k6 CPU는 사용한 논리 코어 수(1.0은 한 코어 전체), 호스트 CPU는 전체 논리 코어의 busy 비율이고 RSS·메모리는 바이트다.
- [Spring Boot Metrics](https://docs.spring.io/spring-boot/reference/actuator/metrics.html), [Gateway Metrics](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/global-filters.html), [Redis Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/) 공식 문서와 실제 Gateway 5.0.4 설정 메타데이터를 확인했다.

### 기존 실행 복구와 추가 실행 판정

기존 실행의 첫 자원 표본과 threshold 로그 시각은 아래와 같다(KST). 첫 표본은 프로세스 시작 후 약 1초 이후이고 로그 시각은 종료 부근이므로 정확한 k6 시작·종료 시각이 아니다. A-1 Prometheus 복구 구간도 앞서 기록한 약 1~2초 오차가 있다. 로그는 모든 실행에서 threshold 미달과 iteration 100% 완료를 보여 주지만, 실제 프로세스 종료 코드를 직접 기록하지 않아 99를 독립적으로 검증할 수 없다. 기존 측정은 한계가 있는 참고 자료로 보존하고 정확한 측정 계약을 충족한 기준으로 판정하지 않는다.

| A-2 | 13:44:13 | 13:50:27 |
| A-3 | 13:51:08 | 13:57:11 |

추가 A `build/loadtest/runs/20261113-215403-queue-surge/`와 B `build/loadtest/runs/20261113-223809-hot-seats/`는 실행별 시각과 k6 종료 코드 99를 기록했지만 시드 로그에서 전 회차 800석·핫 좌석 60석으로 확인됐다. 계약의 5,000석·핫 좌석 100석과 달라 기준 측정으로 사용하지 않는다. 시드 스크립트는 저장된 공연장 ID를 재사용하며 좌석 수를 검증하지 않는다. 800석이 예매 생성 건수 차이와 관련됐을 가능성은 있지만 인과관계를 단정하지 않는다. A-2는 15분 30초 상한에서 iteration 1건이 중단됐다. B-2는 예매 시도가 없어 summary의 p95 0은 표본 없음이다. 추가 B는 Gateway 설정 변경 이후의 작업 트리에서 Scouter 활성 상태로 실행돼 이전 계열과 계측·설정도 다르다. 모든 추가 실행의 정합성 검사는 통과했다.

정확한 좌석 규모를 시드에서 검증하고 관측·Gateway 설정을 기준 계열과 맞춘 뒤 콜드 A·B 각 3회를 다시 확보해야 한다. 변경된 Gateway 설정은 별도 비교 계열로 다룬다. Step 1 완료로 표시하지 않으며 Step 2는 시작하지 않는다.

### 대기열 진단 추가 실행

`build/loadtest/runs/20261114-012847-queue-surge/1`은 커밋 `0494f93`의 미커밋 변경이 있는 작업 트리에서 Scouter 활성, Prometheus 관측 비활성으로 실행했다. 좌석은 5,000석이며 k6 시작·종료 시각은 각각 Unix 1794587351·1794587780, 종료 코드는 0이다. 10,000 iteration 중 등록·입장은 각각 9,978명이고 예매 시도 2,054명, 생성·결제 요청·확정은 각각 2,042건, 매진 이탈은 7,925건이다. 예매 생성 p95는 57.97ms, 예상 밖 오류는 22건(0.06%), SSE 연결 성공은 20,168/20,168이며 세 threshold는 통과했다. 정합성 검사에서 5,000석 판매, 중복 판매와 DB·Redis 불일치 0건이다. 단일 진단 실행이며 dirty 내용이 산출물에 없어 전후 개선율이나 같은 조건의 기준으로 사용하지 않는다.

입장 Lua가 조회 키를 만든 뒤 Gateway 검증 키를 별도로 기록하므로 그 사이 상태 조회가 검증 키의 TTL 부재를 만날 수 있다. 현재 조회 코드는 이 경우 조회 키를 삭제한다. 코드상 가능한 경합이며 실제 발생 빈도와 이전 `removed`의 원인으로는 아직 확정하지 않았다. 준비 중·실제 만료·쓰기 실패를 구분할 수 있는 재현과 수정이 남아 있다.

## 1,000명 폭주 구간 JFR 진단

콜드 1,000명·JFR 1회(`20261114-131040-hot-seats`). 예매 폭주는 13:12:04~07의 약 3초이며 `booking_create` p50 1,320ms·p95 1,673ms·최소 616ms였다. 중복 판매 0건. Prometheus 5초 표본이 이 구간을 놓쳐서 JFR의 1초 `CPULoad`와 실행 샘플로 확인했다. n=1이다.

| 관측 | 폭주 구간 값 |
| --- | --- |
| 호스트 CPU(`machineTotal`) | 최대 0.85 (평시 0.2~0.3) |
| core JVM 사용자 CPU | 최대 0.49(16코어 중 약 8코어) |
| Gateway JVM 사용자 CPU | 최대 0.19~0.40 구간이 3~5초 지속 |
| GC pause, safepoint | 구간 안 0건, 무시할 수준 |
| JIT 컴파일 | core 10건 합 2.05초·최장 439ms, Gateway 11건 합 2.24초·최장 507ms |
| core 실행 샘플(454건) | 한 곳에 몰리지 않고 jOOQ·Jackson·Spring MVC·리플렉션에 분산. `tomcat-handler` 가상 스레드 74% |
| Hikari 풀 | `pendingMax` 0, 타임아웃 0 |

- **병목은 대기가 아니라 CPU 포화다.** 호스트 한 대에서 k6(4코어)·Gateway·core가 같은 순간에 약 3초 동안 CPU를 쓴다. DB·Redis·풀은 비어 있다(이전 절과 일치). 요청 수천 건이 한꺼번에 도착해 각 요청의 CPU 작업이 직렬화된다.
- 단일 단계 하나가 느린 것이 아니라 core 단계(`existing`·`hold`·`persist`)가 모두 p50은 수십 ms인데 p95가 약 300ms로 늘어나는 모양이다. CPU 경합 때문에 모든 단계가 같이 늘어난다는 해석과 맞는다.
- JIT 컴파일 스레드가 폭주 구간에 합 2초 넘게 CPU를 쓴다. 워밍업을 해도 p95가 안 줄었으므로 JIT는 주원인으로 확정하지 못한다.
- 확인하지 못한 것: k6가 사용하는 코어를 줄이거나 앱 코어를 늘린 대조(자원 배분이 다른 값은 서버 개선율로 쓰지 않는다), 요청당 CPU 시간(core 약 8코어·약 1초 ÷ 약 1,000요청 = 요청당 수 ms 이상으로 보이나 정밀 계측은 안 했다).

## 코어 배분 대조 (1,000명, 조건당 3회)

콜드 1,000명 `hot-seats`, `--no-scouter --observability`. 호스트 16코어. 예매 시도 인원은 986~1,000명, `http_req_failed` 0, 정합성 모두 통과. 자원 배분이 다른 값이므로 서버 개선율로 쓰지 않는다. 같은 호스트에서 코어 배분이 폭주 지연에 주는 영향을 보는 진단이다.

| k6 코어 / 앱 코어 | 예매 p95 ms (실행 1·2·3) | 예매 p50 ms (실행 1·2·3) | 실행 디렉터리 |

| --- | --- | --- |
| 기준(`auto`, 관측 스택 켬) | 1,688 · 1,575 · 1,766 | `20261114-131726` |

## Step A. 예열 횟수별 상한 진단 (1,000명, 각 1회, 2026-11-14)

계획 [hot-seats 1,000명 p95 300ms 도달 계획](../plans/docs-performance-m5-improvements-md-hot-recursive-lighthouse.md)의 Step A. 코드 변경 없이 `run.sh --warmup --warmup-rounds N`(같은 앱에 부하 N회 뒤 새 회차로 측정)만 다르게 했다. `hot-seats --observability --no-scouter`, 코어 4/12, 풀 10. 모든 실행에서 정시 준비 1,000명, `http_req_failed` 0, 정합성 통과. n=1이므로 방향만 본다.

| 예열 횟수 | 측정 p50 | 측정 p95 | 측정 최소 | 실행 디렉터리 |

| 5 | 373 | 496 | 96 | `20261114-142338-hot-seats/1` |
| 15 | 189 | 274 | 44 | `20261114-143052-hot-seats/1` |
| 15 (`--jfr`) | 272 | 358 | 54 | `20261114-144838-hot-seats/1` |

회차별 추이(p50 / p95 / 최소, ms):

| 회차 | 5회 실행 | 15회 실행 |
| --- | --- | --- |
| 1 | 1,286 / 1,718 / 523 | 1,750 / 2,352 / 712 |
| 2 | 728 / 1,158 / 89 | 822 / 1,095 / 69 |
| 3 | 541 / 749 / 181 | 521 / 727 / 90 |

- **충분히 예열하면 300ms 근처에 닿는다.** 15회 예열 후 측정 p95는 274ms(JFR 켠 실행은 358ms)다. p50은 1,200ms대에서 189ms로 내려간다. 서버 로직 자체는 1,000명을 300ms 안에 처리할 수 있고, 콜드 상태의 코드 실행 비용이 p95를 끌어올리는 쪽이라는 해석과 맞는다.
- **수렴이 느리고 불안정하다.** 5회로는 부족하고(496ms), 10~14회차에야 p95가 280~340ms대로 내려온다. 같은 구간에서 6·9·15회차는 p95가 1,2xx ms로 튀었다. 원인은 확인하지 못했다(JIT 재컴파일·GC 후보이나 JFR을 켜지 않은 회차라 검증 못 함). 따라서 15회 실행의 274ms도 1회 값이며 안정적 달성으로 판정하지 않는다.
- **JFR로 확인한 인터프리터 비율.** 15회 예열 후 측정 구간의 core 실행 샘플은 폭주 구간(15:05:50~51) 98건 중 최상위 프레임이 Interpreted인 것이 0건이다. 콜드 실행(`20261114-131040`)은 폭주 1초 281건 중 164건(58%)이었다. 예열이 실행 코드를 컴파일된 상태로 바꿔 놓는다는 근거다.
- **판단**: 예열 상태 p95가 300ms 근처로 내려가므로 계획대로 Step B(패자 경로 DB 조회 줄이기)와 Step C(AOT 캐시)로 진행한다. 15회 예열은 학습 횟수 후보로 쓰되, 안정 구간은 10회 이상이다.
- 앞 절의 "워밍업을 해도 p95가 안 줄었으므로 JIT는 주원인으로 확정하지 못한다", "콜드 스타트는 주원인 아님" 결론은 1회 워밍업 기준이었다. 위 수치는 콜드 스타트(인터프리터 실행)가 p95의 큰 몫임을 보여 주므로 이 결론을 정정한다.
- `run.sh --warmup-rounds N`을 추가했다(기본 1, 회차별 `warmup-k6-summary-<n>.json`, `env.txt`의 `warmup-rounds`). 실행 중 포트 18090이 compose의 `fake-pg` 컨테이너와 겹쳐 컨테이너를 멈추고 측정했다.

## Step B. 패자 경로 멱등 조회 제거 (1,000명 콜드 3회)

## 1,000명 기준 변경과 마무리 (2026-11-14)

AOT 캐시를 써도 1,000명 p95가 300ms에 닿지 않았다. 폭주 구간 core 샘플의 Interpreted 비율은 AOT(219/363, 60%)와 콜드(253/448, 56%)가 비슷했고, 서로 다른 메서드 약 210~230개에 샘플이 1~3건씩 퍼져 있었다. AOT 캐시는 적용됐으나(core 기동 16.2 → 7.6초) 이 경로가 JIT 전 인터프리터에서 시작하는 것은 그대로다. 원인 분리(C1 임계 미달과 컴파일 대기열 지연)와 JDK 25 AOT 캐시의 범위 확인은 하지 않았다.

- **기준 변경**: 1,000명 콜드(+AOT) 예매 생성 p95를 300ms에서 **1,500ms**로 완화한다. 300ms는 후속 튜닝 목표로 남긴다. `loadtest/lib/options.ts`의 `thresholdsFor`가 VU 100 초과이면 1,500ms, 이하이면 300ms를 적용한다. 50명 조건 300ms는 그대로다.
- **확인 실행**(`20261114-163619-hot-seats/1`, AOT 학습 2회, 1회): p95 1,052ms로 새 p95 threshold 통과. 같은 실행에서 `sse_connect_success`가 0.972(1,000건 중 28건 실패)로 기준(> 0.999)에 미달했고 k6 종료 코드는 99다. 이전 1,000명 실행도 종료 코드 99였으며 p95 외에 SSE 성공률 미달이 섞여 있었는지는 확인하지 못했다. SSE 성공률은 이번 기준 변경 대상이 아니며 미해결로 남긴다.
- **후속 튜닝 후보**(미실행): 컴파일 임계·컴파일 스레드 수 대조, Gateway Redis 왕복 병렬화, core 풀 크기 대조, 요청당 CPU 계측, SSE 연결 실패 원인 확인.

## Step 3: 워밍업 측정 분리 (2026-11-14)

### 구현

- `scripts/loadtest/run.sh --warmup`(기본은 기존 콜드): 같은 JVM을 재시작하지 않고 같은 시나리오 부하를 `--warmup-rounds`회 보낸 뒤 새 회차·좌석으로 본 측정을 한다. **기본 횟수를 1에서 5로 바꿨고 실행 설정(`env.txt`)에 고정 기록한다.** 5회는 Step A의 15회 상한 진단보다 짧다(Step A: 5회 p95 496ms, 15회 274ms, 1회 값). 워밍업 B 기준은 "5회 예열 상태"이며 15회 예열 수준의 수렴을 뜻하지 않는다.

### 해석

- **생존 만료 이탈**: 전·후 모두 0건이다. Step 2 이전의 `removed`·404는 `seen` 만료가 아니라 조회 키·Gateway 검증 키 공백(Step 2에서 수정)이 원인이었다. 이 step의 대상인 "정상 연결자의 생존 만료 제거"는 현재 설정(유예 30초, heartbeat 15초)에서 재현되지 않는다.
- **생존 신호 지연**: 급증 구간의 `queue.presence.update`는 평균 0.2~0.3초, p95 버킷 1.1~1.8초, p99 약 1.4~2.1초(버킷 상한)다. 유예 30초 대비 약 15배 여유가 있어 현재는 만료로 이어지지 않는다. 지연 원인(단일 Lettuce 연결 큐잉, Redis 서버 점유, CPU 경합, GC)은 이번 관측으로 분리하지 못했고 원인으로 단정하지 않는다. 호출 수는 회차당 약 9.1~9.6만 건(등록·위치 조회·heartbeat 포함)이고 Redis 명령 최대 약 1.25~1.3만/초다.
- **입장 처리량**: 설정은 50명/1초지만 스케줄러는 `fixedDelay`라 한 주기가 평균 약 1.22초(1초 지연 + 배치 0.12~0.16초 + 스케줄링 여유)이고 실제 처리량은 약 37명/초다. 10,000명 입장에 약 270초가 걸린다. 이는 개선 대상이라기보다 입장량 제어의 설계 파라미터이며, 처리량을 50명/초에 맞추려면 `fixedRate`나 배치·간격 변경이 필요하다. 이는 기본 설정 계약(입장량)과 다중 인스턴스 락(`queue:admit-lock` TTL = 간격)에 영향을 주므로 합의 없이 바꾸지 않았다. 배치 실행(평균 0.12~0.16초)은 토큰 키 기록을 이미 `async`로 겹쳐 보내므로 순차 왕복 비용은 남아 있지 않다.
- **GC**: realtime GC pause 합은 구간 264초 중 약 3.7~3.9초(약 1.5%)다. 힙(최대 약 0.9~1.0GB) 부족의 증거는 없어 힙 변경 실험은 진행하지 않았다.
- **회차별 지연**: A는 단일 회차를 쓰므로 회차별 비교는 의미가 없다. 다중 회차 지연은 측정하지 않았다.

### 판정과 한계

- 완료 기준의 "정상 연결자의 만료 제거 감소"는 감소할 대상이 이미 0건이어서 **지표로 입증할 변경이 없고**, 변경하지 않았으므로 실제 이탈자의 유예 후 제거·다중 인스턴스 입장량 제어는 그대로 유지된다(기존 테스트·동작 변경 없음). 콜드 A 3회 전후 비교는 새 변경이 없어 Step 2 후 3회(위 표)를 현재 기준으로 그대로 사용한다. B 흐름에도 영향이 없다.
- 한계: 이 급증이 10,000명 단일 회차 등록 부하이므로 생존 신호 지연이 유예를 넘는 극단(더 큰 인원, Redis 포화)은 측정하지 않았다. `queue.presence.update` 지연이 커지는 원인 분리와, 필요 시 입장 간격을 `fixedRate`로 바꾸는 계약 변경은 후속 합의 사항으로 남긴다.
- 다음 가설(미실행): (1) 생존 신호 지연이 단일 Lettuce 연결 큐잉이면 realtime의 Redis 왕복 수 감소(위치 조회·touch 통합) 후 `queue.presence.update` 분포 비교. (2) 입장량 50명/초 보장이 필요하면 설계 합의 후 스케줄 방식 변경.
- 로드맵 체크박스는 갱신하지 않았다.

## Step 5: 예매 연결 대기 감소 (2026-11-14, 코드 개선 없음·관측 단계 1개 추가)

### 결론

연결 대기는 **선점 패자의 멱등 조회 1회**(예매 시도 약 94%)에서 생기고, 콜드에서만 크다. 원인은 풀 슬롯 부족이 아니라 **연결을 쥔 시간 자체가 콜드에서 4~5배 길어진 것**(usage 평균 콜드 9.4ms, 워밍업 2.0ms)이다. 풀을 20으로 키우면 usage가 두 배(18.5ms)가 되어 총 점유 시간이 같고 예매 p95는 나아지지 않았다. 따라서 **풀 크기·트랜잭션 구조는 바꾸지 않았다.** 추가한 것은 패자 조회의 `existing` 단계 타이머뿐이다(관측용, 성능 주장 없음). 로드맵 체크박스는 갱신하지 않았다.

### 작업 1. 경로별 연결 획득 (진단 `20261114-183120-hot-seats/1`, 콜드 B 1회, 코드 변경 전)

### 작업 2. 코드 변경

`CreateBookingService`의 선점 실패 시 멱등 조회를 `stage("existing")` 타이머로 감쌌다(`ticketing.booking.create.stage{stage=existing}`, `hold` 단계에 포함). 동작은 같다. 패자의 유일한 DB 접근이라 연결 대기가 이 단계 지연으로 그대로 드러난다.

줄일 수 있는 중복 획득은 없었다. 패자 조회는 멱등 재호출 복구의 필수 경로이고 획득이 1회뿐이다. 이를 없애려면 멱등 키를 Redis에 두거나 선점 토큰을 키에서 결정하는 방식이 필요한데, 멱등 키 검사 위치·선점 소유자 검증 규칙이 바뀌는 **설계 변경**이라 구현하지 않았다(아래 한계). 멱등·실패 복구·부분 확정 롤백·유니크 제약 회귀 테스트는 기존 것을 그대로 통과했다.

### 한계와 다음 가설

- 모든 계열이 3회이고 Scouter 활성 조건이다. 콜드 풀 10의 Step 2 값(2,025ms)과 이번 값(1,823ms)의 차이는 세션 차이일 수 있어 개선으로 읽지 않는다.
