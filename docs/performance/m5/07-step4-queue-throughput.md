## Step 4: 대기열 처리량 관측 (2026-11-14, 코드 변경 없음)

### 결론

Step 2 이후의 콜드 A에서 정상 연결자의 생존 만료 제거는 관측되지 않았다. 효과를 입증할 수 있는 개선 대상이 없어 **서버 코드·설정·runner를 바꾸지 않았고 새 측정 실행도 하지 않았다**(힙 변경 비교도 GC 영향이 남지 않아 수행하지 않음). 기존 실행의 `prometheus.json`(`queueMetrics`, `gcPauseSeconds`)을 작업 1·2의 관점으로 다시 읽은 결과만 기록한다. 공통 구현 검증(테스트·ktlint·detekt·E2E)은 변경이 없어 실행하지 않았고 문서 검사만 수행했다.

### 해석

- **생존 만료 이탈**: 전·후 모두 0건이다. Step 2 이전의 `removed`·404는 `seen` 만료가 아니라 조회 키·Gateway 검증 키 공백(Step 2에서 수정)이 원인이었다. 이 step의 대상인 "정상 연결자의 생존 만료 제거"는 현재 설정(유예 30초, heartbeat 15초)에서 재현되지 않는다.
- **생존 신호 지연**: 급증 구간의 `queue.presence.update`는 평균 0.2~0.3초, p95 버킷 1.1~1.8초, p99 약 1.4~2.1초(버킷 상한)다. 유예 30초 대비 약 15배 여유가 있어 현재는 만료로 이어지지 않는다. 지연 원인(단일 Lettuce 연결 큐잉, Redis 서버 점유, CPU 경합, GC)은 이번 관측으로 분리하지 못했고 원인으로 단정하지 않는다. 호출 수는 회차당 약 9.1~9.6만 건(등록·위치 조회·heartbeat 포함)이고 Redis 명령 최대 약 1.25~1.3만/초다.
- **입장 처리량**: 설정은 50명/1초지만 스케줄러는 `fixedDelay`라 한 주기가 평균 약 1.22초(1초 지연 + 배치 0.12~0.16초 + 스케줄링 여유)이고 실제 처리량은 약 37명/초다. 10,000명 입장에 약 270초가 걸린다. 이는 개선 대상이라기보다 입장량 제어의 설계 파라미터이며, 처리량을 50명/초에 맞추려면 `fixedRate`나 배치·간격 변경이 필요하다. 이는 기본 설정 계약(입장량)과 다중 인스턴스 락(`queue:admit-lock` TTL = 간격)에 영향을 주므로 합의 없이 바꾸지 않았다. 배치 실행(평균 0.12~0.16초)은 토큰 키 기록을 이미 `async`로 겹쳐 보내므로 순차 왕복 비용은 남아 있지 않다.
- **GC**: realtime GC pause 합은 구간 264초 중 약 3.7~3.9초(약 1.5%)다. 힙(최대 약 0.9~1.0GB) 부족의 증거는 없어 힙 변경 실험은 진행하지 않았다.
- **회차별 지연**: A는 단일 회차를 쓰므로 회차별 비교는 의미가 없다. 다중 회차 지연은 측정하지 않았다.

### 판정과 한계

- 완료 기준의 "정상 연결자의 만료 제거 감소"는 감소할 대상이 이미 0건이어서 **지표로 입증할 변경이 없고**, 변경하지 않았으므로 실제 이탈자의 유예 후 제거·다중 인스턴스 입장량 제어는 그대로 유지된다(기존 테스트·동작 변경 없음). 콜드 A 3회 전후 비교는 새 변경이 없어 Step 2 후 3회(위 표)를 현재 기준으로 그대로 사용한다. B 흐름에도 영향이 없다.
- 한계: 이 급증이 10,000명 단일 회차 등록 부하이므로 생존 신호 지연이 유예를 넘는 극단(더 큰 인원, Redis 포화)은 측정하지 않았다. `queue.presence.update` 지연이 커지는 원인 분리와, 필요 시 입장 간격을 `fixedRate`로 바꾸는 계약 변경은 후속 합의 사항으로 남긴다.
- 다음 가설(미실행): (1) 생존 신호 지연이 단일 Lettuce 연결 큐잉이면 realtime의 Redis 왕복 수 감소(위치 조회·touch 통합) 후 `queue.presence.update` 분포 비교. (2) 입장량 50명/초 보장이 필요하면 설계 합의 후 스케줄 방식 변경.
- 로드맵 체크박스는 갱신하지 않았다.
