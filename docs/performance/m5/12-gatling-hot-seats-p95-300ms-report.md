# M5-2 개선 및 측정 인계 (12) Gatling 외부 예열 hot-seats p95 300ms 최종 보고

> 허브: [M5-2 개선 및 측정 인계](../m5-improvements.md) · 이전: [Step 8 최종 측정과 M5 결과](11-step8-final-report.md) · 계획: [hot-seats Gatling p95 300ms 계획](../../plans/hot-seats-gatling-p95-300ms.md) · 상세 기록: [Gatling 인계](../../plans/hot-seats-gatling-handoff.md)

## 결론

- **목표(외부 15회 예열 후 5회 모두 예매 생성 p95 300ms 미만)는 달성하지 못했다.** 로드맵 항목은 체크하지 않는다.
- 최종 판정 D 5회의 전체 p95는 403·374·386·306·391ms(중앙값 386ms)다. 5회 모두 미달이다. 정합성·준비 인원·429·SSE 검사는 통과했고 미달은 p95 항목뿐이다.
- 현 코드의 외부 15회 예열 상태는 350~386ms 범위다. 내부 예열 계열의 목표 비교 기준은 이 값이다(콜드 1,385ms와 섞지 않는다).
- 서버 코드·설정은 바꾸지 않았다. 변경은 측정 도구(러너·판정·검증 스크립트)와 문서뿐이다.

## 측정 조건

Scouter OFF(별도 표기 제외)·관측 ON·Gatling 힙 2g, CPU 배치 발생기 0-3 / 앱 4-15(AMD Ryzen 7 5700G, 16논리 CPU), 1,000명 hot-seats, `--booking-p95-ms 300`. 실행 산출물은 `build/loadtest/runs/`에 있다. 콜드 계열과 웜 계열 수치를 섞지 않는다.

## 단계별 결과(전체 p95, ms)

|---|---|---|---|
| A | 5회 예열 | 512, 534, 505 | 512 |
| A | 15회 예열 | 328, 392, 368 | 368 |
| B | CPU 기존 배치, 15회 예열 | 400, 350, 344 | 350 |

- 예열 5→15회로 약 28% 줄었다(512→368ms). 이후 예열 증가 효과는 확인하지 않았다.
- Scouter ON은 같은 시기 OFF(368~421ms)보다 높았으나 3회 표본이라 비용을 정량화하지 않는다. CPU·GC·메모리 비교는 정리하지 않았다.
- 공식 에이전트 계열은 `.env`의 에이전트가 쓰여 패치 에이전트가 아니었다. 별도 계열로만 보존했다.

## 진단 결과

- 1,000건은 첫 163ms 안에 모두 발송되고 지연은 시작 시점과 무관하게 약 290ms다. p95는 개별 요청 비용이 아니라 폭주 처리 완료 시간(0.35~0.43초)이 결정한다.
- 폭주 1초 평균 JVM CPU는 gateway 1.25·core 1.03·fake-pg 0.39코어로 앱용 12코어 대부분이 비어 있다. core 처리 평균은 32ms다. GC 정지(서버 합 14~17ms)와 Redis 서버 연산(`EVALSHA` 평균 약 24µs)은 원인이 아니다.
- 평균 분해(`20261115-213031`): Gateway route 138ms = jwt 0.5 + admission-body 14.0 + admission-redis 22.4 + ratelimit-redis 41.2 + proxy 61.6. Gatling p50(260ms)과 route p50(142ms) 사이 약 118ms는 구성을 분해하지 못했다.
- 발생기 CPU를 6코어로 늘린 대조는 오히려 악화됐다(1,255/428/390ms). 발생기 코어 부족 가설은 지지되지 않는다.
- **병목 원인은 확정하지 못했다.** 서버 코드·설정 변경 후보에 근거가 없어 변경하지 않았다.

## 미해결 항목

- Gateway→core 연결 리셋(`Connection reset by peer(-104)`): B와 교대 실행에서 무효 실행 4건+`warmupDelta` 어긋난 실행을 만들었다. D 최종 판정에서는 재발하지 않았다. 원인 미확인이며 무효 표본은 보존하고 판정에서 제외했다.
- 폭주 sub-second 단위의 스레드별 CPU 대기·JIT 상태, 클라이언트~Gateway 118ms, 간헐적 1.2초 튐은 설명하지 못했다.

## 회귀 확인

- queue-surge Gatling 3회(`20261116-044521-queue-surge`): 모두 통과, 중복 판매 0·Redis 불일치 0·5,000석 확정, 예매 생성 p95 26/43/90ms. 서버 변경이 없어 전후 비교가 아닌 현 코드 기록이다.
- 보상(`seat-conflict-refund`): Gatling 러너를 연결했다(첫 단계·본 단계 별도 JVM, `compensation.json`의 `ok`를 `verdict.json`에 반영). `20261116-050237` 통과(쌍 100, 확정 100, 환불 100, 중복 환불 0).
- 도구 결함 수정: `verify-compensation.sh`가 PG 거래를 UTC 날짜로 조회해 한국 시각 00~09시에 쌍별 PG 검사가 실패했다. Asia/Seoul 날짜로 고쳤다. 수정 전 실패 실행 `20261116-050028`을 보존했다.

Python 회귀 12개, 셸 구문, ktlint·detekt, 문서 검사를 통과했다. 변경이 셸·Python·문서뿐이고 서버 코드는 바꾸지 않아 전체 `run-tests.sh`·E2E는 다시 돌리지 않았다.
