## Step 2: 대기열 경합 수정 (2026-11-14)

### 경합 재현과 수정

`realtime/src/test/kotlin/io/github/ticketing/realtime/queue/QueueRaceTests.kt`가 Redis 템플릿 서브클래스(`InterleavingRedis`)의 훅으로 명령 직전에 다른 흐름을 끼워 넣어 실행 순서를 통제한다(Testcontainers Redis, 고정 `MutableClock`). 수정 전 코드(HEAD)에서 7건 중 5건이 실패했고 수정 후 모두 통과한다. 수정 전 로그는 `build/queue-races-red.log`다.

| 경합 | 수정 전 | 수정 |
|---|---|---|
| `waiting` 등록 후 `seen` 기록 전 admit | 통과(Step 1의 등록 Lua로 이미 닫힘, 회귀 방지 테스트) | 없음 |
| 입장 토큰 확인 뒤 등록 전에 admit가 입장시킴 | 입장한 회원이 대기열에 다시 들어가고 `WAITING` 응답(입장 중복 가능) | `register.lua`: 입장 기록 확인·대기 여부·`INCR`·`waiting`·`seen`을 회차 해시 태그 안의 한 스크립트로 처리. 재등록은 순번을 쓰지 않는다 |
| 순번 조회 뒤 admit, 이후 `seen` 갱신 | 입장한 회원의 `seen` 항목이 남음 | `touch-seen.lua`: 대기 중인 회원만 갱신 |
| 조회 키는 있고 Gateway 검증 키는 아직 없음 | 조회 키 삭제, 404 `QUEUE_ENTRY_NOT_FOUND`, SSE도 404(`removed`) | 조회 키 남은 TTL이 `토큰 TTL - admission-preparation-grace(기본 5초)`보다 크면 준비 중으로 보고 조회 키를 유지, `WAITING` position 1로 응답. 검증 키 해시가 있으나 만료 시간 미설정인 틈도 같다. 유예 이후에도 검증 키가 없으면 기존처럼 정리·404 |
| 마지막 대기자 처리 중 새 등록 | 대기자가 있는데 `queue:active`에서 빠짐 | 제거 뒤 `waiting` 크기를 재확인해 있으면 `SADD`(`queue.active{result=restored}`) |

토큰은 Gateway가 검증할 수 있을 때만 응답한다. 키 소유·발급 절차·API 상태 값은 바꾸지 않았으며 새 지표만 추가했다(`queue.admission{result=preparing|lookup_removed}`). `queue:active`와 Gateway 키는 다른 슬롯이라 Lua에 넣지 않았다. ADR 0021이 허용한 프로세스 중단 시 토큰 기록 공백은 그대로다(유예 후 정리). `QueueApiTests`의 "없는 토큰 정리"는 방금 만든 키를 준비 중으로 보게 되어 조회 키 TTL을 9분으로 바꿨다. 다중 인스턴스 테스트 3건(재등록·동시 등록·활성 회차 복구)을 추가했다.

정상 등록·입장 중의 404·잘못된 `removed`·결과 없이 종료는 사라졌다(A 전 3회 모두 발생, 후 3회 0건). B의 예매 p95 1,500ms·300ms 기준 미달은 이 step의 범위 밖이며 남아 있다. 로드맵 체크박스는 갱신하지 않았다.
