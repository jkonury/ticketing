## Step 3: 워밍업 측정 분리 (2026-11-14)

### 구현

- `scripts/loadtest/run.sh --warmup`(기본은 기존 콜드): 같은 JVM을 재시작하지 않고 같은 시나리오 부하를 `--warmup-rounds`회 보낸 뒤 새 회차·좌석으로 본 측정을 한다. **기본 횟수를 1에서 5로 바꿨고 실행 설정(`env.txt`)에 고정 기록한다.** 5회는 Step A의 15회 상한 진단보다 짧다(Step A: 5회 p95 496ms, 15회 274ms, 1회 값). 워밍업 B 기준은 "5회 예열 상태"이며 15회 예열 수준의 수렴을 뜻하지 않는다.
- 워밍업 고정 조건: 회차당 시나리오 기본 부하(B 1,000명), 회차마다 새 공연 회차·좌석 시드, 요청마다 새 멱등 키. 회차 종료 후 완료 조건은 (1) 그 회차에서 결제 요청이 나간 PENDING 예매 0건(상한 120초), (2) 대기열 waiting 0건이고 `queue:active`에서 빠짐(상한 30초)이다. 상한 안에 끝나지 않으면 실행 실패다. 결과는 `warmup-settle-<n>.json`. DB·Redis는 삭제·flush하지 않는다(남은 `queue:admitted` 키는 TTL 만료이며 회차 ID가 달라 본 부하와 겹치지 않는다). 격리는 `isolation.json`(회차 ID 구분, 워밍업 회차와 본 회차의 멱등 키 겹침 0건)으로 확인한다.
- 서버 지표 `scripts/loadtest/metrics-delta.py`: 워밍업 직전·본 부하 직전·본 부하 직후에 각 앱 `/actuator/prometheus`를 직접 읽어 누적 카운터·히스토그램 버킷의 차분을 `server-delta.json`(본 측정), `server-delta-warmup.json`(워밍업 구간)에 저장한다. 처음 생긴 시계열의 사전값은 0, 값이 줄거나(reset) 사라진 시계열은 오류(종료 코드 2, 워밍업 실행은 실패 처리)다. p50/p95/p99는 버킷 차분의 선형 보간값, Hikari 획득 평균·GC pause 합계·대기열 카운터도 같은 경계다. 직접 수집·Prometheus 마지막 scrape 시각은 같은 파일에 기록한다. LongTaskTimer 계열(`*_active_seconds_*`)은 누적 카운터가 아니라 수집에서 제외한다(첫 smoke에서 reset 오류로 드러나 수정). 게이지 최대값·Timer max는 두 시점 사이 최대를 알 수 없어 차분 파일에 없고 5초 표본(`prometheus.json`)의 한계를 따른다. 워밍업 실행의 `prometheus.json`에서는 `last_over_time` 누적 항목을 제거했다.
- 통제 입력 검증: 본 측정 차분의 Gateway `core-bookings-create` POST·core `POST /api/v1/bookings` 건수가 k6 예매 시도 수와 같고, 워밍업 구간 차분은 워밍업 k6 시도 합과 같은지 `controlledInputChecks`에서 확인한다(B 3회 모두 본 측정 1,000=1,000, 워밍업 5,000=5,000으로 일치). 워밍업 요청이 본 측정 구간에 들어가지 않았다는 근거다.
- B 준비 현황: `hot-seats` handleSummary가 등록·입장·정시 준비·지각·예매 시도·정시 미준비 인원과 시작 시각을 `readiness.json`(워밍업 회차는 `warmup-readiness-<n>.json`)에 남기고 `measurement.txt`의 `b_readiness`에 요약한다. 표본 없는 카운터가 0으로 보이지 않도록 B 흐름 시작 시 0 표본을 넣어 "기록 없음(null)"과 "0명"을 구분한다. 60초 대기는 워밍업이 아니다. 이 변경은 콜드 실행의 요청·지연에는 영향이 없고 B의 k6 Counter 표본만 늘어난다. A의 인원 흐름은 기존 `flow_*` 지표를 `k6-summary.json`에서 읽는다(A 워밍업은 이 step에서 측정하지 않음).
- 서버 코드·Redis Lua·DB 스키마·설계 규칙은 바꾸지 않았다(셸·Python·k6 스크립트 변경만).

### 검증과 실패 이력

- Kotlin·Lua·백엔드 코드를 바꾸지 않아 `run-tests.sh`, `ktlintCheck detekt`, E2E는 실행하지 않았다(건너뜀). `bash -n scripts/loadtest/run.sh scripts/loadtest/seed.sh`(`run-summary.sh`)와 Python 컴파일 검사 통과.
- 콜드 smoke 최초 실행 `build/loadtest/runs/20261114-180016-smoke/1`: 서버 차분 오류(LongTaskTimer `spring_security_http_secured_requests_active_seconds_sum` 감소를 reset으로 오판)와, 1초 미만 실행이라 Prometheus 추출 구간이 비어 실패(`to-epoch는 from-epoch보다 커야 합니다`, 기존 한계)했다. 수집 대상에서 해당 계열을 제외하고 smoke의 추출 구간 끝을 시작+1초로 보정한 뒤 재실행했다. 이 실행은 오류 재현 기록으로 보존한다.
- 콜드 smoke `20261114-180105-smoke/1`(차분 유효, 통제 입력 k6 1 = core 1), 워밍업 smoke `20261114-180138-smoke/1`(워밍업 5회, 워밍업 구간 차분 k6 5 = core 5, 본 측정 1 = 1) 통과. smoke는 회차·좌석이 없어 settle·격리 확인은 해당 없음.
- 마지막으로 `run.sh`의 `warmup-settle-<n>.json`에 `waitedSeconds`가 빠져 있던 것을 추가했다(워밍업 B 3회는 추가 전 버전으로 실행해 이 항목이 null이다). 추가 후 회귀 확인은 `20261114-182413-hot-seats/1`(`--vus 20 --warmup --warmup-rounds 1`, Scouter 비활성, 1회 확인용)에서 통과했다. 이 실행은 비교에 쓰지 않는다.
- 18090 점유로 compose의 `ticketing-fake-pg-1`을 중지하고 측정한 뒤 다시 시작했다.

### 한계

- 워밍업 횟수(5회)가 Step A의 안정 구간(10회 이상)보다 짧아 수렴 중일 수 있다. 본 측정 2회차의 튐을 설명하지 못한다.
- 워밍업 B 3회는 Scouter 활성 조건이다(Step 2 콜드와 같음). Scouter 영향 분리는 하지 않았다.
- 콜드 B는 이 step에서 재측정하지 않아 날짜·세션 차이가 있다.
- A의 워밍업 측정과 JFR 확인은 하지 않았다.
- 게이지 최대·Timer max는 5초 표본 한계가 있다. 이번 3회의 Hikari `pendingMax`는 0~0, `activeMax`는 0~7이고 5초 표본이라 순간 포화를 놓쳤을 수 있다.
- 로드맵 체크박스는 갱신하지 않았다.
