# M5-2 개선 및 측정 인계 (03) 1,000명 폭주 진단

> 허브: [M5-2 개선 및 측정 인계](../m5-improvements.md) · 이전: [예매 p95 진단과 중간 개선 시도](02-booking-p95-diagnosis.md) · 다음: [1,000명 튜닝 Step A~C와 기준 변경](04-1000-user-steps-a-c.md)

## 1,000명 폭주 구간 JFR 진단

콜드 1,000명·JFR 1회(`20261114-131040-hot-seats`). 예매 폭주는 13:12:04~07의 약 3초이며 `booking_create` p50 1,320ms·p95 1,673ms·최소 616ms였다. 중복 판매 0건. Prometheus 5초 표본이 이 구간을 놓쳐서 JFR의 1초 `CPULoad`와 실행 샘플로 확인했다. n=1이다.

| 관측 | 폭주 구간 값 |
| --- | --- |
| 호스트 CPU(`machineTotal`) | 최대 0.85 (평시 0.2~0.3) |
| core JVM 사용자 CPU | 최대 0.49(16코어 중 약 8코어) |
| Gateway JVM 사용자 CPU | 최대 0.19~0.40 구간이 3~5초 지속 |
| GC pause, safepoint | 구간 안 0건, 무시할 수준 |
| JIT 컴파일 | core 10건 합 2.05초·최장 439ms, Gateway 11건 합 2.24초·최장 507ms |
| core 실행 샘플(454건) | 한 곳에 몰리지 않고 jOOQ·Jackson·Spring MVC·리플렉션에 분산. `tomcat-handler` 가상 스레드 74% |
| Hikari 풀 | `pendingMax` 0, 타임아웃 0 |

- **병목은 대기가 아니라 CPU 포화다.** 호스트 한 대에서 k6(4코어)·Gateway·core가 같은 순간에 약 3초 동안 CPU를 쓴다. DB·Redis·풀은 비어 있다(이전 절과 일치). 요청 수천 건이 한꺼번에 도착해 각 요청의 CPU 작업이 직렬화된다.
- 단일 단계 하나가 느린 것이 아니라 core 단계(`existing`·`hold`·`persist`)가 모두 p50은 수십 ms인데 p95가 약 300ms로 늘어나는 모양이다. CPU 경합 때문에 모든 단계가 같이 늘어난다는 해석과 맞는다.
- JIT 컴파일 스레드가 폭주 구간에 합 2초 넘게 CPU를 쓴다. 워밍업을 해도 p95가 안 줄었으므로 JIT는 주원인으로 확정하지 못한다. (정정: 이 판정은 1회 워밍업 기준이었다. [04 문서](04-1000-user-steps-a-c.md)의 Step A 참고)
- 확인하지 못한 것: k6가 사용하는 코어를 줄이거나 앱 코어를 늘린 대조(자원 배분이 다른 값은 서버 개선율로 쓰지 않는다), 요청당 CPU 시간(core 약 8코어·약 1초 ÷ 약 1,000요청 = 요청당 수 ms 이상으로 보이나 정밀 계측은 안 했다).

## 코어 배분 대조 (1,000명, 조건당 3회)

콜드 1,000명 `hot-seats`, `--no-scouter --observability`. 호스트 16코어. 예매 시도 인원은 986~1,000명, `http_req_failed` 0, 정합성 모두 통과. 자원 배분이 다른 값이므로 서버 개선율로 쓰지 않는다. 같은 호스트에서 코어 배분이 폭주 지연에 주는 영향을 보는 진단이다.

| k6 코어 / 앱 코어 | 예매 p95 ms (실행 1·2·3) | 예매 p50 ms (실행 1·2·3) | 실행 디렉터리 |
| --- | --- | --- | --- |
| 4 / 12 (기준) | 1,688 · 1,575 · 1,766 | 1,282 · 1,146 · 1,345 | `20261114-131726` |
| 2 / 14 | 1,645 · 1,596 · 1,457 | 1,157 · 1,279 · 876 | `20261114-132241` |
| 8 / 8 | 2,435 · 2,122 · 2,032 | 1,954 · 1,620 · 1,608 | `20261114-132759` |

- **앱 코어가 줄면 지연이 뚜렷하게 늘고(p95 약 1.7초 → 약 2.2초), k6 코어가 줄어도 변하지 않는다.** 폭주 지연은 k6 발생기가 아니라 앱(core·Gateway) CPU에 묶여 있다는 앞 절의 해석과 맞는다.
- 앱 코어를 12에서 14로 늘린 효과는 p95 기준으로 방향만 보이고(기준 1,575~1,766 대 1,457~1,645) 구간이 겹쳐 확정하지 못한다.
- 코어 12개를 써도 p95 300ms 근처에 가지 못한다. 코어를 늘리는 것으로는 목표에 닿지 않는다. 요청당 CPU를 줄이거나, 동시 도착 기준을 분리해야 한다.

## Gateway Observation·context propagation 대조 (1,000명, 조건당 3회)

JFR(`20261114-131040`)의 Gateway 폭주 구간 실행 샘플 823건 중 약 25%(209건)가 `SimpleObservation`·`DefaultContextSnapshot.setThreadLocalsFrom`·`TracingObservationHandler`를 지나갔다(스택 깊이 40 제한). `spring.reactor.context-propagation: auto` 때문으로 보고, 설정 파일은 바꾸지 않고 환경 변수로만 대조했다. 코어 배분은 기준(4/12)이다.

| 조건 | 예매 p95 ms (실행 1·2·3) | 실행 디렉터리 |
| --- | --- | --- |
| 기준(`auto`, 관측 스택 켬) | 1,688 · 1,575 · 1,766 | `20261114-131726` |
| `SPRING_REACTOR_CONTEXT_PROPAGATION=limited`, 관측 스택 켬 | 1,975 · 1,793 · 1,650 | `20261114-133515` |
| 관측 스택 끔(`--observability` 없음) | 1,751 · 1,912 · 1,769 | `20261114-134032` |

- **개선 없음.** 두 조건 모두 기준과 구간이 겹치거나 오히려 높다. CPU 샘플에서 25%를 차지해도 이를 줄인 것이 폭주 p95로 이어지지 않았다. 샘플 비중이 지연 몫과 같지 않다는 뜻이다.
- 따라서 trace 전파 설정은 바꾸지 않는다. 설계(관측·추적)를 건드릴 이유가 없다.
- 지금까지 CPU 포화는 확인했지만 한 곳에 몰린 핫스팟은 없고(core는 jOOQ·Jackson·MVC에 분산, Gateway는 Netty·Lettuce·Observation에 분산), 한 가지를 줄여서는 p95가 눈에 띄게 움직이지 않는다.

## 입장 배치 규모(50명) 기준 측정 (조건당 3회)

[기준 분리](../../plans/m5-2-improvements.md)에 따라 300ms 기준을 판정하는 조건이다. `hot-seats --vus 50 --observability --no-scouter`, 코어 배분 4/12, 예매 시도 인원 49~50명, `http_req_failed` 0, 정합성 모두 통과.

| 조건 | 예매 p95 ms (실행 1·2·3) | 예매 p50 ms | 실행 디렉터리 |
| --- | --- | --- | --- |
| 콜드 | 247 · 305 · 258 | 222 · 290 · 237 | `20261114-134746` |
| 워밍업 후 | 119 · 140 · 144 | 86 · 102 · 111 | `20261114-135254` |

- **워밍업 후는 3회 모두 p95 300ms 미만이다(119~144ms).**
- **콜드는 3회 중 2회가 300ms 미만이고 1회(305ms)가 넘는다.** 중앙값은 258ms지만 최댓값이 기준을 넘으므로 콜드 달성으로 판정하지 않는다. 콜드 스타트(클래스 로딩)가 p50의 절반 이상을 차지한다는 [02 문서](02-booking-p95-diagnosis.md)의 50명 분해 결과와 같은 방향이다.
- k6 threshold 미달 2건 중 콜드 2회(305ms)는 p95 기준 때문이다. 워밍업 2회는 p95가 아니라 `sse_connect_success`(50건 중 1건 실패, 0.98) 미달이다. 예매 지연과는 무관한 SSE 연결 쪽 문제이며 원인은 확인하지 못했다. SSE 연결 성공률 기준(> 99.9%)은 이 조건에서도 달성 여부를 따로 확인해야 한다.
