## Step 6: Gateway 지연 분석 (2026-11-14, 코드·설정 변경 없음)

### 결론

콜드 A 10,000 VU의 티켓 발급 지연(k6 p95 2.6~5.2초)은 **Gateway·core 구간에서 생기지 않았다.** 같은 요청의 서버 측 `POST /api/v1/sse-tickets`(core) p95는 39~63ms, Gateway `core-api` route p95는 1.4~4.0ms, Gateway 연결 풀 pending은 0이다. 지연은 k6 관측값에서만 나타나며 k6가 4코어 전부(최대 3.99코어)를 쓰는 구간과 겹친다. 다만 k6 코어를 6개로 늘린 진단에서도 k6가 5.85/6코어까지 포화해 지연이 사라지지 않았으므로 **발생기 포화가 원인이라고 확정하지 못한다**(한계). Gateway 500은 이번 실행에서 **재현되지 않았다**. 근거 없는 연결 설정·힙 변경은 하지 않았다(변경 0건, 공통 구현 검증은 코드 변경이 없어 생략, 문서 검사만). 로드맵 체크박스는 갱신하지 않았다.

### 측정 조건과 Scouter 불일치

이 step의 모든 측정은 **Scouter 없이**(`--no-scouter`, 각 실행 `env.txt`에 `scouter: 비활성` 확인) 현재 코드(HEAD `aa928aa`)로 실행했다. Step 2·3·5의 결과 문서와 일부 `env.txt`는 `scouter: 활성`으로 기록돼 있다. 따라서 Step 2의 콜드 A 값은 기준으로 가져오지 않았고 Scouter 활성 계열과 비활성 계열을 섞어 개선율을 계산하지 않는다. 그 외(코어 k6 0-3·앱 4-15, 힙 core 2g·realtime 1g·gateway 1g, 추적 0.1, scrape 5초, 앱 매번 새로 기동, 워밍업 없음, 10,000명·5,000석·입장 배치 50)는 기존값이다. 변경이 없으므로 전후 비교는 없고 이 3회가 현재 코드의 콜드 A 기준이다.

route 타이머는 필터·라우팅·업스트림 응답 시간을 포함하며 SSE route(`realtime-streams`)에는 스트림 유지 시간이 들어가므로 API 지연으로 해석하지 않았다(티켓 발급은 `core-api`이며 SSE 시간은 위 표에서 제외). 서버 p95 합산(수십 ms)과 k6 p95(2.6~5.2초) 사이의 2~3자릿수 차이는 서버 구간 밖에서 생긴다. k6 CPU 포화 구간은 실행 시작 0~4초와 15~29초 등이고(1회차 `resources.csv`), 이는 10,000 VU가 한꺼번에 등록·SSE를 시작하는 폭주 구간이다. **한계: k6는 요청별 시계열을 남기지 않아 지연 급증 시각과 CPU 포화 시각을 초 단위로 겹쳐 보지 못했다.** 포화 시각과의 일치는 실행 단위 집계에서의 정황 근거다. `http_req_blocked`(연결 수립 대기)가 크므로 k6 측 연결·스케줄링 대기가 지연의 큰 부분일 가능성이 높지만 k6 내부 구간은 분해하지 못했다.

### 작업 2. `PrematureCloseException`·IOException 확인

- 현재 설정은 `spring.cloud.gateway.server.webflux.httpclient.pool.max-idle-time: 20s`(c7c50eb, 코어 Tomcat keep-alive 약 60초보다 짧게)다. 이 커밋 이후(2026-11-13 22:11 이후) 저장된 콜드 A `gateway.log` 34개를 실행 구간(k6 시작~종료) 안에서 세었다. 구간 안에서 `PrematureCloseException`·500이 있던 실행은 11월 13일 23:09~11월 14일 00:34의 10개 실행뿐이다. 이들은 당시 Scouter 에이전트의 `InaccessibleObjectException`이 동반된 Gateway 계측 오류 구간(커밋 `e91094b` "gateway 스카우터 오류 수정" 전후)이거나, 마지막 실행(`20261114-002920-queue-surge/1`, k6 종료 코드 130)처럼 realtime `OutOfMemoryError: Java heap space`로 SSE 연결이 끊긴 실행이다. 그 실행 이후의 콜드 A 실행 구간에는 0건이다(디렉터리 기준 22개, 이번 3회 포함, 중단 실행은 일부 제외).
- 경계 밖 발생: `20261114-035645-queue-surge/3`의 `POST /api/v1/sse-tickets` 500(`연결이 거부됨 localhost:18080`)은 k6 시작(04:08:20) 전인 04:08:13, core가 기동 중이던 때 발생했다(부하 중 아님). `20261114-194258-queue-surge/1`의 `GET /api/v1/streams/...` `PrematureCloseException DURING response`는 k6 종료(19:50:41) 뒤 graceful shutdown이 30초 만에 중단된 19:51:29 시점이다. 이들은 종료·기동 중 아티팩트로 분류했다.
- 이번 3회의 Gateway 경고는 `NativeIoException: recvAddress failed -104(상대편이 연결을 끊음)` 7~12건(후행 `post termination`)으로 k6가 연결을 먼저 끊은 흔적이며 응답 오류는 아니다(`http_req_failed` 0).
- 따라서 **현재 설정에서 Gateway 500·`PrematureCloseException`은 재현되지 않았고**(OOM 실행 이후 콜드 A 약 22회, 구간 내 0건) idle·연결 설정을 바꿀 증거가 없어 바꾸지 않았다. SSE route에 짧은 response timeout은 적용하지 않았다. 해결을 단정하지는 않는다(과거 오류는 max-idle-time 적용과 계측 수정·OOM 해소가 섞여 있어 어느 쪽이 얼마나 기여했는지 이 step에서 분리하지 못했다).

### 작업 3. 발생기·호스트 진단 (진단 각 1회, 서버 개선율에 쓰지 않음, 모두 `scouter: 비활성`)

| 진단 | 실행 | 조건 | k6 CPU 최대 | 티켓 k6 p50/p95/max ms | core 서버 티켓 p95 ms | Gateway pending | 비고 |
|---|---|---|---|---|---|---|---|
| 기준과 동일 조건 | `20261114-203947-queue-surge/1` | k6 0-3·앱 4-15 | 3.99/4 | 1,804 / 5,311 / 6,870 | 63.4 | 0 | 입장 10,000, 정합성 통과, `http_req_blocked` p95 1,291ms |
| k6 6코어 | `20261114-202303-queue-surge/1` | k6 0-5·앱 6-15(앱 10코어) | 5.85/6 (5코어 이상이던 초 9) | 1,308 / 4,600 / 6,312 | 139.7 | 0 | 15분 실행 상한에서 1 VU 중단(아래), 정합성 통과 |

- 코어 배분을 바꾼 값은 앱 코어도 12 → 10으로 달라져 서버 개선율로 쓰지 않는다. 결과: 티켓 지연은 사라지지 않았고(p95 4.6초) k6가 6코어에서도 포화(5.85/6)했다. 앱 코어 수가 줄어 core 티켓 p95가 63 → 140ms로 늘었으나 k6 관측값 대비 여전히 1/30 수준이다. 이 진단만으로 "k6 포화가 원인"을 입증하지 못한다. 더 큰 발생기 자원(예: 8코어 이상 별도 호스트)이 필요하며 이 환경에서는 비교하지 못했다.
- **호스트 TCP accept 큐 확인**(기준과 동일 조건 진단 1회): `nstat` 차분으로 `TcpExtListenOverflows` +0, `TcpExtListenDrops` +0, `TcpExtTCPSynRetrans` +64(실행 전 138,165 → 후 138,229; 부팅 이후 누적 ListenOverflows 223,366은 이전 실행의 값). 18000 listen 큐 넘침은 일어나지 않았다. `http_req_blocked`가 1초에 가까운 SYN 재전송 시그니처는 아니다(포트 범위 32768~60999, somaxconn 4096, 호스트 전체 카운터라 k6·앱 구분 불가).
- Gateway 힙·GC: GC pause 합 1.77~1.93초(구간 약 260초, 약 0.7%), pending 0, CPU 0.32코어 이하라 지연과 연결되지 않아 **힙 단독 변경 비교는 하지 않았다**(작업 3의 조건 불충족).
- 1 VU 미완료(`20261114-202303-queue-surge/1`, k6 6코어 진단): k6는 입장 9,999명으로 집계했고 15분 상한에서 1개 반복이 중단됐다. 같은 실행의 realtime 지표는 `gateway_ready` 10,000·`lookup_created` 10,000으로 서버는 전원을 입장시켰다. 다른 기준 3회·진단 1회는 10,000 전원 입장이므로 발생기 쪽 누락으로 보이나 **원인은 확인하지 못했고 1회 관측**이다. 정합성(5,000석 확정·중복 0·Redis 일치)은 통과했다.

### 작업 4. 채택한 변경

없음. 변경 후 비교 대상이 없으므로 콜드 A 전후 비교와 연결 풀 계측 한계는 다음과 같다. Gateway 연결 풀 지표(`reactor_netty_connection_provider_*`)는 5초 scrape 표본이라 폭주 순간의 pending을 놓칠 수 있다(pending 0은 5초 표본 기준). `pendingTimeBuckets`의 ERROR 상태 버킷도 요약 값은 0이다.

### 한계와 다음 가설

- 지연 위치는 "서버 구간 밖(발생기·호스트 측)"까지만 좁혔고 k6 내부(Go 런타임 스케줄링, 10,000 VU·SSE 10GB RSS, 연결 수립 대기)는 분해하지 못했다.
- 가설 1: 별도 발생기 호스트 또는 VU 수를 나눈 두 k6 프로세스로 같은 앱 설정에서 티켓 지연이 줄면 발생기 포화로 확정한다(설계 변경 없음, 환경 변경이므로 별도 계열).
- 가설 2: k6 `--out json`이나 per-name Trend를 실행 후 시간대별로 저장해 지연 급증 시각을 `resources.csv`와 초 단위로 겹쳐 본다(runner 변경이므로 합의 후).
- Gateway 500 재현을 다시 확인하려면 다중 실행이 필요하다. 이번 약 22회 미재현은 해결의 증거가 아니다.
- 중단된 실행(비교 제외): `20261114-195528-smoke`, `20261114-195605-queue-surge`, `20261114-195819-queue-surge`(이전 에이전트 중단 잔여물, 삭제하지 않음). 이번 Step 6의 재실행은 없고 진단 2회는 모두 완료했다.
- 이 step의 실행: 콜드 A `20261114-200042-queue-surge/1~3`, 진단 `20261114-202303-queue-surge/1`(k6 6코어), `20261114-203947-queue-surge/1`(nstat). fake-pg 컨테이너는 측정 뒤 `docker start`로 복구했다.
