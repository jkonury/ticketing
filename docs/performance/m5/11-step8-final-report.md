## Step 8: 최종 측정과 M5 결과 보고서 (2026-11-14)

### 결론

- **채택된 개선은 대기열·입장 구간의 오류 제거와 도달 인원 복구다.** A의 예상 밖 오류율은 M5-1 7.65%(입장 약 7,000명)에서 최종 0%(전원 10,000명 입장)로, B의 정시 준비는 M5-1·관측 보강 단계의 30~441명에서 최종 1,000/1,000으로 올랐다. 이 개선은 Step 2 전후 같은 조건 3회(A 전 3회 모두 404·`removed`·결과 없이 종료 발생 → 후 0건)로 확인했다.
- **B 예매 생성 p95의 잠정 기준 300ms는 해결하지 못했다.** 현재 HEAD·Scouter 비활성 콜드 B 중앙값은 1,385.3ms(3회 모두 미달), 워밍업 B(5회 예열)는 383.3ms(3회 모두 미달)다. 임시 기준 1,500ms는 콜드·워밍업 모두 통과한다(로드맵 완료 기준과 무관한 임시값).
- 좌석 중복 판매는 이번 실행 전부(콜드 A·B 6회, 워밍업 B 3회, JFR 2회)에서 0건, DB·Redis 불일치 0건이다.
- Virtual Thread pinning은 **정상 상태에서 0건**이고 모두 첫 예매 폭주 구간의 클래스 로딩·초기화다. 커넥션 풀은 A에서 병목이 아니고 B 콜드에서만 대기가 크며 풀 증설(Step 5)로는 개선되지 않았다. 확신도: pinning 결론 높음(JFR 3종 모두 일치, 이벤트 시각까지 확인), 풀 결론 중간(5초 표본·1회 JFR 한계), B 지연의 근본 원인은 CPU 포화와 콜드 초기화 가능성이 높지만 **원인 확정에 이르지 못했다**.
- 설계 변경 필요 없음. 이 step에서 서버 코드·설정·Scouter 파일은 바꾸지 않았다(측정과 문서만).

B 콜드의 폭주는 3초 안에 끝나는 콜드 구간이라 "정상 상태"가 따로 없고(마지막 이벤트 +63.7s, 실행 종료 약 +65s) B의 첫 요청 지연과 클래스 로딩 pinning이 겹친다는 사실만 확인했다. 이 pinning이 B 콜드 p95 1,385ms의 얼마를 차지하는지는 JFR만으로 분리하지 못했다(Step 5의 usage 증가·인터프리터 가설과 일치하는 정황이다). Prometheus `jvm.threads.virtual` 지표도 A 3회 core `pinnedEvents` 0·9(최장 27.0ms)·0, B 3회 0·0·0, 워밍업 B 3회 `pinnedMaxSeconds` 0·`submitFailed` 0(워밍업 실행은 누적 이벤트 수를 지표에서 제거)으로 모순이 없다. M5-1 JFR(core 755건·최장 59.7ms, 합 약 0.84초)과 같은 모양이다(건수·합계는 이번이 더 큼: A core 695건·합 1.29초, 계측 보강과 클래스패스 차이 영향 가능, 원인 미확인).
