# M5-2 개선 및 측정 인계 (04) 1,000명 튜닝 Step A~C와 기준 변경

## Step A. 예열 횟수별 상한 진단 (1,000명, 각 1회, 2026-11-14)

계획 [hot-seats 1,000명 p95 300ms 도달 계획](../../plans/docs-performance-m5-improvements-md-hot-recursive-lighthouse.md)의 Step A. 코드 변경 없이 `run.sh --warmup --warmup-rounds N`(같은 앱에 부하 N회 뒤 새 회차로 측정)만 다르게 했다. `hot-seats --observability --no-scouter`, 코어 4/12, 풀 10. 모든 실행에서 정시 준비 1,000명, `http_req_failed` 0, 정합성 통과. n=1이므로 방향만 본다.

| 예열 횟수 | 측정 p50 | 측정 p95 | 측정 최소 | 실행 디렉터리 |
| --- | --- | --- | --- | --- |
| 5 | 373 | 496 | 96 | `20261114-142338-hot-seats/1` |
| 15 | 189 | 274 | 44 | `20261114-143052-hot-seats/1` |
| 15 (`--jfr`) | 272 | 358 | 54 | `20261114-144838-hot-seats/1` |

회차별 추이(p50 / p95 / 최소, ms):

| 회차 | 5회 실행 | 15회 실행 |
| --- | --- | --- |
| 1 | 1,286 / 1,718 / 523 | 1,750 / 2,352 / 712 |
| 2 | 728 / 1,158 / 89 | 822 / 1,095 / 69 |
| 3 | 541 / 749 / 181 | 521 / 727 / 90 |
| 4 | 416 / 541 / 57 | 501 / 1,188 / 74 |
| 5 | 453 / 582 / 55 | 442 / 1,233 / 67 |
| 6~9 | | 300·310·451·299 / 1,278·501·611·1,265 |
| 10~14 | | 204~249 / 282~344 |
| 15 | | 222 / 1,242 / 51 |
| 측정 | 373 / 496 / 96 | 189 / 274 / 44 |

- **충분히 예열하면 300ms 근처에 닿는다.** 15회 예열 후 측정 p95는 274ms(JFR 켠 실행은 358ms)다. p50은 1,200ms대에서 189ms로 내려간다. 서버 로직 자체는 1,000명을 300ms 안에 처리할 수 있고, 콜드 상태의 코드 실행 비용이 p95를 끌어올리는 쪽이라는 해석과 맞는다.
- **수렴이 느리고 불안정하다.** 5회로는 부족하고(496ms), 10~14회차에야 p95가 280~340ms대로 내려온다. 같은 구간에서 6·9·15회차는 p95가 1,2xx ms로 튀었다. 원인은 확인하지 못했다(JIT 재컴파일·GC 후보이나 JFR을 켜지 않은 회차라 검증 못 함). 따라서 15회 실행의 274ms도 1회 값이며 안정적 달성으로 판정하지 않는다.
- **JFR로 확인한 인터프리터 비율.** 15회 예열 후 측정 구간의 core 실행 샘플은 폭주 구간(15:05:50~51) 98건 중 최상위 프레임이 Interpreted인 것이 0건이다. 콜드 실행(`20261114-131040`)은 폭주 1초 281건 중 164건(58%)이었다. 예열이 실행 코드를 컴파일된 상태로 바꿔 놓는다는 근거다.
- **판단**: 예열 상태 p95가 300ms 근처로 내려가므로 계획대로 Step B(패자 경로 DB 조회 줄이기)와 Step C(AOT 캐시)로 진행한다. 15회 예열은 학습 횟수 후보로 쓰되, 안정 구간은 10회 이상이다.
- [03 문서](03-1000-user-diagnosis.md)의 "워밍업을 해도 p95가 안 줄었으므로 JIT는 주원인으로 확정하지 못한다"와 [02 문서](02-booking-p95-diagnosis.md)의 "콜드 스타트는 주원인 아님" 결론은 1회 워밍업 기준이었다. 위 수치는 콜드 스타트(인터프리터 실행)가 p95의 큰 몫임을 보여 주므로 이 결론을 정정한다.
- `run.sh --warmup-rounds N`을 추가했다(기본 1, 회차별 `warmup-k6-summary-<n>.json`, `env.txt`의 `warmup-rounds`). 실행 중 포트 18090이 compose의 `fake-pg` 컨테이너와 겹쳐 컨테이너를 멈추고 측정했다.

## Step B. 패자 경로 멱등 조회 제거 (1,000명 콜드 3회)

`CreateBookingService.create()`의 진입 시 `existing` 조회를 없앴다. 순서는 `find-copies → hold → (선점 실패 시 기존 예매 ?: 409) → persist`이고, 좌석이 풀린 뒤의 재호출은 `persist`의 `(member_id, idempotency_key)` 유니크 위반이 기존 예매를 돌려준다. 신규 요청당 멱등 DB 조회가 2회에서 패자 1회·승자 0회가 됐다. 단계별 `Timer`도 호출마다 생성하지 않고 필드로 둔다(`existing` 단계 태그는 사라진다). 만료·취소된 예매의 키로 재호출하면 좌석이 잠깐 선점됐다 풀리지만 응답(200, 기존 예매)은 같다.

`hot-seats --runs 3 --observability --no-scouter`, 콜드, 코어 4/12, 풀 10. 정시 준비 1,000명, `http_req_failed` 0, 정합성 통과.

| 조건 | 예매 p95 ms (1·2·3) | 예매 p50 ms | 실행 디렉터리 |
| --- | --- | --- | --- |
| 기준(변경 전) | 1,688 · 1,575 · 1,766 | | `20261114-131726` |
| Step B | 1,158 · 1,255 · 1,415 | 801 · 1,007 · 968 | `20261114-151242` |

- p95가 3회 모두 내려갔다(평균 약 1,676 → 1,276ms, 약 24% 감소). 기준은 같은 날 앞선 실행이며 코드 변경 직전에 다시 재지는 않았다.
- 300ms와는 여전히 4배 이상 차이가 난다. 콜드 상태 코드 실행 비용이 남은 주원인이라는 Step A 결과에 따라 Step C(AOT 캐시)로 간다.

## Step C. AOT 캐시 기동 (콜드 3회)

`run.sh --aot-cache`: core·gateway·realtime을 `java -Djarmode=tools -jar <jar> extract`로 풀고, 학습 기동(`-XX:AOTCacheOutput`, hot-seats 부하 15회)에서 SIGTERM 종료 시 캐시를 쓴 뒤, 측정 기동마다 새 프로세스를 `-XX:AOTCache -XX:AOTMode=on`으로 띄운다(캐시를 못 쓰면 기동 실패). 워밍업 요청은 없다. 캐시 크기는 core 약 254MB·gateway 약 128MB·realtime 약 118MB이고 `env.txt`에 기록한다. 학습과 측정은 같은 힙·CPU·에이전트 옵션이다. 결정은 [ADR 0026](../../adr/0026-aot-cache-startup.md), 절차는 [런북](../loadtest-runbook.md)에 있다.

| 조건 | 예매 p95 ms (1·2·3) | 예매 p50 ms | 실행 디렉터리 |
| --- | --- | --- | --- |
| 1,000명, Step B(AOT 없음) | 1,158 · 1,255 · 1,415 | 801 · 1,007 · 968 | `20261114-151242` |
| 1,000명, Step B + AOT | 1,167 · 861 · 1,094 | 747 · 603 · 802 | `20261114-152333` |
| 50명, AOT 없음(Step B 이전) | 247 · 305 · 258 | 222 · 290 · 237 | `20261114-134746` |
| 50명, AOT | 141 · 199 · 215 | | `20261114-160313` |

정시 준비 1,000명(1,000명 조건), `http_req_failed` 0, 정합성 통과.

- **1,000명은 AOT로 300ms에 닿지 않는다.** 평균 p95가 약 1,276 → 1,041ms로 줄었지만 3회 모두 800ms 이상이고, 1·3회는 Step B와 차이가 작아 n=3으로 효과를 확정하기 어렵다.
- **JFR(`20261114-154503/1`, 1회)으로 본 폭주 구간 Interpreted 비율은 줄지 않았다.** core 최다 샘플 1초(230건) 중 135건(59%), 다음 1초(89건) 중 56건(63%)이 Interpreted다. 콜드 실행의 58%와 같은 수준이다. 원인은 확인하지 않았지만, 캐시를 써도 이 경로의 코드가 인터프리터에서 시작한다는 뜻이다. `VirtualThreadPinned`는 50건이고 `loadClass` 프레임은 매칭되지 않았지만, AOT 없는 JFR 실행과는 비교하지 않았다.
- **50명은 3회 모두 300ms 미만이다(141·199·215ms).** 이전 콜드 247·305·258ms에서 모두 내려갔다. 입장 배치 규모(50명) 콜드 기준은 AOT 캐시 기동 조건에서 달성한다. AOT 없는 콜드는 3회 중 1회(305ms)가 기준을 넘었다.
- 판정: 1,000명 조건은 AOT 캐시를 써도 미달이다. 기준 분리를 유지한다. 15회 예열 상태 274ms(Step A)에 닿으려면 JIT된 코드가 필요하고, 이는 Step D 후보(CPU 배분·풀·Gateway Redis 병렬화, 요청당 CPU 계측)를 근거로 좁혀야 한다.

## 1,000명 기준 변경과 마무리 (2026-11-14)

AOT 캐시를 써도 1,000명 p95가 300ms에 닿지 않았다. 폭주 구간 core 샘플의 Interpreted 비율은 AOT(219/363, 60%)와 콜드(253/448, 56%)가 비슷했고, 서로 다른 메서드 약 210~230개에 샘플이 1~3건씩 퍼져 있었다. AOT 캐시는 적용됐으나(core 기동 16.2 → 7.6초) 이 경로가 JIT 전 인터프리터에서 시작하는 것은 그대로다. 원인 분리(C1 임계 미달과 컴파일 대기열 지연)와 JDK 25 AOT 캐시의 범위 확인은 하지 않았다.

- **기준 변경**: 1,000명 콜드(+AOT) 예매 생성 p95를 300ms에서 **1,500ms**로 완화한다. 300ms는 후속 튜닝 목표로 남긴다. `loadtest/lib/options.ts`의 `thresholdsFor`가 VU 100 초과이면 1,500ms, 이하이면 300ms를 적용한다. 50명 조건 300ms는 그대로다.
- **확인 실행**(`20261114-163619-hot-seats/1`, AOT 학습 2회, 1회): p95 1,052ms로 새 p95 threshold 통과. 같은 실행에서 `sse_connect_success`가 0.972(1,000건 중 28건 실패)로 기준(> 0.999)에 미달했고 k6 종료 코드는 99다. 이전 1,000명 실행도 종료 코드 99였으며 p95 외에 SSE 성공률 미달이 섞여 있었는지는 확인하지 못했다. SSE 성공률은 이번 기준 변경 대상이 아니며 미해결로 남긴다.
- **후속 튜닝 후보**(미실행): 컴파일 임계·컴파일 스레드 수 대조, Gateway Redis 왕복 병렬화, core 풀 크기 대조, 요청당 CPU 계측, SSE 연결 실패 원인 확인.
