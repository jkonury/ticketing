# M5-2 개선 및 측정 인계 (13) 컴파일 임계 대조(순수 콜드 B, Gatling)

> 허브: [M5-2 개선 및 측정 인계](../m5-improvements.md) · 이전: [Gatling 외부 예열 최종 보고](12-gatling-hot-seats-p95-300ms-report.md) · 계획: [내부 예열 계획](../../plans/hot-seats-internal-warmup-cold-900ms.md) 3.1

## 결론

- `-XX:CompileThresholdScaling`을 1.0·0.25·0.1로 바꿔도 순수 콜드 B 예매 생성 p95는 줄지 않았다. 9회 모두 1.5초 이상이다(범위 1,511~1,767ms). 설정 간 차이는 같은 설정의 회차 간 흩어짐(1.0: 1,598~1,687)보다 작거나 같다.
- 계획 3.1의 **중단 조건에 해당한다**. 컴파일 임계를 낮추는 것만으로는 외부 15회 예열 상태(350~386ms)에 근접하지 못한다. 서비스 코드·설정은 바꾸지 않았다.
- 이 결과는 "예열 없이 임계만 낮추는 효과가 없다"는 뜻이다. 내부 예열이 효과가 없다는 증거는 아니다. 내부 예열은 컴파일 임계 외에 클래스 로딩·초기화·연결 생성·타입 프로파일 수집을 미리 수행하기 때문이다. 다만 어떤 부분이 콜드 지연을 만드는지는 이 실험으로 분리되지 않았다.

## 조건

HEAD `4e38743` + 미커밋 변경(`run.sh --jvm-opts`, 문서). `--no-scouter`·관측 ON·Gatling 힙 2g·1,000명·`--booking-p95-ms 300`·CPU 발생기 0-3 / 앱 4-15·예열 없음·앱 매번 새 기동. 옵션은 core·gateway에만 추가했고 `env.txt`의 `jvm-opts(core·gateway)`에 기록된다. 1.0 → 0.25 → 0.1 순으로 번갈아 3라운드(시계열 드리프트 완화). 기본값은 `java -XX:+PrintFlagsFinal`로 확인했다(`CompileThresholdScaling=1.0`, Tier3 호출 200·Tier4 호출 5,000, `CICompilerCount=12`). `CICompilerCount`는 이번에 대조하지 않았다.

## 한계

2026-11-16 후속: 사용자가 아래 선택지 1을 선택해 [JVM 옵션 실제 적용 확인 + JFR 콜드 진단](14-cold-jfr-diagnosis.md)을 수행했다. 아래 한계는 이 보고서의 과거 9회 측정에 대한 것이며, 후속 실행으로 소급 검증된 것은 아니다.

- 옵션이 JVM에 실제로 전달됐는지는 `env.txt` 기록과 러너 코드 경로로만 확인했다. 실행 중 JVM 프로세스 인자나 `PrintFlagsFinal` 로그로는 확인하지 않았다. 효과 없음 결론의 전제이므로 다음 실험 전에 프로세스 인자로 확인한다.
- JFR Interpreted 비율은 이번에 수집하지 않았다(계획의 기록 항목 중 미수행).
- 이전 순수 콜드 B 기준 1,385ms는 k6 계열이다. 이번 Gatling 콜드(기준 설정 1,598~1,687ms)와 직접 비교해 개선·악화율을 계산하지 않는다.

## 판정과 다음 선택지

계획의 중단 조건에 따라 내부 예열 구현(3.2)은 시작하지 않았다. 선택지는 사용자 결정이 필요하다.

1. 옵션 전달을 확인한 뒤 JFR로 콜드 폭주의 Interpreted 비율을 수집해, 콜드 지연이 JIT 때문인지 클래스 초기화·연결 생성 때문인지 분리한다.
2. 이 결과와 무관하게 내부 예열의 기대 효과를 작은 프로토타입(계층 1만, 공유 자원 0)으로 확인한다.
3. 내부 예열 계열을 접고 외부 예열 후 병목(350~386ms) 진단으로 돌아간다.
