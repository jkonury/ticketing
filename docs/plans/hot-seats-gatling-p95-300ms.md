# Gatling hot-seats 1,000명 예매 생성 p95 300ms 달성 계획

- 작성일: 2026-11-15
- 상태: 장기 과제로 보류(로드맵 후속 항목). 측정 기반 확장·전용 대시보드 추가 후 사용자 요청으로 중단. 실행 결과·미검증 항목·재개 순서는 [인계 문서](./hot-seats-gatling-handoff.md)를 따른다. 최종 측정은 미완료다.
- 목표: 단일 Gateway·core 구조에서 **15회 예열 후 예매 생성 p95 < 300ms를 독립 실행 5회 모두 달성**한다.
- 실행 도구: Gatling. 기존 k6 결과는 가설의 근거이며 Gatling 개선율의 기준선으로 사용하지 않는다.
- 관련 문서: [로드맵](../roadmap.md), [M5 최종 보고서](../performance/m5/11-step8-final-report.md), [Gatling 실행 안내](../../loadtest/gatling/README.md), [기존 1,000명 진단](../performance/m5/04-1000-user-steps-a-c.md).

## 1. 합의한 범위와 현재 근거

이번에는 예열 완료 후 달성을 우선한다. 콜드 결과는 별도 계열로 기록하고 콜드 300ms 달성을 주장하지 않는다. 단일 인스턴스 구조, API·멱등 계약, Redis 선점과 DB 최종 유니크 제약을 유지한다. Redis 멱등 저장, 인스턴스 증설, MSA·k8s, AOT 적용은 이번 범위에서 제외한다. 설계 변경이 필요하면 먼저 사용자와 합의하고 ADR과 아키텍처를 갱신한다.

| 기존 근거 | 해석과 이번 조치 |
|---|---|
| k6 최종 콜드 B p95 중앙값 1,385ms, 5회 예열 B 383ms | 예열 여부를 분리하고 Gatling 기준선을 새로 측정한다. |
| k6 15회 예열 후 274ms 1회 관측, 예열 중 1초 이상 튐 | 달성 가능성의 단서다. 예열 횟수를 고정하고 좋은 회차를 골라 합격시키지 않는다. |
| 예열 B core p95 107~170ms, Gateway route p95 351~402ms | Gateway·전송·발생기 구간을 우선 분해한다. 서로 다른 요청 집합의 p95 차이를 구간 비용으로 쓰지 않는다. |
| Hikari 풀 20 대조에서 개선 없음 | 풀 10을 유지한다. 새로운 병목 근거 없이 풀을 늘리지 않는다. |
| 패자 요청은 선점 실패 후 DB 멱등 조회 1회 수행 | 이 조회의 비용은 측정하되 제거하거나 Redis로 옮기지 않는다. |

문서 작성 시 호스트의 SMT 형제는 0·8, 1·9, …, 7·15였다. 기존 부하 도구 CPU 0-3과 앱 CPU 4-15는 일부 물리 코어를 공유한다. 물리 코어 경합은 **검증할 가설**이며 원인으로 확정하지 않는다. 실제 실행 전에 CPU 토폴로지를 다시 확인한다.

## 2. 선행 작업: Gatling 측정 기반 확장

현재 `scripts/loadtest/run.sh`는 Gatling의 hot-seats·queue-surge를 지원하지만 Gatling과 `--warmup` 조합은 거부한다. Gatling assertion도 100명 초과에서는 1,500ms다. 아래 작업을 먼저 구현·검증한다. 기존 동작을 지원하는 것으로 가정하고 측정에 들어가지 않는다.

### 2.1 예열과 본 측정 분리

- Gatling에 `--warmup --warmup-rounds N`을 지원한다. 기본 횟수 5는 유지하고 이번 실행에서 15를 명시한다.
- 한 독립 실행은 앱 새 기동 → 같은 앱 JVM에 예열 N회 → 본 측정 1회 → 앱 종료다. Gatling JVM은 회차마다 새로 띄워 현재의 정적 카운터·시드 로딩을 격리한다. 발생기 자체의 예열 정책도 모든 전후 실행에서 동일하게 유지한다.
- 예열·본 측정마다 새 공연 회차와 멱등 키를 사용한다. 예열마다 기존 settle 조건(PENDING 예매 0건, waiting 0·active 정리)과 시간 상한을 재사용하고 본 측정과 회차 ID가 겹치지 않는지 검사한다. DB·Redis 전체 초기화는 하지 않는다.
- 예열의 p95 미달만으로 다음 예열을 막지 않는다. 다만 정시 준비·요청 수·정합성·SSE·예상 밖 오류 기준 미달, 스크립트 예외, settle 실패는 실행을 무효 처리한다. 이전 회차의 미완료 처리가 남은 채 본 측정을 시작하지 않는다.
- 회차별 Gatling 로그·원시 결과·준비 현황·요약·settle 결과를 보관한다. 서버 지표는 예열 전·본 측정 전·후를 수집하고 본 측정은 직전·직후 차분만 사용한다.
- warmup 관련 집계와 통제 입력 검사가 k6 파일명·요약 구조에 묶인 부분을 도구별로 분기한다. 카운터만으로 HTTP 지연이 복원된다고 가정하지 않는다.

### 2.2 300ms 판정과 결과 계약

- 러너에 `--booking-p95-ms N`을 추가하고 Gatling에는 `BOOKING_P95_MS`로 전달한다. 양의 정수만 허용하며 미지정 시 기존 VU별 300/1,500ms 기준을 유지한다. 이번 실행은 항상 300을 명시한다. k6에 이 옵션을 전달하면 미지원 오류로 거부해 묵시적으로 무시하지 않는다.
- `commonAssertions`의 booking_create p95 한도를 전달값으로 선택한다. 전체 실패율·SSE assertion은 유지한다. 선택된 한도를 실행 메타데이터에 남긴다.
- 전체 booking_create의 지연 표본은 기존 요청 이름으로 보존한다. 생성 성공 2xx, 정상 경합 409 `SEAT_ALREADY_HELD`, 429, 기타 오류를 별도 집계한다. 409를 모두 정상 경합으로 분류하지 않는다.
- 응답 결과별 건수와 p50/p95/p99를 기계 판독 가능한 요약에 추가한다. 결과별 지연은 실제 Gatling HTTP 요청의 시작·완료 시간을 사용하고, 세션 준비·pause 시간을 HTTP 지연에 섞지 않는다. 기존 서버 차분 소비자가 사용하는 카운터 구조와 호환되게 확장한다.
- 생성 성공 p95도 별도로 판정한다. 정상 409가 대부분인 전체 p95만으로 생성 성공의 지연을 숨기지 않는다. 표본 0건은 합격이 아니다.
- 현재 러너는 Gatling assertion 미달 종료 코드 2를 기록하고도 전체 종료 코드 0을 반환할 수 있다. 본 측정의 assertion·준비 인원·통제 입력·정합성·성공 응답 지연을 합친 별도 판정 파일을 생성하고, 하나라도 미달·누락이면 최종 실행은 비정상 종료한다. 실패해도 정합성 검증과 로그 보존을 끝낸다.
- 합격 측정의 HTML 리포트는 끄고 원시 결과를 보존한다. 필요하면 측정 종료 후 별도로 생성한다. 콘솔 문구 정규식에만 의존해 최종 판정하지 않는다.

Gatling의 응답 시간·assertion·원시 결과와 응답별 계측 API는 구현 시 저장소 버전에 맞는 [공식 문서](https://docs.gatling.io/)로 확인한다. k6와 지연 정의가 같다고 가정하거나 두 도구 수치로 개선율을 계산하지 않는다.

## 3. 측정 계약과 실험 순서

### 공통 조건

- HotSeatsSimulation, 1,000명, 전체 5,000석·핫 100석, 기존 1~4석 선택 분포, 충돌 재시도 0회, 60초 공동 시작 대기와 입장 배치 1,000을 유지한다.
- 모든 요청은 Gateway 18000을 경유한다. 생성 성공자는 기존대로 결제 요청·웹훅·확정까지 진행한다. 생성 지연만 재기 위해 후속 처리를 끄지 않는다.
- 기준선·최종 판정은 Scouter 비활성, 관측 활성, 추적 샘플링 0.1, Hikari 10, 앱 힙 core 2g·realtime 1g·gateway 1g·fake-pg 512m, Gatling 힙 2g를 고정한다. 실제 적용값을 메타데이터에서 확인한다.
- Gradle 검사·다른 부하와 병행하지 않는다. 호스트·JDK·Gatling 버전, 코드 revision·dirty diff, 시드, CPU 배치, 예열 횟수, 지표 옵션을 보존한다. 비밀 값은 로그·문서에 넣지 않는다.
- 5초 scrape는 짧은 폭주를 놓칠 수 있다. 누적 히스토그램 차분을 기준으로 쓰고, 고빈도 자원 수집·JFR은 진단 계열로 분리한다.

### 단계별 실행

| 단계 | 고정한 실험 | 다음 단계 조건 |
|---|---|---|
| A. 기준선 | 기존 CPU 배치에서 5회 예열 3회와 15회 예열 3회 | Gatling 기준선·입력 유효성을 확보한다. 5→15 차이는 예열 효과로 기록한다. |
| B. CPU 격리 | 15회 예열, 기존 배치와 SMT 분리 배치를 각각 3회 번갈아 실행 | 총 논리 CPU 수는 유지한다. 후보는 발생기 0,1,8,9 / 앱 2-7,10-15다. |
| C. 병목 진단·수정 | 채택 CPU 배치에서 15회 예열, 한 요소씩 전후 각 3회 | 같은 요청에서 지연 위치를 확인한 뒤 해당 요소만 수정한다. |
| D. 최종 판정 | 최종 코드·설정 고정, 앱 새 기동부터 독립 실행 5회 | 5회 모두 아래 합격 기준을 충족한다. |
| E. 회귀·보고 | queue-surge 3회와 보상 경로 검증 | 경합 개선이 다른 흐름과 정합성을 악화시키지 않았는지 기록한다. |

B와 C에서 후보를 채택하려면 입력·정합성 기준을 모두 만족하고 p95 중앙값이 기준 대비 10% 이상 감소하며 생성 성공 p95 중앙값도 악화되지 않아야 한다. 아니면 기각하거나 진단을 보강한다. 최종 300ms 판정은 상대 개선율과 별개다. 모든 실패 실행은 보존한다. 기준선을 재측정할 때도 코드 외 조건을 동일하게 한다.

CPU 후보의 이득은 물리 코어 배분·경합 변화가 포함된 실행 환경 개선으로 기록한다. 서버 코드 효과는 동일 CPU 배치끼리 비교한다. 다른 호스트에서는 SMT 형제끼리 같은 그룹에 묶는 원칙으로 재배치하고 실제 CPU 번호를 기록한다.

### 병목에 따른 개선 우선순위

1. Gateway의 입장 Redis 조회, 본문 수집·파싱, rate limit, 프록시·연결 획득을 분리한다. 기존 타이머가 중첩된 구간을 확인하고, 지연 요청의 중복 복사·파싱·계측 조회 비용부터 줄인다. 인증·입장 검증 순서와 오류 계약은 유지한다.
2. Gateway 이벤트 루프 대기·연결 획득이 지배적이면 CPU 프로파일과 해당 대기를 근거로 설정 후보 하나를 실험한다. 기존 연결 풀에 문제가 없으면 증설하지 않는다. Redis 검증 호출 병렬화도 검증·차감 순서가 바뀔 수 있으므로 이번 범위에서 미리 구현하지 않는다.
3. core의 find-copies, Redis hold, existing, persist·commit을 구분한다. 패자 조회의 SQL 실행과 연결 획득을 분리하고, 반복 객체 생성·직렬화·예외 응답 처리 중 실제 CPU 비용이 큰 부분을 개선한다. DB 멱등 조회는 유지한다.
4. 결제·웹훅·이벤트 처리와 예매 폭주의 자원 경합을 확인한다. 외부 호출의 트랜잭션 진입·불필요한 연결 점유가 발견되면 기존 설계 규칙 안에서 수정한다.

분산 추적의 같은 요청을 연결해 지연 위치를 판단한다. 요청 ID·trace ID는 메트릭 태그로 넣지 않고 로그·trace에서만 사용한다. 추적만으로 발생기 구간을 설명할 수 없으면 별도 진단에서 한정된 요청의 발송 지연과 호출 경과 시간을 수집한다. JFR·상세 계측 수치는 최종 합격 실행과 섞지 않는다. 새로운 병목 근거 없이 설정 조합을 무작위로 탐색하지 않는다.

## 4. 실행 명령과 합격 기준

### 현재 러너로 가능한 확인 실행

아래 명령은 콜드·기존 1,500ms 기준 확인용이다. 이번 목표의 합격 실행으로 사용하지 않는다.

```bash
./scripts/loadtest/run.sh --scenario hot-seats --tool gatling --runs 1 --observability --no-scouter
```

### 선행 확장 완료 후 사용할 명령

다음 명령은 아직 지원되지 않는 Gatling 예열 조합과 새 옵션을 포함한다. 2절 구현·검증을 먼저 완료해야 한다. `--k6-cpus`는 현재 러너에서 Gatling에도 적용되는 기존 옵션명이다.

```bash
# A: 기존 CPU 배치, 각 실행은 앱 새 기동 + 예열 + 본 측정
./scripts/loadtest/run.sh --scenario hot-seats --tool gatling --gatling-heap 2g --runs 3 --observability --no-scouter --warmup --warmup-rounds 5 --booking-p95-ms 300 --k6-cpus 0-3 --app-cpus 4-15
./scripts/loadtest/run.sh --scenario hot-seats --tool gatling --gatling-heap 2g --runs 3 --observability --no-scouter --warmup --warmup-rounds 15 --booking-p95-ms 300 --k6-cpus 0-3 --app-cpus 4-15

# B: 각 명령 --runs 1로 기존 배치와 분리 배치를 번갈아 실행해 각각 3회 확보
./scripts/loadtest/run.sh --scenario hot-seats --tool gatling --gatling-heap 2g --runs 1 --observability --no-scouter --warmup --warmup-rounds 15 --booking-p95-ms 300 --k6-cpus 0,1,8,9 --app-cpus 2-7,10-15
```

최종 D는 채택한 CPU 배치를 명시하고 동일 명령의 `--runs 5`로 수행한다. 15회 예열로 처음부터 목표를 충족하면 불필요한 서버 변경 없이 최종 반복 검증으로 넘어간다.

**독립 실행 5회 모두 충족해야 할 기준:**

- 등록·입장·정시 준비·예매 시도 각각 1,000명, 지각 0명. 실제 booking_create HTTP 요청도 1,000건이며 예매 생성 429·재시도 0건이다.
- Gatling 예매 생성 요청 수와 Gateway·core 차분 카운터 일치, 차분·격리 검사 유효. 표본 누락·카운터 불일치를 합격 처리하지 않는다.
- 전체 booking_create p95 < 300ms, 생성 성공 2xx p95 < 300ms. 정상 409의 건수·p95도 함께 보고한다.
- 전체 예상 밖 오류율 < 1%, 각 SSE 연결 성공률 > 99.9%. 전체 HTTP 실패율만으로 예매 API 오류를 가리지 않도록 예매 생성의 오류 건수·비율도 별도 보고한다.
- 중복 판매 0건, DB·Redis 불일치 0건, 생성된 예매의 결제·확정 처리 완료. 성공 예매 건수·판매 좌석 수도 보존한다.

최종 보고서는 각 실행의 전체·생성 성공·409 p50/p95/p99와 표본 수, 준비 인원, 오류, 정합성, 선택 설정, 판정, 산출물 경로를 담는다. 회차별 p95의 중앙값은 비교용이며 최종 합격을 대체하지 않는다.

## 5. Scouter ON/OFF 추가 비교

사용자 추가 요청으로 최종 동일 코드·채택 CPU 배치·관측 활성·15회 예열 조건에서 ON/OFF를 각각 최소 3회 교대 실행한다. OFF는 기존 최종 5회 판정과 별도로 비교 표본을 명시하고, ON도 전체·생성 성공 p95 300ms 기준을 동일하게 적용해 미달을 그대로 보고한다. ON은 `--no-scouter`를 빼고 패치 에이전트·모듈별 설정·해시·collector 연결을 실제 확인한다. 예열 횟수·시드 규모·발생기 정책을 고정한다.

기존 콜드 ON/OFF 결과와 섞지 않으며 결과별 지연·요청 수·오류·정합성·CPU·GC·메모리를 함께 문서화한다. 기존 Grafana Overview를 유지하고 [이번 전용 대시보드와 지표 안내](../performance/gatling-hot-seats-dashboard.md)를 사용한다.

## 6. 구현 검증·인계 완료 조건

- 러너: Gatling 예열 횟수, 지원하지 않는 조합·잘못된 한도 거부, 예열/본 측정 격리, settle 실패, 지표 누락, assertion 미달의 최종 비정상 종료를 검증한다. 준비 인원 부족·429·성공 표본 없음도 합격하지 않는지 확인한다.
- 결과 집계: 알려진 지연·응답 분류 표본으로 건수·분위수·판정을 검증한다. Gatling OK에는 정상 경합 409도 포함되므로 OK 집합을 생성 성공 집합으로 사용하지 않는다.
- 서버 변경: 기존 멱등·동시 중복·DB 실패 시 선점 해제·부분 확정 롤백·좌석 유니크 제약 테스트를 유지한다. 모듈 의존 변경 시에만 Modulith 구조 검증·문서 생성을 추가한다.
- 테스트와 검사는 순차 실행한다. 전체 테스트, check, Kotlin 품질 검사, 셸 구문 검사와 변경 흐름 E2E를 실행한다. 부하는 다른 Gradle 작업이 모두 끝난 뒤 단독 실행한다.

```bash
./scripts/agent/test/run-tests.sh
./scripts/agent/test/check-summary.sh
./scripts/agent/test/check-summary.sh ktlintCheck detekt
./scripts/agent/test/run-summary.sh -- bash -n scripts/loadtest/run.sh
./scripts/e2e/run.sh
./scripts/agent/docs/check-docs.sh
```

queue-surge는 Gatling으로 전후 같은 조건 각 3회를 비교한다. seat-conflict-refund는 현재 Gatling Simulation은 있지만 러너가 지원하지 않는다. k6로 대체하지 않고 Gatling 러너의 2단계 실행·원장·환불 검증을 먼저 연결해 기존 보상 기준으로 검증한다. 기존 시드·주입·검증 도구를 재사용하며 시나리오의 업무 계약은 바꾸지 않는다. 이 확장은 서버 변경 후 보상 회귀를 수행하기 전에 완료한다.

결과는 [M5 측정 허브](../performance/m5-improvements.md)에서 연결하는 새 보고서로 남기고 로드맵의 이 계획 항목은 최종 판정 후에만 완료 처리한다. 기존 M5 완료 이력·콜드 미달 사실을 덮어쓰지 않는다. 300ms 미달이면 실패 수치와 근거를 그대로 남긴다. 남은 지배적 병목이 DB 멱등 조회라면 별도 설계 합의를 다음 작업으로 제안하고 이번 범위에서 임의로 구현하지 않는다.
