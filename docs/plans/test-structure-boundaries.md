# fake 대체 경계와 남긴 통합 검증

단위 테스트는 서비스의 판단과 포트에 전달한 값만 검증한다. 실제 저장소·트랜잭션·메시지 전달을 fake가 보장한다고 간주하지 않는다. 직접 대체하기 어려운 부분과 남긴 검증을 이 문서에 기록한다.

## core

| 영역 | 대체의 한계 | 유지한 검증 |
| --- | --- | --- |
| 예매 트랜잭션 | 수기 트랜잭션 매니저는 실제 롤백·격리를 구현하지 않는다. | 단위에서는 커밋 콜백 및 충돌 응답 이후 보상만 검사한다. 좌석 유니크 제약·낙관적 잠금·Redis Lua와 이벤트 재전달은 기존 통합 테스트로 검사한다. |
| 결제 웹훅 | 메모리 fake의 이벤트 ID 집합과 상태는 DB 트랜잭션처럼 함께 롤백되지 않는다. | 계약·중복·재시도 분기는 단위에 추가하고 웹훅 기록·발행 실패의 롤백, 동시성, 멱등 DB 제약은 통합으로 남긴다. |
| 회원 인증 | 빠른 테스트 PasswordEncoder는 실제 해시 비용·보안을 검증하지 않는다. fake는 refresh 행 잠금을 제공하지 않는다. | 로그인·토큰 회전·만료·재사용은 단위, 실제 해시·HTTP 인가·동시 refresh 잠금·폐기 커밋은 통합으로 검사한다. |
| SSE 티켓 발급 | SseTicketService가 구체 StringRedisTemplate에 직접 의존한다. 저장소 fake를 넣으려면 별도의 운영 인터페이스가 필요하다. | 발급은 난수 생성·Redis 저장이 중심이므로 이 범위에서는 별도 추상화를 추가하지 않고 실제 Redis TTL·HTTP 인증 통합 검증을 유지한다. |
| 공연·정산·알림 | fake는 JPA 매핑·캐시 무효화·Modulith 전달·Batch 재실행을 보장하지 않는다. | 등록·소유권·가격·중복·이벤트 내용과 사본 처리 분기는 단위, 매핑·jOOQ 조회·시드·이벤트 전달·Batch는 통합에 유지한다. |

## 통합 테스트의 리스너 mock

Step 4에서는 기존 3개 통합 테스트에 있던 MockitoBean 5개를 유지했다. 이들은 다른 모듈의 비동기 결제·환불·예매 처리를 차단하므로 단순히 제거하면 테스트가 의도하지 않은 PG 호출과 상태 변경을 일으킨다. 리스너는 구체 타입이어서 포트 fake만 주입하는 방식과 다르다. Step 6에서 수기 유스케이스를 사용하는 리스너 대체 또는 공통 fake PG 구성으로 전환하고 실제 전달 검증과 격리 이유를 기록한다.
