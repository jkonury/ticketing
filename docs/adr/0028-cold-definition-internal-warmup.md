# 0028. 부하 측정의 "콜드" 정의: readiness 전 내부 예열 허용

## 상태

수락 (2026-11-16). 측정 판정 조건에 대한 결정이다. 내부 예열 구현은 이 결정에 포함하지 않으며, 별도 계획 문서에서 구현 전에 다시 확인한다.

## 맥락

hot-seats 1,000명 예매 생성 p95 300ms를 현 코드의 콜드(앱 새로 기동, 외부 워밍업 요청 없음)로 재면 1,385ms(3회 모두 미달)다([Step 8](../performance/m5/11-step8-final-report.md)).
외부 요청 15회 예열 후에도 현 코드는 전체 p95 350~386ms로 300ms에 닿지 못했다([Gatling 최종 보고](../performance/m5/12-gatling-hot-seats-p95-300ms-report.md)).
순수 JIT 콜드 상태로 300ms를 달성하는 것은 기존 측정 근거로 현실적이지 않다. 운영에서는 readiness 통과 전에 앱이 스스로 준비하는 방식(k8s readiness gate)이 일반적이다.

## 검토한 대안

- 콜드 정의를 유지하고 300ms를 포기: 목표를 측정할 수 없게 되어 후속 개선의 기준이 사라진다.
- 외부 워밍업 요청을 콜드로 인정: 측정 도구가 예열을 수행해 앱 개선과 구분되지 않는다. 기존 "예열 계열"로 따로 둔다.
- readiness 전 앱 내부 예열을 콜드로 인정(선택).

## 결정

- 성능 측정에서 "콜드"는 앱을 새로 기동한 뒤 **외부 부하 기준으로 워밍업 요청을 보내지 않는 것**이다. readiness가 `ACCEPTING_TRAFFIC`이 되기 전에 앱 내부에서 하는 예열은 허용한다.
- 내부 예열은 기동 시간 상한을 두고, 상한을 넘기면 중단한 채 ready로 전환한다. 예열이 만든 DB 쓰기는 롤백하고 Redis는 예열 전용 네임스페이스·TTL·삭제를 전제한다. 예열 중 DB·Redis 호출 수와 소요 시간은 실행 기록(`env.txt`)에 남긴다.
- 내부 예열을 쓴 계열은 순수 콜드 계열·외부 예열 계열과 **별도 계열**로 기록하고 개선율을 섞어 계산하지 않는다. 순수 콜드 B는 회귀 기준(1,500ms)으로 계속 함께 측정한다.
- 300ms 목표는 달성이 보장되지 않는 조건부 목표다. 비교 기준은 외부 15회 예열 상태(현 코드 350~386ms)이며, 달성 여부는 측정 후 판정한다. 미달이면 결과를 그대로 남긴다.
- 기존 Gatling 외부 예열 계획의 판정 계약(15회 예열 후 독립 5회)은 바꾸지 않는다.

## 결과

- 이 ADR 자체는 코드·설정을 바꾸지 않는다. 내부 예열, JVM 컴파일 임계 조정(`CompileThresholdScaling`) 등은 새 계획 문서에서 다루며, 서비스 동작이 바뀌는 항목은 구현 전에 사용자와 합의한다.
- 예열 중 공유 DB·Redis 쓰기가 판매·정산·SSE에 섞이지 않는지(rollback-only persist, 좌석 상태 이벤트 발행 경로)가 미확인 가정이며 구현 전에 확인한다.
- 기동 시간이 늘어난다. 상한과 ready 전환 정책은 새 계획에서 정한다.
