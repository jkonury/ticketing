# 0025. booking의 불변 좌석 사본 캐시

## 상태

수락 (2026-11-14). 예매 p95 진단 후 사용자가 좌석 사본 캐시 도입을 승인했다.

## 맥락

인기 좌석에 집중한 요청이 같은 좌석의 가격·라벨 사본을 매번 PostgreSQL에서 읽는다.
사본은 회차 등록 이벤트로 한 번 저장하며 기존 회차를 수정하는 기능은 없다.
DB 연결 획득과 조회 비용을 줄이되 DB 원장과 판매 유니크 제약은 유지해야 한다.

## 검토한 대안

- DB 직접 조회 유지: 단순하지만 동일 사본을 반복 조회한다.
- 회차 전체 JSON 캐시: 구현은 단순하지만 최대 4석 요청마다 5,000석을 전송·역직렬화한다.
- 인스턴스 로컬 캐시: Redis 왕복은 없지만 인스턴스마다 초기화되고 메모리 관리가 추가된다.
- Redis Hash에서 요청 좌석만 조회: 기존 Redis를 활용하며 필요한 필드만 전송한다.

## 결정

- booking 어댑터 안에서 `booking:seat-copies:v1:{<scheduleId>}` Hash를 사용한다.
  field는 좌석 ID, value는 타입 정보 없는 JSON(`grade`, `label`, `price`)이다.
- `HMGET`으로 요청 좌석만 읽고 누락·손상된 필드만 booking DB 사본에서 조회한다.
  빈 결과와 없는 좌석은 캐시하지 않는다. 회차 정보 조회는 기존 DB 경로를 유지한다.
- 신규 등록과 DB 조회 결과는 트랜잭션 커밋 이후에만 캐시에 쓴다. 롤백 시 쓰지 않는다.
  트랜잭션 밖에서 읽은 DB 결과는 바로 채운다. 중복 등록 이벤트의 페이로드는 캐시에 쓰지 않는다.
- Lua 한 번으로 필드 쓰기와 TTL 6시간 설정을 원자화한다. 캐시를 채울 때 회차 키 TTL을 갱신하고,
  hit만으로는 TTL을 연장하지 않는다. 기존 필드는 불변이므로 부분 채움과 동시 쓰기가 안전하다.
- Redis 조회·쓰기 오류는 경고를 남기고 DB 조회·DB 원장을 유지한다. 캐시 장애 fallback은
  사본 조회에 한정되며 Redis 좌석 선점 장애까지 우회하지 않는다.
- 판매 가능 상태·선점 소유자·판매 확정은 저장하지 않는다. Redis 선점과 DB 유니크 제약은 기존대로다.
- 향후 회차 사본 수정 기능을 도입할 때는 캐시 무효화·버전 계약을 새로 정한다.

## 결과

반복 좌석 조회에서 DB 접근을 줄일 수 있다. Redis 왕복과 JSON 변환, 만료 직후 동시 miss 비용은 남는다.
캐시만으로 예매 p95 300ms 달성을 보장하지 않으며 동일 조건 부하 측정으로 확인한다.
테스트는 hit·부분 miss·손상·만료·오류 fallback·커밋과 롤백을 검증한다.
