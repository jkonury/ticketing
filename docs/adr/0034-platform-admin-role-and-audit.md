# ADR 0034: 플랫폼 관리자 역할과 audit 모듈

- 상태: 합의
- 작성일: 2026-11-17
- 합의일: 2026-11-17
- 결정 주체: 2026-11-17 M5.5 설계 인터뷰(Q4, Q12)
- 대체: [ADR 0013](0013-jwt-behind-bff.md)의 "플랫폼 관리자는 두지 않는다" 결정을 일부 변경
- 대체됨·일부 변경: 없음
- 관련: [계획](../backup/plans/m5-5-coupon.md), [ADR 0035](0035-coupon-module-reservation-saga.md)

## 배경

쿠폰은 플랫폼이 발행하므로 정의 생성·지급·회수를 하는 플랫폼 관리자가 필요하다. 지금은 USER·ORGANIZER 역할뿐이고, 로드맵의 후속 항목이던 "플랫폼 관리자 역할"을 M5.5에서 앞당긴다. 가입 API는 요청의 `role`을 검증 없이 받으므로, `ADMIN`을 추가하기 전에 가입 시 허용 역할을 제한해야 한다. 그렇지 않으면 누구나 관리자로 가입한다.

## 결정

1. `Role`에 `ADMIN`을 추가한다. 가입 요청의 role은 USER·ORGANIZER만 허용하고 ADMIN은 400으로 거부한다.
2. 최초 관리자는 `.env`의 이메일 값(`ticketing.admin.bootstrap-email`)으로 부트스트랩한다. 해당 이메일로 가입한 회원을 기동 시 ADMIN으로 승격하며, 멱등이다. 회원이 없으면 경고 로그만 남긴다.
3. 이후 승격·강등은 `PUT /api/v1/admin/members/{id}/role`로 한다. 관리자 전용이다. 마지막 ADMIN은 강등할 수 없다(409 `LAST_ADMIN`).
4. 역할을 바꾸면 그 회원의 refresh 토큰을 전부 폐기한다. 기존 access 토큰의 잔여 수명 안에서만 이전 역할이 남는다.
5. 관리자 행위 기록은 새 `audit` 모듈(계층형, 스키마 `audit`)이 맡는다. member가 `MemberRoleChanged`를 발행하고 audit가 구독해 `admin_action`에 적재한다. 원본 이벤트 ID에 유니크 제약을 걸어 재전달을 멱등 처리한다. 쿠폰 관리 이벤트는 M5.5-2에서 같은 방식으로 추가한다.
6. 관리자 영역은 BFF(`/admin` 서버 가드, 서버 액션마다 재검사)와 코어(메서드 권한 검사)에서 이중으로 막는다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| DB에 직접 SQL로 관리자 지정 | 학습·시연 환경에서 재현이 번거롭고, 변경 기록이 남지 않는다. |
| 승격·강등 API 없이 부트스트랩만 | 쿠폰 운영 주체를 늘릴 수 없고 강등·폐기 흐름을 다루지 못한다. |
| 가입 시 role 제한 없이 ADMIN 추가 | 누구나 관리자로 가입할 수 있다. |
| 감사 로그를 member 안에 두기 | 쿠폰 등 다른 모듈의 관리 행위를 담을 수 없어 의존이 member로 몰린다. 이벤트 구독 모듈로 분리하면 모듈 간 호출 규칙(이벤트만)도 지켜진다. |
| BFF 가드만 두기 | BFF를 우회한 직접 호출이 막히지 않는다. 코어가 최종 방어선이다. |
| 역할 변경 후 토큰 폐기 없음 | 강등된 회원이 refresh로 계속 이전 역할을 얻는다. |

## 결과

- 얻는 것: 쿠폰 관리자 흐름과 감사 추적, 권한 상승 경로 차단.
- 감수하는 것: 모듈이 하나(audit) 늘고 스키마·Flyway 마이그레이션이 추가된다. 역할 변경 직후 이미 발급된 access 토큰은 만료까지 유효하다.
- 바뀌는 문서·지침: `docs/architecture.md` 모듈·스키마 목록, `docs/roadmap.md` M5.5-1 (별도 작업에서 갱신).
