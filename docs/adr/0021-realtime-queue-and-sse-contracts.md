## 배경

M3-2에서 realtime은 대기열 API와 입장 스케줄러, 순번·좌석 SSE를 구현한다. 여러 인스턴스가 같은 Redis를 사용하고 연결이 끊겼다 재개될 수 있으므로 순서, 입장 중복 처리, 이탈자 정리, 좌석 변경 재생의 계약을 먼저 정해야 한다. 실시간 앱은 PostgreSQL을 사용하지 않으며 코어와 Gateway의 기존 책임 경계도 유지한다.

이 ADR은 ADR 0008·0009·0014·0020의 결정을 구체화하며 대체하지 않는다.

## 결정

1. 대기 순서는 `INCR queue:seq:{<scheduleId>}`가 반환한 일련번호를 Sorted Set score로 사용해 정한다. 등록은 회차 해시 태그 안의 Lua 한 스크립트(`register.lua`)로 입장 기록 확인·대기 여부 확인·순번 발급·`waiting`·`seen` 기록을 원자적으로 수행하므로 재등록은 순번을 소모하지 않고 기존 순번을 유지한다.
2. 입장은 주기마다 회차별 고정 인원으로 처리하며, 회차별 락을 획득한 인스턴스 하나만 처리한다. 같은 해시 태그를 가진 키만 Lua에서 원자적으로 처리한다. 해시 태그가 없는 `queue:admission:<token>`은 Lua 실행 밖에서 기록한다.
3. 끊긴 대기자는 마지막 신호 시각과 유예 시간으로 정리한다. SSE heartbeat와 상태 조회가 `queue:seen:{<scheduleId>}`를 갱신하고, 스케줄러는 입장 직전에 기본 30초 유예를 넘긴 회원을 대기열에서 제거한다.
4. 좌석 SSE는 인스턴스별·회차별 Redis Stream 리더를 공유하고 스냅샷 ID를 기준으로 재생한다. 스냅샷 이벤트 `id`는 스냅샷 직전 Stream 마지막 ID이며 변경 이벤트 `id`는 Stream entry ID다. `Last-Event-ID`가 Stream에 남아 있으면 그 다음부터 재생하고, 그렇지 않으면 스냅샷부터 보낸다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 인스턴스 시각(epoch ms)을 대기 순서 score로 사용 | 인스턴스 간 시계 차이로 순서가 바뀔 수 있고 같은 밀리초에는 동점이 생긴다. |
| 락 없이 모든 인스턴스가 `ZPOPMIN`으로 입장 처리 | 인스턴스 수만큼 입장 속도가 늘어나 회차별 입장량을 제어할 수 없다. |
| 동시 입장 인원 상한을 두고 입장자의 예매가 끝난 뒤 다음 사람 입장 | 입장자의 완료 여부를 알려면 코어 예매 상태를 알아야 하므로 “코어는 대기열을 모른다”는 경계와 충돌한다. |
| 명시적 이탈 요청만 대기열에서 제거 | 떠난 회원에게 입장 자리가 낭비된다. |
| SSE 연결 종료 즉시 대기열에서 제거 | 순간적인 끊김에도 순번을 잃고, 재연결 때마다 새 SSE 티켓이 필요해진다. |
| 연결마다 블로킹 `XREAD`를 실행 | 공유 Redis 연결이 막힐 수 있고 연결 수만큼 Redis 연결이 필요하다. |
| Redis Pub/Sub로 좌석 변경 전달 | 연결이 끊긴 동안의 변경을 재생할 수 없다. |

## 결과

- 얻는 것: 단조 증가 일련번호로 대기 순서를 일관되게 정하고, 단일 회차 처리자와 Redis 원자 연산으로 입장을 조율한다. 마지막 신호를 기준으로 이탈자를 정리하며 Stream ID로 좌석 변경을 재연결할 수 있다.
- 감수하는 것: Lua 처리와 토큰 기록 사이에 인스턴스가 종료되면 해당 회원은 무효 토큰을 받을 수 있다. Gateway가 `ADMISSION_TOKEN_INVALID`로 대기열에 돌려보내므로 이를 감수한다. 좌석 Stream 리더 상태는 인스턴스 메모리에 있지만 Redis 원본에서 파생되므로 재시작 후 복구할 수 있다.
- 바뀌는 문서·지침: `docs/architecture.md`, `docs/adr/README.md`.
