# 0033. 내부 예열의 요청 지표를 일반 요청과 분리

- 상태: 합의
- 작성일: 2026-11-16
- 합의일: 2026-11-16
- 결정 주체: 사용자 요청 반영. 지표 별도 분리, 지표 우선 적용, fake-pg 포함을 선택했다. 이번 작업은 문서만 작성한다.
- 대체: 없음. ADR 0024의 관측 정책에 내부 예열 분류를 추가한다.
- 대체됨·일부 변경: 없음
- 관련: [ADR 0024](0024-observability-and-load-test.md), [ADR 0032](0032-warmup-traffic-mix.md), [구현 계획](../plans/internal-warmup-metrics-isolation.md)

## 배경

내부 예열은 실제 HTTP·예매·캐시·PG 조회 경로를 실행한다. DB 롤백과 Redis 키 격리로 업무 데이터는 보호하지만 요청 타이머·캐시 카운터는 일반 요청과 같은 시계열에 누적된다. 예열이 끝나도 누적 히스토그램과 카운터는 남고, readiness 이후 수집을 시작하는 것만으로는 대시보드와 누적값 기반 집계의 오염을 막을 수 없다.

예열 성능을 관측하면서도 일반 요청의 건수·지연·오류율·캐시 적중률을 독립적으로 평가해야 한다. 기존 부하 테스트 집계가 지정하지 않은 라벨을 합산하므로 수집 태그와 집계 정책을 함께 결정한다.

## 결정

1. 요청에 귀속 가능한 완료 HTTP 서버·클라이언트 관측, Gateway 라우트·단계 타이머, 예매 생성 단계 타이머와 좌석 캐시 지표를 `traffic=application|warmup`으로 분리한다. realtime의 HTTP 지표에도 기본값 application을 붙인다. 외부 부하 테스트의 예열은 application이며 기존 계열·phase로 구분한다.
2. 기존 자격 검증 결과와 모듈 내부 예열 실행 범위만 분류 근거로 사용한다. 헤더 존재나 음수 ID만으로 요청을 제외하지 않는다. 일반 요청과 위조·만료 자격 요청은 application에 남긴다.
3. fake-pg 수신 지표까지 분리한다. payment의 예열 거래 조회에만 기존 공유 PG 비밀로 서명한 시각·요청 한정 표식을 보내고, fake-pg가 검증한다. 표식 계약과 실패 처리는 구현 계획을 따른다. 분류는 인가와 업무 응답을 바꾸지 않는다.
4. 기본 대시보드와 부하 테스트 결과는 application만 집계하고 warmup·전체 조회를 제공한다. 수집 원본은 유지하며 라벨 없는 과거 데이터는 호환 조회에서 application으로 취급한다. 이미 오염된 과거 데이터는 복원하거나 소급 수정하지 않는다.
5. JVM·GC·커넥션 풀·DB·Redis·진행 중 HTTP 요청 지표는 전체 원본을 유지한다. 앱별 예열 active·종료 시각으로 구간을 표시하며 요청별 비용으로 차감하지 않는다. Tempo·Scouter의 분리 정책은 후속 범위다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 예열 지표 수집 제외 | 예열의 호출량·지연·오류를 별도로 확인할 수 없다. |
| readiness 이후 scrape 시작 | 앱 내부에 이미 누적된 카운터·히스토그램은 남는다. |
| 예열 종료 후 registry 초기화 | 일반 요청과 겹치면 정상 데이터도 잃고, counter reset과 meter 참조 문제가 생긴다. |
| 대시보드의 시간 범위만 변경 | 누적값 조회와 집계 스크립트는 계속 영향을 받으며 예열과 일반 요청이 겹친 경우도 분리하지 못한다. |
| 기동 중 모든 요청을 예열로 분류 | 실제 요청·관리 요청·인증 실패를 예열로 숨길 수 있다. |
| 모든 자원 지표에 요청 태그 부여 | 공유 자원 비용을 개별 요청에 정확히 귀속할 수 없다. |

## 결과

- 얻는 것: 실제 경로 예열과 지표 수집을 유지하면서 일반 요청의 결과를 독립적으로 평가한다. fake-pg와 부하 테스트 집계에서도 동일한 분류를 사용한다.
- 감수하는 것: 대상 meter의 태그 조합 수가 늘고 조회·집계·과거 데이터 호환 처리가 필요하다. 공유 자원에는 예열 비용이 남는다. fake-pg 표식은 유효기간 내 재사용이 가능하며 실제 PG 도입 시 재검토해야 한다.
- 바뀌는 문서·지침: 아키텍처의 관측 정책, 로드맵의 미완료 항목, ADR 목록과 구현 계획. 구현 상태의 원본은 아키텍처의 구현 차이와 로드맵에 둔다.

## 검증

구현 계획의 체크리스트를 완료 조건으로 삼는다. 실제 Prometheus 노출, 일반·예열 동시 요청, 위조·만료 표식, 예외·취소 뒤 분류 복구, 집계의 과거 데이터 호환을 검증한다. 구현 시 전체 테스트·품질 검사·예열 활성 E2E를 실행한다. 이번 문서 작업에서는 링크·앵커·문서 경로 검사만 수행한다.
