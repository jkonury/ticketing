## 배경

M5.5-3은 선착순 한정 발급의 경합을 다룬다. 많은 사용자가 소수 수량을 동시에 노리고, 초과 발급과 중복 발급은 0건이어야 한다. 좌석 선점이 Redis Lua와 DB 유니크 제약으로 푸는 문제와 같은 구조다.

## 결정

1. 발급 경로는 Redis Lua 스크립트로 재고 감소와 회원 중복 Set 확인·등록을 원자적으로 하고, 성공하면 동기로 DB에 발급 행을 INSERT한다.
2. 최종 방어선은 DB의 `(정의, 회원)` 유니크 제약이다. Redis만 믿고 확정하지 않는다.
3. 유니크 위반이나 DB 실패 시 보상 스크립트로 Redis 재고와 Set을 되돌린다.
4. Redis 유실·불일치는 DB를 기준으로 재구성한다(재고 = 총 수량 − 발급 수, Set = 발급 회원).
5. 대기열과 입장 토큰은 쓰지 않는다. 보호는 Gateway rate limit만 쓴다.
6. 비교 실험으로 같은 시나리오를 DB 조건부 UPDATE 방식으로도 측정하고 결과를 `docs/performance/`에 기록한다. 프로퍼티로 전환한다.
7. rate limit 수치와 Redis 키 상세는 M5.5-3 측정 후 정한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| DB 조건부 UPDATE(`remaining > 0`) 단독 | 정합성은 충분하지만 한 행에 쓰기가 몰려 락 경합으로 지연이 늘 것으로 예상한다. 채택 전에 비교 실험으로 확인하므로 기본 경로로 정하지 않는다. |
| Redis만으로 발급(DB는 비동기 반영) | 유실 시 발급 사실을 잃는다. 확정은 DB 제약이 방어해야 한다는 규칙에 어긋난다. |
| 대기열 경유 발급 | 쿠폰 발급은 짧은 요청 하나이므로 대기열·입장 토큰 비용이 과하다. 코어는 대기열을 모른다는 규칙도 있다. |
| 메시지 큐로 비동기 발급 | 사용자가 결과를 즉시 알 수 없고 구성 요소가 늘어난다. 학습 목표는 경합 처리다. |

## 결과

- 얻는 것: 초과·중복 발급 0건을 부하 테스트로 검증할 수 있고, 좌석 선점과 같은 패턴으로 일관된다.
- 감수하는 것: Redis와 DB 두 저장소의 불일치 보정 로직이 필요하다. 수치(rate limit, 키 구성)는 측정 후 확정이라 현재 미정이다.
- 바뀌는 문서·지침: `docs/architecture.md` 쿠폰 절, `docs/roadmap.md` M5.5-3 (별도 작업에서 갱신).
