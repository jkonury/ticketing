# ADR 0048: Claude Code·Codex 공용 반자율 개발 파이프라인

- 상태: 합의
- 작성일: 2026-11-25
- 합의일: 2026-11-25
- 결정 주체: 사용자 합의
- 대체: 없음
- 대체됨·일부 변경: 없음
- 관련: [워크플로 로드맵](../workflow/roadmap.md), [서브에이전트 위임 지침](../rules/subagent-delegation.md), [delegate 워크플로](../../.agents/skills/delegate/references/workflow.md)

## 배경

지침(`AGENTS.md`, `docs/rules/`), 명령 정책 훅, 출력 요약 테스트 스크립트, herdr 교차 위임은 이미 갖췄다. 그러나 작업 한 건을 진행하는 흐름은 매번 사람이 손으로 이었다. 가장 비용이 큰 구간은 두 가지였다.

- 로드맵 항목 착수: 문서 조사, 계획, task 분해
- 구현 후 검증 루프: ktlint·detekt·test 실패를 고치는 반복

스킬은 Claude Code 쪽(`.claude/skills`)에만 있어 Codex 세션에서는 같은 절차를 쓸 수 없었다. 실패한 검사를 남긴 채 에이전트가 작업을 끝내는 일도 막지 못했다.

이 워크플로를 티켓팅 기능보다 우선하는 포트폴리오 주제로 삼는다. 그러려면 "이 하네스로 개발했다"는 주장을 측정 데이터로 뒷받침해야 한다. 그래서 파이프라인과 측정 구조를 함께 정한다.

## 결정

1. 자동화 목표는 반자율 파이프라인이다. `/plan-next`(계획) → 사람 승인 → `/implement`(task마다 구현 → 검증 게이트 → 로컬 커밋)로 진행한다. 무인 실행은 PR 자동 리뷰로만 한정하고, 이것도 후속 단계에서 정한다.
2. 기본 실행 단위는 단일 에이전트다. herdr 교차 위임은 기존처럼 별도 스킬(`/delegate`)로 둔다. 두 방식은 계획 문서 형식만 공유한다.
3. 스킬 원본은 `.agents/skills/`에 두고, `.claude/skills`는 이를 가리키는 심볼릭 링크로 둔다. 자동 호출 금지는 도구별로 설정한다. Claude Code는 frontmatter의 `disable-model-invocation`, Codex는 `agents/openai.yaml`의 `policy.allow_implicit_invocation`을 쓴다.
4. 범용으로 쓸 수 있는 실행 코드(훅 어댑터, 게이트, 지표 수집)는 `harness/`에 둔다. 이 프로젝트 전용 코드(명령 정책, 테스트 요약 스크립트)는 `scripts/agent/`에 그대로 둔다. 범용성이 확인되면 `harness/`를 별도 저장소로 추출하는 방안을 검토한다.
5. 훅 스크립트는 공통 어댑터 위에 짠다. 어댑터는 Claude Code와 Codex의 훅 입력을 같은 형태로 바꾼다. 두 도구를 같은 훅 스크립트로 지원한다.
6. 검증 게이트는 Stop 훅으로 건다. 게이트는 파이프라인 세션에만 적용하고, 다음 순서로 동작한다.
   - 파이프라인 세션 판별: 상태 파일 `.metrics/active.json`의 `session_id`와 현재 세션이 일치해야 한다.
   - 검사 선택: 커밋하지 않은 변경 경로를 보고 고른다. 현재 task에 AC가 있으면 AC를 실행하고, 없으면 변경 모듈의 ktlint·detekt·test를 실행한다. web은 `web-check.sh`, 문서는 `check-docs.sh`를 실행한다.
   - 반복 상한: 한 task에서 3회까지 막는다. 상한을 넘으면 통과시키고 미해결로 기록한다.
   - 제외 대상: E2E는 게이트에서 돌리지 않고, `/implement`의 마지막 단계에서 실행한다. 파일을 수정할 때마다 도는 포맷 훅(PostToolUse)은 두지 않는다.
7. 실행 계획은 `docs/workflow/plans/`에 두고 git으로 추적한다. 계획 문서는 frontmatter의 `status`로 상태를 남긴다(`draft` → `approved` → `done`). 대화에서 승인을 받으면 에이전트가 `status`를 바꾸고 승인 시각을 남긴다. 승인된 계획의 task별 로컬 커밋은 사용자가 요청한 커밋으로 본다. 푸시는 사람이 한다. 마일스톤 설계 계획(`docs/plans/`)은 지금처럼 따로 둔다.
8. 측정은 훅이 자동으로 수집한다. 원본은 `.metrics/`(git 제외)의 JSONL에 남기고, 계획 단위로 묶은 집계는 `docs/workflow/metrics/`에 둔다. 지표는 다음과 같다.
   - task별 토큰과 소요 시간
   - 게이트 반복 횟수
   - AC 첫 시도 통과율
   - 사람 개입: 질문 라운드, 구현 중 프롬프트, 게이트 상한 초과, 커밋 후 사람 수정의 네 유형을 각각 따로 센다. 계획 승인은 계획마다 고정으로 한 번이라 지표에서 뺀다.
9. 워크플로 작업은 별도 로드맵 [docs/workflow/roadmap.md](../workflow/roadmap.md)(W 트랙)로 관리하고 M6와 병행한다. M6 task는 파이프라인을 실제로 시험하는 대상으로 쓴다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 대화형 가속(스킬)만 도입 | 검증 루프를 사람이 계속 감시해야 하고, 측정할 단위(계획·task)가 생기지 않는다. |
| GitHub Actions에서 구현까지 무인 실행 | 검증에 Docker·Testcontainers·로컬 인프라가 필요해 CI에서 재현하는 비용이 크다. 비밀값 관리 부담도 생긴다. |
| 처음부터 별도 하네스 저장소로 분리 | 실제 사용 근거 없이 추상화부터 하게 된다. 디렉터리만 나눠 두고 추출은 나중에 판단한다. |
| 스킬을 도구별로 따로 관리 | 지침을 `AGENTS.md`·`docs/rules`로 하나로 모은 원칙과 어긋나고, 두 사본이 서로 어긋난다. |
| 모든 세션에 Stop 게이트 적용 | 질문 하나에 답한 세션도 모듈 테스트를 몇 분씩 돌리게 된다. |
| 파일 수정마다 포맷 훅 실행 | Gradle `ktlintFormat`은 한 번에 수 초 이상 걸린다. 독립 실행형 CLI는 버전을 따로 맞춰야 한다. Stop 게이트가 같은 문제를 잡는다. |
| 지표 수동 기록 | 1인 프로젝트에서는 기록이 금방 끊긴다. |

## 결과

- 얻는 것:
  - 두 도구가 같은 스킬과 같은 게이트를 쓴다.
  - 실패한 검사를 남긴 채 task가 끝나지 않는다.
  - 계획, 커밋, 지표가 연결되어 사례 연구의 근거가 남는다.
- 감수하는 것:
  - Stop 게이트가 모듈 테스트를 돌리는 동안 세션이 기다린다.
  - 두 도구의 훅 입력 형식이 바뀌면 어댑터를 고쳐야 한다. 대화 기록 파일 형식은 공식적으로 안정된 인터페이스가 아니어서, 토큰 파싱이 깨질 수 있다.
  - Codex의 프로젝트 훅은 사람이 신뢰 승인을 해야 동작한다.
  - 계획 승인이 곧 커밋 허용이므로 계획 검토가 부실하면 잘못된 커밋이 쌓인다.
- 바뀌는 문서·지침:
  - `AGENTS.md` 1절(문서 목록), 3절(작업 방식), 7절(커밋 예외)
  - `docs/roadmap.md`의 W 트랙 링크
  - 신설: `docs/workflow/roadmap.md`
  - `docs/architecture.md`는 서비스 구조를 다루는 문서라 바꾸지 않는다.

## 검증

- `harness/tests/`의 단위 테스트가 다음을 검사한다.
  - 어댑터가 두 도구의 훅 입력을 정규화하는 동작
  - 게이트의 세션 판별, 검사 선택, 반복 상한
- `docs/workflow/roadmap.md`의 각 단계 완료 기준에 실제 동작 확인 절차를 적는다. 예: 고의로 넣은 실패를 두 도구의 게이트가 잡는지 확인한다.
