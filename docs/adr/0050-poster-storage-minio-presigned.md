# ADR 0050: 공연 포스터 저장소와 presigned URL 업로드

## 배경

[ADR 0049](0049-ui-redesign-direction.md)의 커머스형 화면은 공연 포스터를 쓴다. 지금 `catalog.performance`에는 이미지 필드가 없고, 저장소에는 파일을 둘 곳이 없다. 포스터는 주최자가 공연을 등록할 때 올린다.

다음 제약이 있다.

- JWT는 브라우저에 노출하지 않는다. 브라우저 요청은 BFF를 거쳐 Gateway, core로 간다.
- 추후 k8s와 클라우드로 옮길 계획이 있다. 로컬에서만 동작하는 파일 시스템 저장은 그대로 옮기기 어렵다.
- 이미지 바이트가 BFF, Gateway, core를 모두 거치면 업로드 크기만큼 각 계층의 메모리와 연결을 점유한다.

## 결정

1. 포스터는 S3 호환 객체 저장소에 둔다. 로컬과 개발 환경은 MinIO를 Compose에 추가해 쓴다. 코드는 S3 API만 쓰고 MinIO 전용 기능에 의존하지 않는다.
2. 업로드는 presigned URL로 한다. 흐름은 다음과 같다.
   - 브라우저가 BFF에 업로드 URL을 요청한다.
   - BFF가 Gateway를 거쳐 core `catalog` 모듈에 요청한다. core는 주최자 권한을 확인하고 객체 키를 직접 만들어 짧은 유효 시간의 업로드 URL을 발급한다.
   - 브라우저가 그 URL로 저장소에 직접 업로드한다.
   - 브라우저가 BFF를 거쳐 업로드 완료를 알리면, core가 객체의 존재·크기·콘텐츠 유형을 확인한 뒤 공연에 객체 키를 저장한다.
3. 객체 키는 core가 만들고 클라이언트가 정하지 못한다. 허용 형식은 JPEG, PNG, WebP이며 크기 상한을 둔다. 콘텐츠 유형은 서명에 묶고, 크기는 완료 확인 단계에서 검사해 넘으면 객체를 지우고 거부한다.
4. DB에는 URL이 아니라 객체 키를 저장한다. 공개 조회 URL은 설정한 공개 기준 주소와 키로 조합해 응답한다. 저장소 주소가 바뀌어도 데이터를 고치지 않는다.
5. 포스터 조회는 공개 읽기로 한다. 업로드와 삭제 권한은 core만 가진다.
6. 완료 확인 없이 남은 객체(업로드만 하고 등록을 마치지 않은 경우)는 이번 범위에서 정리하지 않는다. 필요해지면 Batch 정리 작업을 따로 정한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 외부 이미지 URL 입력만 받기 | 가장 싸지만 시연이 외부 링크에 의존하고 업로드 흐름을 설계할 기회가 없다. |
| BFF를 거쳐 core로 업로드 프록시 | 구현은 단순하지만 이미지 바이트가 모든 계층을 지나 메모리와 연결을 점유한다. |
| 로컬 파일 시스템 저장 | k8s에서 여러 인스턴스와 볼륨 관리가 필요해 전환 비용이 크다. |
| DB에 공개 URL 저장 | 저장소 주소나 CDN이 바뀌면 데이터를 모두 고쳐야 한다. |

## 결과

- 얻는 것:
  - 이미지 바이트가 애플리케이션 계층을 거치지 않는다.
  - 로컬 MinIO에서 클라우드 S3로 설정만 바꿔 옮길 수 있다.
- 감수하는 것:
  - core에 S3 클라이언트 의존이 생기고, Compose와 개발 스크립트에 MinIO가 추가된다.
  - 브라우저가 저장소에 직접 접근하므로 저장소의 CORS와 공개 주소(nginx 경로)를 설정해야 한다.
  - 업로드 후 완료하지 않은 객체가 남을 수 있다.
- 바뀌는 문서·지침: 구현할 때 `docs/architecture.md`(인프라 구성, catalog 모듈), `AGENTS.md` 5절(명령), `docs/rules/backend-core.md`를 함께 고친다.

## 검증

- core 통합 테스트(Testcontainers MinIO)로 다음을 검증한다: 주최자가 아닌 사용자의 발급 거부, 키 위조 거부, 허용하지 않는 콘텐츠 유형 거부, 크기 초과 객체 삭제와 거부.
- web E2E에서 주최자가 포스터를 올리고 공연 목록에 표시되는지 확인한다.
