## 배경

PG 요청은 응답을 잃어도 외부에서 승인될 수 있다. 미확정 결과를 실패로 확정하면 돈이 빠져나갔는데 예매가 취소되는 문제가 생긴다. 웹훅만 기다리며 리스너를 완료하면 PG에 요청이 도달하지 않았을 때 복구가 M2 대사까지 미뤄진다.

환불도 REFUND_REQUESTED 저장 뒤 PG 호출 전에 장애가 날 수 있다. 해당 상태의 재수신을 무조건 무시하면 실제 환불을 다시 시도할 수 없다. 또한 ApplicationModuleListener는 기본적으로 새 트랜잭션에서 실행되어, 메서드 내부에서 DB 작업과 HTTP 호출을 나누는 것만으로는 외부 호출의 트랜잭션을 없앨 수 없다.

## 결정

1. PG 호출이 있는 결제·환불 리스너는 `@ApplicationModuleListener(propagation = NOT_SUPPORTED)`로 실행한다. application의 별도 서비스 트랜잭션에서 준비 저장을 커밋하고, 트랜잭션 밖에서 PG를 호출한 다음 필요한 결과를 새 트랜잭션으로 반영한다. 웹훅 기록·결과 저장·이벤트 발행은 하나의 트랜잭션으로 묶는다.
2. 결제의 타임아웃·연결 실패·5xx 등 Unknown은 REQUESTED를 유지하고 예외를 전파해 원 이벤트 발행을 미완료로 남긴다. 재시작 또는 명시적 재제출 때 동일 키와 본문으로 다시 요청한다. 확정적 거절만 실패 이벤트로 변환한다.
3. 환불 Rejected·Unknown은 REFUND_REQUESTED를 유지하고 예외를 전파한다. REFUND_REQUESTED 상태에서도 `refund-{orderId}`로 재호출하고 REFUNDED면 종료한다. 환불 실패 상태는 추가하지 않는다.
4. HTTP 호출과 응답 처리 사이에 웹훅이 먼저 도착할 수 있다. 거래 ID가 없으면 주문으로 결제를 찾아 붙이고, 지연 응답이 최신 상태를 되돌리지 않게 한다. 동일 웹훅과 동일 결과의 재수신은 결과 이벤트를 추가 발행하지 않는다.
5. 로컬 유니크·낙관적 락과 PG 멱등 키를 함께 사용한다. 병렬 재처리에서 HTTP 호출이 여러 번 발생할 수 있지만 실제 거래·환불과 커밋된 상태 전이·이벤트는 중복되지 않아야 한다. 충돌한 처리의 재시도는 새 트랜잭션에서 수행한다.
6. M1-5에는 주기적 재처리 스케줄러·대사를 추가하지 않는다. 레지스트리의 미완료 기록은 즉시 자동 재시도를 뜻하지 않는다. 운영 중 복구는 재시작·명시적 재제출에 의존하고, M2 대사는 별도 구현한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| Unknown을 결제 실패로 확정 | 외부 승인 가능성을 무시해 결제·예매 상태가 어긋난다. |
| Unknown은 로그만 남기고 이벤트 완료 | 웹훅이 없으면 M2 이전 복구 수단이 부족하다. |
| REFUND_REQUESTED 재수신을 모두 무시 | 저장 후 장애·PG 응답 유실에서 환불이 누락된다. |
| REFUND_FAILED 상태 추가 | 실패 상태별 복구 정책이 더 필요하다. 현재는 원 발행을 보존하고 같은 키로 재처리한다. |
| 리스너 기본 트랜잭션 안에서 PG 호출 | 외부 지연 동안 커넥션과 락을 붙들고, 내부 새 트랜잭션은 풀 고갈 위험을 늘린다. |

## 결과

- 얻는 것: 외부 I/O와 DB 트랜잭션 분리, 원 이벤트 기반 복구, 요청·환불의 안전한 재처리.
- 감수하는 것: 트랜잭션 사이의 장애·경합을 처리해야 한다. 미완료 발행을 재제출하기 전까지 처리가 지연될 수 있고, 영구 거절은 원인 해소가 필요하다. fake-pg는 메모리 저장소이므로 PG 자체 재시작에 걸친 멱등성은 보장하지 않는다.
- 바뀌는 문서·지침: 설계 6.4·10절과 payment phase 지시서. 공통 지침 변경 없음.

## 검증

구현 세션에서 PaymentListenerTests가 실제 리스너의 PG 호출 시 트랜잭션 부재와 레지스트리 완료/미완료를 검사한다. PaymentFlowTests는 원 미완료 발행 재제출, 지연 웹훅, 중복·경합, 환불 거절/미확정 후 복구를 검증한다. 테스트 이름은 지시서상 예정 이름이며 구현은 아직 하지 않았다.
