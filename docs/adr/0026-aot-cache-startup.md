# 0026. 부하 측정의 AOT 캐시 기동

## 상태

수락 (2026-11-14). 측정 러너 옵션이며 앱 코드와 `application.yml`은 바꾸지 않는다.

## 맥락

1,000명 동시 도착 측정에서 예매 생성 경로는 폭주 순간이 첫 호출이라 core 실행 샘플의 약 58%가
인터프리터 최상위 프레임이다. 충분히 예열하면(15회) p95가 274ms까지 내려간다([측정](../performance/m5-improvements.md)).
합의한 판정 조건은 "콜드(워밍업 요청 없음) + AOT 캐시 기동"이다. 기동 시 클래스 로딩·링크 비용을 줄이는 것이 목적이다.

## 검토한 대안

- 기동 시 자체 워밍업 호출: 앱 코드가 측정 목적을 알게 되고 운영 동작이 바뀐다.
- CRaC: 사용 중인 Temurin 25 빌드에서 확인하지 않았고, 체크포인트 운영 부담이 커서 이번에는 검토하지 않았다.
- 측정 기준 유지(콜드만): 클래스 로딩 비용이 p95에 섞인 채로 남는다.

## 결정

- `scripts/loadtest/run.sh --aot-cache`로 core·gateway·realtime을 `-Djarmode=tools extract`로 풀고(중첩 jar는 캐시 대상이 아니다),
  학습 기동에서 `-XX:AOTCacheOutput`으로 hot-seats 부하를 여러 번(기본 15회) 보낸 뒤 SIGTERM으로 캐시를 쓴다.
- 측정 기동은 매 회 새 프로세스를 `-XX:AOTCache -XX:AOTMode=on`으로 띄운다. 캐시를 못 쓰면 기동이 실패한다. 워밍업 요청은 보내지 않는다.
- 학습과 측정은 같은 힙·CPU·에이전트 옵션을 쓴다. `--aot-cache`와 `--warmup`은 함께 쓰지 않는다.
- 앱 코드와 설정은 바꾸지 않는다. 운영 배포에 적용하는 결정은 아니다.

## 결과

50명 콜드 p95가 3회 모두 300ms 미만이 됐다(141·199·215ms). 1,000명에서는 평균 p95가 약 1,276 → 1,041ms로 줄었지만
폭주 구간의 Interpreted 비율(약 59%)은 그대로라서 300ms에 닿지 않는다. 캐시 파일은 실행 루트(`build/loadtest/runs/<회차>/aot`)에
있고 core 약 254MB 등 크기가 크다. 학습 부하를 포함해 실행 시간이 길어진다.
