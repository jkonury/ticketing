# Frontend 리뷰 지침 (web)

`web` 변경(diff, PR)을 리뷰할 때 쓰는 기준이다. 작성 규칙은 [frontend.md](frontend.md)가 정의하고, 이 문서는 **그 규칙이 diff에서 지켜졌는지 확인하는 순서와 판정 기준**만 다룬다. 규칙 자체를 여기서 다시 정의하지 않는다. 충돌하면 `frontend.md`가 우선한다.

## 리뷰 방법

1. `git diff --stat`으로 범위를 확인하고, 변경된 파일이 `server/`, `app/api/`, `features/`, `components/`, `lib/` 중 어디인지 분류한다.
2. 아래 심각도 순서대로 확인한다. 위 단계에서 막히면 아래 단계는 지적만 짧게 남긴다.
3. 기존 코드의 문제는 이번 변경이 건드리지 않았다면 지적하지 않는다. 필요하면 별도 후속 항목으로 제안한다.
4. Next.js API(캐싱, 쿠키, Route Handler, `proxy`)가 쓰였으면 기억이 아니라 `web/node_modules/next/dist/docs/`의 설치된 버전 문서로 확인한다.
5. 실행 결과를 근거로 삼는다: `./scripts/agent/test/web-check.sh`(필요하면 `--build`)를 돌리고, 실패는 실패한 그대로 보고한다.

## 심각도

| 등급 | 의미 | 처리 |
|---|---|---|
| 차단 | 토큰 노출, 인증·CSRF 누락, 설계 규칙 위반, 데이터 정합성 위험 | 머지 전에 반드시 수정 |
| 주의 | 오류 처리 누락, 테스트 부재, 규칙 이탈, 접근성 결함 | 수정 권장. 미루려면 사유 기록 |
| 제안 | 가독성, 중복, 이름 | 선택 |

지적은 `파일:행`, 어긴 규칙(`frontend.md`의 절), 구체적인 실패 시나리오를 함께 적는다. 취향 차이는 차단·주의로 올리지 않는다.

## 1. 차단 항목

### 토큰과 세션
- JWT, `Authorization` 헤더, refresh 토큰이 응답 본문, 클라이언트 props, `NEXT_PUBLIC_*`, 브라우저 저장소, URL, 로그, 오류 메시지 어디에도 나가지 않는가.
- Server Component에서 클라이언트 컴포넌트로 세션 객체나 백엔드 응답 원본을 통째로 넘기지 않는가.
- 세션·토큰 처리 코드가 `server/auth/` 밖에 생기지 않았는가. 프로세스 메모리나 쿠키에 토큰을 두지 않는가.
- 쿠키 속성(`HttpOnly`, `SameSite=Lax`, 운영 `Secure`)을 약화하지 않았는가.
- 토큰 갱신을 건드렸다면: 세션당 한 번(single-flight + Redis 락)이 유지되는가, 실패 시 세션 파기 후 로그인으로 가는가.

### CSRF와 인증 경계
- 상태를 바꾸는 Route Handler·Server Action마다 `Origin` 검증이 있는가. 새 변경 엔드포인트에서 빠지기 쉽다.
- 인가를 `proxy.ts`나 메뉴 숨김에 맡기지 않았는가. 서버에서 `requireUser` 등으로 확인하는가.
- 401/403을 부분 실패로 삼키지 않고 세션 처리로 전파하는가.

### 서버 전용 경계와 백엔드 호출
- `server/` 아래 새 파일이 `import 'server-only'`로 시작하는가. `lib/`에 세션·환경 변수·Gateway 클라이언트가 들어가지 않았는가.
- `process.env`를 `server/env.ts` 밖에서 직접 읽지 않는가.
- 브라우저가 Gateway를 직접 호출하지 않는가(SSE 제외). 컴포넌트·Route Handler가 Gateway URL로 직접 `fetch`하지 않는가.
- SSE에 JWT를 싣지 않고 단기 티켓을 쓰는가. 재연결마다 새 티켓을 받는가.

### 설계 규칙과의 정합
- BFF에서 조인을 흉내 내거나 백엔드 규칙(좌석 확정, 대기열 판정, 입장 토큰 검증)을 재구현하지 않았는가. 필요한 API가 없으면 소유 모듈에 추가를 제안하는 방향인가(ADR 0022).
- 좌석 선점 성공 여부를 클라이언트 상태가 아니라 서버 응답으로 판단하는가.
- `Idempotency-Key`가 사용자 의도 한 건당 하나이고 재시도·재제출에 같은 키를 쓰는가. 요청마다 새로 만들지 않는가.
- 입장 토큰을 `X-Admission-Token`으로 전달하되 형식을 해석하지 않는가.

## 2. 주의 항목

### 데이터 경계
- 백엔드 응답을 zod로 검증하는가. `any`, 근거 없는 `as`가 없는가.
- 오류를 `ProblemDetail`의 `code`로 분기하는가. 메시지 문자열 비교가 없는가. 내부 메시지·스택이 브라우저로 나가지 않는가.
- 사용자별 데이터가 `no-store`인가. 캐시 여부가 공통 클라이언트 호출 옵션으로 드러나는가.
- 모든 Gateway 호출에 타임아웃이 있고, 타임아웃·연결 실패가 일시 오류로 처리되는가.

### 조합 함수
- 독립 호출을 `Promise.all`/`allSettled`로 병렬화했는가. 불필요한 순차 `await`가 없는가.
- 핵심/부가 구분이 명시되어 있고, 부가 실패가 결과 타입에서 "빈 값"과 구분되는가.
- 결과가 화면용으로 가공된 타입인가. 백엔드 응답을 그대로 이어 붙이지 않았는가.

### SSE 훅
- 언마운트 시 연결과 재연결 타이머를 모두 정리하는가.
- 지수 백오프(상한, 지터)가 있고, 재시도해도 소용없는 종료(인증 실패 등)와 일시 오류를 구분하는가.
- 재연결 시 `?lastEventId=`로 이어 받는가. `EventSource` 자동 재연결에 기대지 않는가.
- 이벤트 중복·순서 역전에도 화면 상태가 깨지지 않는가.

### 예매 화면
- 남은 시간이 서버 만료 시각 기준인가. 클라이언트에서 5분을 따로 세지 않는가.
- 결제·예매 버튼이 요청 중 비활성화되는가.
- 선점 실패, 선점 만료, 입장 토큰 만료(대기열 복귀), 결제 실패 안내가 구분되는가. 새 오류 코드를 일반 오류로 삼키지 않는가.

### 컴포넌트 구조
- 기본이 Server Component이고 `'use client'`가 상호작용·브라우저 API가 필요한 최소 단위에만 붙었는가.
- 초기 데이터를 `useEffect`로 가져오지 않는가. 서버 상태를 전역 스토어에 복사하지 않는가.
- 라우트마다 `loading`과 `error` 경계가 있고, `error`가 내부 오류를 노출하지 않는가.
- 변경이 Server Action(화면에 묶인 폼) 또는 Route Handler(클라이언트 직접 호출)로 구현되고 같은 `server/` 함수를 쓰는가.

### 테스트
- 변경한 동작에 맞는 테스트가 있는가: 조합 함수(부분 실패, 타임아웃), 토큰 갱신(동시 갱신, 실패 시 파기), SSE 훅(재연결, 언마운트), 변경 엔드포인트(Origin 허용/거부, 미인증).
- 컴포넌트 테스트가 구현 세부가 아니라 사용자 동작을 검증하는가.
- 테스트를 지우거나 비활성화해 통과시키지 않았는가.
- 토큰 노출 위험이 있는 변경이면 E2E 토큰 비노출 검증이 유지되는가.

## 3. 제안 항목

- **분리와 재사용**: 한 파일이 여러 화면 단계나 독립 상태를 함께 맡는가(500줄은 검토 신호일 뿐이다). 같은 책임이 반복되면 공통 컴포넌트·훅으로 추출했는가. 반대로 모양만 비슷한 코드를 억지로 합치지 않았는가. 공통화 시 문구, 접근성, 이벤트 동작이 유지되는가.
- **loading/error 공유**: 경계 파일은 유지하고 표시 UI만 공유하는가. 경계 파일을 없애거나 옮겼다면 처리 범위 변화를 확인했는가.
- **TypeScript와 스타일**: `strict`, named export(Next 요구 파일 제외), kebab-case 파일명, PascalCase 컴포넌트. ESLint 규칙을 끄는 주석이 없는가.
- **접근성**: 시맨틱 마크업, 키보드 조작, 좌석 버튼의 좌석 번호·상태 레이블.
- **UI**: [UI 가이드](../ui-guide.md)의 공통 시각 규칙과 화면별 구성을 따르는가.
- **주석**: "왜"가 코드에 드러나지 않을 때만 있는가.

## 4. 문서 정합

- 설계와 다르게 구현했다면 `docs/architecture.md` 변경 합의가 있었는가. 문서와 코드가 어긋난 채 남지 않았는가.
- 단계 항목을 끝낸 변경이면 `docs/roadmap.md` 체크박스가 갱신됐는가. "단계와 무관한 후속 항목"을 요청 없이 앞당겨 구현하지 않았는가.
- 설계를 바꾸는 결정이면 새 ADR이 있는가.
- 명령, 환경 변수, 디렉터리 구조가 바뀌면 `AGENTS.md`, `web/README.md`, `.env.example`이 따라왔는가.

## 5. 검증 확인

- `./scripts/agent/test/web-check.sh`가 통과했는가. 라우팅·빌드에 영향이 있으면 `--build`도 확인한다.
- core·gateway·realtime 흐름이나 SSE·인증 경계를 바꿨다면 `./scripts/e2e/run.sh --web`을 실행했는가.
- 문서를 옮기거나 제목·링크를 바꿨다면 `./scripts/agent/docs/check-docs.sh`를 통과했는가.

## 리뷰 결과 형식

```
## 요약
변경 범위와 전반적 판단 한 줄.

## 차단
- `web/src/...:행` (frontend.md 「절 이름」): 문제와 실패 시나리오. 제안 수정.

## 주의
- ...

## 제안
- ...

## 검증
- web-check: 통과/실패(실패한 테스트 이름과 메시지 일부)
- 실행하지 않은 검사와 사유
```

지적이 없는 등급은 "없음"으로 적는다. 확인하지 못한 항목은 통과로 쓰지 않고 "확인 안 함"으로 적는다.
