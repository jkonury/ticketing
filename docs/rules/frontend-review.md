# Frontend 코드 리뷰 지침

`web`의 변경 또는 기존 코드를 리뷰할 때 적용한다. 구현 규칙은 [Frontend 지침](./frontend.md), 설계와 계약은 [아키텍처](../architecture.md)와 관련 ADR을 기준으로 한다. 범위와 변경 의도를 먼저 확인하고, 변경된 코드뿐 아니라 직접 영향을 받는 호출자·API 계약·테스트까지 살펴본다. 요청 범위를 벗어나는 개선은 별도로 구분한다.

## 리뷰 순서

1. 변경의 목적과 사용자 흐름을 파악하고 관련 설계·계약과 기존 테스트를 확인한다.
2. 재현 가능한 오류, 데이터 정합성, 보안 문제를 먼저 찾는다. 정상 경로와 실패·재시도·취소·경계 조건을 함께 살핀다.
3. 컴포넌트 책임, 중복과 재사용, 접근성, 성능을 검토한다. 기존 컴포넌트나 훅으로 같은 책임을 표현할 수 있는지 확인하되, 겉모양만 같은 코드를 억지로 합치도록 요구하지 않는다.
4. 변경으로 깨질 수 있는 동작에 기존 테스트가 있는지 확인하고, 필요한 검증과 실행하지 못한 검증을 기록한다. 테스트 개수나 구현 세부사항을 그대로 따라 하는 테스트를 목표로 삼지 않는다.

## 중점 확인 사항

- **인증과 경계**: JWT와 비밀 값이 브라우저 응답·props·저장소·URL·로그에 노출되지 않는지, 서버 전용 코드가 클라이언트에 섞이지 않는지 확인한다. 상태 변경 요청의 Origin 검증과 서버 측 인가·세션 처리도 살핀다.
- **BFF와 데이터**: Gateway 호출과 응답 검증이 정해진 경계를 지키는지, 사용자별 캐시·타임아웃·인증 오류 전파·부분 실패 구분이 계약에 맞는지 확인한다.
- **예매와 결제**: 좌석 상태를 확정 근거로 오인하지 않는지, 멱등 키가 사용자 의도와 재시도에 맞게 유지되는지 확인한다. 입장 토큰 오류, 선점 만료, 결제 실패, 중복 제출과 시계 오차를 살핀다.
- **SSE와 비동기 작업**: 티켓 재발급, 재연결과 마지막 이벤트 ID, 재시도할 수 없는 오류, 언마운트 시 연결·타이머·요청 정리를 확인한다. 연결이 끊겼을 때 오래된 데이터와 사용자 안내도 살핀다.
- **화면과 접근성**: 로딩·오류·빈 상태와 부분 실패가 구분되는지, 오류 경계와 복구 동작이 적절한지 확인한다. 시맨틱 마크업, 키보드 조작, 레이블과 상태 안내를 검토한다.
- **구조와 재사용**: 컴포넌트나 훅이 독립된 여러 책임을 담당하는지, 기능 내부 코드와 범용 UI의 위치가 적절한지 확인한다. 라우트 경계나 화면별 문구·동작을 바꾸는 공통화인지 살핀다. 줄 수는 검토 신호이며 단독 결함은 아니다.
- **성능**: 실제 사용자 흐름에서 불필요한 요청, 순차 호출, 반복 렌더링이나 큰 목록 처리로 문제가 발생할 가능성이 있는지 확인한다. 측정 없이 성능 개선 효과를 단정하지 않는다.

## 결과 작성

- 발견 사항은 심각도 순으로 작성하고, 각 항목에 파일과 관련 줄, 발생 조건, 사용자나 시스템에 미치는 영향, 수정 방향을 적는다. 가능한 경우 기존 테스트나 재현 결과를 근거로 든다.
- 심각도는 영향과 발생 조건을 기준으로 판단한다. 보안·데이터 손실이나 핵심 흐름 차단을 우선하고, 제한된 기능 오류와 유지보수 개선은 구분한다. 근거가 부족한 추측은 확정된 결함으로 쓰지 않는다.
- 라이브러리 API나 버전에 관한 판단은 설치된 버전의 문서 또는 공식 문서로 확인한다. 확인하지 못한 가정은 명시한다.
- 발견 사항이 없더라도 검토 범위, 실행한 검사, 실행하지 못한 검사와 남은 위험을 밝힌다. 리뷰 요청만으로 코드를 수정하거나 테스트를 비활성화하지 않는다.
