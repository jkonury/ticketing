# 용어사전

ticketing의 문서·코드 주석·issue·PR·커밋 메시지에서 쓰는 표준 용어다. 같은 개념은 같은 말로 쓰고, 코드 식별자와 설정 키는 원문을 유지한다. 커밋 형식은 [공통 지침](../AGENTS.md)의 8절을 따른다.

설계의 기준은 [설계 합의서](./design.md), 구현 여부의 기준은 [로드맵](./roadmap.md)이다. 아래에는 구현 예정인 개념도 포함되며, 용어가 실렸다는 뜻이 구현 완료를 의미하지는 않는다.

## 1. 표기 원칙

- 공식 제품명·API·설정 키는 원문을 유지한다. 예: Spring Modulith, Redis Streams, `ApplicationModuleListener`.
- 일반 개념은 설계서와 기존 문서의 한국어 표현을 우선한다. 예: 스키마, 배치, 커밋, 좌석 선점.
- 식별자는 백틱으로 감싼다. 아직 정하지 않은 클래스·테이블·이벤트 이름을 표준 식별자로 만들지 않는다.
- 약어는 필요하면 처음에 풀어 쓴다. BFF, JWT, SSE, MSA, k8s처럼 저장소에서 통용되는 약어는 그대로 쓴다.
- 새 용어는 공식 명칭 → 저장소의 일관된 표현 → 실무 통용어 → 자연스러운 한국어 순으로 정한다.

## 2. 예매 도메인

| 표준 표기 | 영어·식별자 | 프로젝트에서의 뜻 |
| --- | --- | --- |
| 회원 | `member` | 가입·로그인·인증과 역할을 관리하는 대상 및 코어 모듈 |
| 일반 사용자 | `USER` | 공연을 조회하고 티켓을 예매하는 역할 |
| 주최자 | `ORGANIZER` | 공연·회차를 등록하고 판매·정산 정보를 확인하는 역할. 플랫폼 관리자와 구분한다 |
| 공연 | `catalog` 소유 | 공연 자체의 정보. 특정 날짜·시각의 회차와 구분한다 |
| 회차 | — | 같은 공연의 특정 일시 상연 단위. 선점·좌석 확정의 기준 |
| 공연장 | — | 공연이 열리는 장소 |
| 좌석 배치 | — | 공연장의 지정석 구성. Spring Batch와 구분한다 |
| 지정석 | — | 개별 좌석을 선택해 예매하는 방식. 등급별 수량제 좌석은 현재 범위 밖이다 |
| 좌석 선점 | seat hold | 결제 전 Redis에서 좌석을 임시 확보하는 것. 유지 시간 5분, 1회 최대 4매 |
| 다중 좌석 선점 | Lua | 여러 좌석의 선점이 전부 성공하거나 전부 실패하도록 원자적으로 처리하는 것 |
| 예매 | `booking` | 좌석 선점부터 생성·확정·만료·취소까지의 업무 및 코어 모듈. 일반 명칭은 예약 대신 예매로 쓴다 |
| 예매 대기 | `PENDING` | 예매 생성 후 결제 결과를 기다리는 상태. 대기열 순번 대기와 구분한다 |
| 예매 확정 | `CONFIRMED` | 결제 성공 후 예매가 확정된 상태. DB의 (회차, 좌석) 유니크 제약이 중복 확정의 최종 방어선이다 |
| 예매 만료 | `EXPIRED` | 결제 대기 시간이 지난 예매 상태. Redis 선점 키 만료와 DB 상태 변경은 구분한다 |
| 예매 취소 | `CANCELLED` | 사용자가 예매를 취소한 상태. 결제된 예매는 환불 흐름이 수반된다 |
| 좌석 반환 | — | 실패·만료·취소 등으로 좌석을 다시 예매할 수 있도록 해제하는 것 |
| 좌석 스냅샷 | Redis | 회차별 현재 좌석 현황. SSE 접속 시 전달할 초기 상태 |
| 결제 | `payment` | PG 결제 요청·결과 처리·환불을 맡는 코어 모듈 및 업무 |
| PG | Payment Gateway | 결제를 처리하는 외부 시스템. 요청을 라우팅하는 Gateway 앱과 구분한다 |
| 가짜 PG | `fake-pg` | 지연·타임아웃·실패·중복 웹훅을 재현하는 별도 앱. 실제 PG 연동은 후속 범위다 |
| 웹훅 | webhook | PG가 코어에 결제 결과를 알리는 요청. 중복·지연 도착할 수 있다 |
| 멱등성 / 멱등 키 | idempotency / idempotency key | 같은 요청을 반복해도 업무 결과가 중복되지 않는 성질 / 결제 요청·웹훅 중복 처리의 기준 키 |
| 환불 | refund | 결제 금액을 돌려주는 처리. 예매 취소라는 상태 변경과 구분한다 |
| 만료 후 결제 성공 | — | 좌석 선점이 만료된 뒤 결제 성공이 도착한 경우. 자동 환불로 보상한다 |
| 정산 | `settlement` | 이벤트로 받은 자기 스키마의 사본을 기준으로 주최자 지급액·수수료 등을 계산하는 업무 |
| 결제 대사 | reconciliation | PG 거래 내역과 내부 기록을 비교해 불일치를 검출·기록하는 작업 |
| 알림 | `notification` | 예매 확정·취소 이벤트에 반응하는 코어 모듈. 초기 구현 범위는 로그 출력이다 |

## 3. 대기열·인증·화면

| 표준 표기 | 영어·식별자 | 프로젝트에서의 뜻 |
| --- | --- | --- |
| 대기열 | queue, Redis Sorted Set | `realtime`이 소유하는 입장 순서. 코어는 대기열을 모른다 |
| 입장 토큰 | admission token | 차례가 된 사용자에게 실시간 앱이 발급하고 Gateway가 예매 API에서 검증하는 단기 토큰 |
| SSE 티켓 | SSE ticket | 브라우저의 SSE 접속을 위해 BFF가 발급하고 Gateway가 검증하는 단기 티켓. 입장 토큰과 목적이 다르다 |
| SSE | Server-Sent Events | 실시간 앱이 대기 순번·좌석 현황을 브라우저에 전달하는 단방향 연결. BFF를 거치지 않는다 |
| 재연결 | `Last-Event-ID` | SSE 연결이 끊긴 후 마지막 수신 이벤트를 기준으로 연결을 이어가는 처리 |
| 인증 | authentication | 요청한 사용자가 누구인지 확인하는 것 |
| 인가 | authorization | 해당 사용자가 작업을 수행할 수 있는지 판단하는 것 |
| 역할 | role | 일반 사용자·주최자 등 인가 판단에 쓰는 자격 |
| access 토큰 | JWT | 코어 API 인증에 쓰는 토큰. BFF 서버 측에서 보관하며 브라우저에 노출하지 않는다 |
| refresh 토큰 | opaque token | access 토큰 갱신용 불투명 난수. DB에는 해시만 저장하며 갱신 때 교체한다. JWT와 구분한다 |
| 토큰 로테이션 | rotation | 갱신 시 이전 refresh 토큰을 폐기하고 새 토큰으로 교체하는 것 |
| 세션 | session | BFF의 로그인 상태. 브라우저에는 httpOnly 세션 쿠키만 전달한다. 에이전트 대화는 작업 세션으로 구분한다 |
| BFF | Backend for Frontend, `web` | Next.js 서버에서 인증 토큰 보관·갱신과 화면별 API 응답 조합을 맡는 부분 |
| 조합 응답 | aggregation | 공연 정보·잔여 좌석·내 예매 여부 등 여러 API 결과를 화면 단위로 묶은 응답 |

## 4. 구조·데이터·실행

| 표준 표기 | 영어·식별자 | 프로젝트에서의 뜻 |
| --- | --- | --- |
| 코어 모듈 | Modulith application module | `io.github.ticketing` 바로 아래의 member, catalog, booking, payment, settlement, notification 패키지 경계 |
| Gradle 모듈 | subproject | core, core-batch, realtime, gateway, fake-pg 등 빌드 단위. 코어 모듈과 구분한다 |
| 실행 앱 / 배포 단위 | application | 별도로 실행하는 앱. `core-batch`는 코어 코드를 공유하는 배치 실행 앱이다 |
| Modulith | Spring Modulith | 코어를 한 앱으로 실행하면서 패키지별 모듈 경계를 검증하고 이벤트로 연동하는 구조 |
| MSA | Microservices Architecture | 모듈을 독립 배포 단위로 분리하는 후속 구조. payment·settlement가 우선 분리 대상이다 |
| 헥사고날 | hexagonal architecture | booking·payment·settlement에 적용하는 도메인·포트·어댑터 구조 |
| 입력 포트 / 출력 포트 | `provided` / `required` | 유스케이스를 제공하는 경계 / 영속성·외부 시스템에 요구하는 경계. 패키지 명명은 ADR 0016을 따른다 |
| application 서비스 | `application.service` | 유스케이스를 구현하는 계층. 제품 전체나 독립 배포 서비스를 뜻하는 표현과 구분한다 |
| 이벤트 | Modulith event | 코어 모듈 사이의 상태 변경 전달 수단. 다른 모듈 내부 클래스를 직접 호출하지 않는다 |
| 이벤트 발행 레지스트리 | `event_publication` | Modulith 이벤트 전달 상태를 기록하는 저장소. public 스키마에 둔다 |
| Redis Streams | — | 코어가 발행한 좌석 변경을 실시간 앱이 구독하는 앱 간 전달 수단. Modulith 이벤트와 구분한다 |
| 스키마 | PostgreSQL schema | 모듈별 데이터 소유 경계. 스키마를 넘는 외래 키·조인을 만들지 않는다 |
| 트랜잭션 | DB transaction | DB 작업의 원자적 처리 경계. PG 거래 내역의 거래와 구분한다 |
| 마이그레이션 | Flyway migration | DB 스키마 변경 파일과 실행. MSA 전환·앱 분리·데이터 이관과 구분한다 |
| 명령 / 조회 | Command / Query | 쓰기는 JPA, 조회·집계는 jOOQ로 분담한다 |
| TTL | Time to Live | Redis 키 등의 유지 시간. 좌석 선점 TTL은 5분이다 |
| Virtual Thread | — | 코어 WebMVC 요청 처리에 사용하는 Java 스레드. 실시간 앱의 WebFlux·Coroutines와 구분한다 |
| 배치 | Spring Batch | 정산·미결제 예매 정리·결제 대사를 수행하는 작업 |
| Job / Step / chunk | Spring Batch | 배치 작업 / 작업 단계 / 묶음 처리 단위. API 식별자는 원문을 유지한다 |
| Gateway | `gateway` | 라우팅·입장 토큰 및 SSE 티켓 검증·요청 제한을 맡는 앱. PG와 구분한다 |
| 실시간 앱 | `realtime` | WebFlux·Coroutines·SSE 앱. Redis만 사용하고 PostgreSQL에 접근하지 않는다 |
| k8s | Kubernetes | MSA 전환 단계에서 도입할 배포·실행 환경 |

## 5. 조사·검증 용어

| 표준 표기 | 뜻 |
| --- | --- |
| 증상 / 원인 | 관측한 현상 / 그 현상을 만든 동작·조건. 추정은 확인된 원인과 구분한다 |
| 장애 / 실패 | 시스템이 정상 동작하지 못하는 상태 / 개별 요청·Job·테스트의 결과 |
| 오류 응답 / 예외 | 클라이언트에 전달하는 실패 정보 / 코드에서 발생하는 예외 |
| 재현 / 검증 | 같은 조건에서 문제를 다시 발생시키는 것 / 기대 동작과 실제 결과를 비교하는 것 |
| 단위 테스트 / 통합 테스트 / 모듈 테스트 | 개별 로직 / DB 등 실제 연동 / Modulith 모듈 범위 검증. 세부 기준은 백엔드 규칙을 따른다 |
| fixture | 테스트용 입력 데이터. 실제 개인정보·결제 정보를 대신할 합성 데이터를 사용한다 |
| 롤백 | 코드·설정·배포를 이전 상태로 되돌리는 것. PG 환불이나 업무 보상과 구분한다 |
| 보상 | 이미 진행된 업무의 결과를 후속 처리로 상쇄하는 것. 만료 후 결제 성공에 대한 환불 등이 해당한다 |
| 단계 | 로드맵의 M0~M6. 예정된 작업과 완료된 구현을 구분해 쓴다 |

문제 조사 기록은 [문제 해결 템플릿](./templates/trouble-shooting.md)을 사용한다. 용어와 실제 코드가 달라졌다면 식별자를 임의로 바꾸지 말고 설계·로드맵·관련 ADR과 함께 확인한다.
